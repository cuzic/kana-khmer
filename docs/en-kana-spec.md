# en-kana 表記仕様 (v0.1 叩き台)

> **状態**: 叩き台。実機(デスクトップの Chrome の Windows・macOS)での描画確認は未実施。未決の点は §5。決定の経緯は [ADR-0031](adr/0031-en-kana-with-shoulder-ipa.md)。
> 実装の正は `tools/en-prosody-spike/src/kana.py`(Python)で、`packages/en-prosody/src/kana.ts`(TS 版)が同じ出力を返す。

日本語話者が英語の**推定の発音**を読むための、英語→カナ表記。入力は ARPABET(CMUdict の第 1 発音、ストレス数字つき。米国英語)で、
出力は「基本のカナ + 右肩の IPA 小文字」。表記の文字列に NFKC/NFKD を適用しない(修飾文字が通常の文字に置き換わる)。

## 1. 方針
- 基本のカナは、日本語話者が読める最も近い音にする。
- 日本語にない区別は、IPA の小文字(Unicode の修飾文字)を右肩に添えて示す。
- 「詳細」は右肩を含む。「ライト」は右肩を除く(暫定。§5 の未決)。
- 母音の前以外の子音は、母音を足さない小書きカナ(ㇰ ㇳ ㇷ゚ ㇲ ㇱ ㇺ ㇽ)で書く(ko-kana の考え方と同じ)。有声の子音には `ᵈ` `ᵍ` `ᵇ` `ᶻ` を添える。
  例外: n は `ン`、w は `ウ`、y は `イ`(いずれも全角)、h は書かない。w・y の全角は、弱い母音との組(you → `イᵊ`)で不自然になる(§5 の未決 5)。

## 2. 変換表
「由来」は、その表記を誰が決めたか。**user** = ユーザーが画面を見て指示した、または質問への回答として選んだ。**agent** = エージェントの判断。未決の点は §5。

| 音 | 表記 | 例 | 由来 |

## 3. 使う右肩の字と Unicode の事実(`unicodedata` の名前で確認)
- `ʳ`(U+02B3)`ˡ`(U+02E1)`ʰ`(U+02B0)`ᶿ`(U+1DBF)`ᶞ`(U+1D9E)`ᶺ`(U+1DBA)`ᶦ`(U+1DA6)`ᶷ`(U+1DB7)`ᵓ`(U+1D53)`ᵊ`(U+1D4A)`ᵑ`(U+1D51)
  `ᵈ`(U+1D48)`ᵇ`(U+1D47)`ᵍ`(U+1D4D)`ᶻ`(U+1DBB)`ᶾ`(U+1DBE)`ᵛ`(U+1D5B)`ᵗ`(U+1D57)は、対応する IPA の字の右肩形。
  (`ᵛ` は、現在の kana.py の出力には出ない(v はヴ行)。glyph-check の確認用に含めている。`ᶟ`(U+1D9F、ɜ の右肩形)は ɝ に使う。)
- **`ᵆ`(U+1D46)は「MODIFIER LETTER SMALL TURNED AE」で、æ の右肩形ではない。** æ の右肩形は U+10783(Latin Extended-F、Unicode 14)で、対応するフォントが少ない。
- ɾ の右肩形は U+107A9、ɜ は `ᶟ`(U+1D9F)、r 音色は `˞`(U+02DE、RHOTIC HOOK)がある。ɾ と æ の U+107xx は対応フォントが少ない。
- フォントの対応(別のエージェントが fontTools の cmap で確認したもの。Linux。こちらでは再確認していない): Noto Sans JP は上の 19 の字をすべて欠く。DejaVu Sans・Noto Sans(latin-ext)は持つ。小書きカナは Noto Sans JP が持ち、DejaVu 系は欠く。

## 4. ko-kana との関係
同じ字を別の意味で使う: ko-kana の `ᵓ`(ㅓ ≈ [ʌ])と本記法の `ᵓ`(ɔ)。ko-kana の `ᵓ` が表す音は、本記法では `ᶺ` で書く。[ADR-0005](adr/0005-ng-shared-modifier.md) が
「多言語共通」を理由に `ᵑ` を選んだ方向とは逆になる。ko-kana は設計中で未コミット(`docs/ko-kana-spec.md`・ADR-0024)。

## 5. 決定済みと未決
**決定済み(ユーザーの選択。2026-09-30)**
- æ の右肩は `ᵆ`(turned ae)の代用のまま進める(本物の U+10783 は将来の課題)。
- ɝ は `ᶟʳ`、ɚ は `ʳ` だけ(ɚ を `ʳ` だけにしたのは agent の推論だったが、ユーザーが現状維持を選択した)。
- ビートは、PoC は語単位のまま。音節単位は次に設計する。
- ライトで何を残すかは、ADR-0006 の方式(機能負担量の実測)で測って決める(次のセッション)。

**未決**
1. **ライトで何を残すか**(上記。測定は次のセッション)。いまは右肩の字を一律に消す暫定で、the → `ㇲ`、to → `ㇳ`、a → `ァ`、rice/lice = `ライㇲ`、road/load = `ロウㇳ`、thin/shin = `シン`、
   cup/cop = `カㇷ゚` になり、入門・標準プリセットの既定がこのライトになる。少なくとも `ʳ` `ˡ` `ᶿ` `ᶞ` は残す候補。弱形の `ᵊ` を残すか全角にするかも。
2. **半母音 + ə のうち w**: was → `ウᵊㇲᶻ`、would → `ウᵊㇳᵈ`(y は ヤᵊ に決めた)。`ワᵊ` にするか。
3. **右肩の文字が 2 つ重なる語**(`シᶿᶦンᵑㇰ`、`カʰᵆㇳ`)が読めるか。有気音の `ʰ` で重なる語が増えた。
4. **右肩の字の意味が記法ごとに違ってよいか**(ko-kana の `ᵓ` と本記法の `ᵓ`。§4)。ユーザーから意味の違いの説明を求められている。
5. **有気音の解釈**: 二次強勢の母音の前も含めるか、ch を含めるか(ユーザーは p t k ch と言った)、連結で移った子音を除くことでよいか。
6. **母音消失の表記**: ユーザーの提案(2026-09-30): you can は「ュㇰン みたいなのでもいい。母音消失が起きる組合せだから」。弱い you の母音が `ュ` になり、can の弱い母音が消えて `ㇰン`(母音なしの小書き + ン)になる形。
   決めること: どの組合せを消失とするか(弱形の can・and・on・in などが母音で終わる語のあとに来るとき、など。規則か、音声で観測したときだけか)、母音の消失を `ᵊ` なしで表すこと、弱い you を `ヤᵊ` でなく `ュ` にするか。
   ADR-0032 の「語末の子音の脱落・同化などの規則は未実装」と同じ種類の規則で、規則が観測と合うと確かめてから足すのが筋。
7. **描画の確認**: 拡張が動くのはデスクトップの Chrome なので、Windows・macOS での目視確認が要る。拡張の font-family(`"Noto Sans JP", "Hiragino Sans", "Yu Gothic", system-ui, "Noto Sans", "DejaVu Sans"`)は
   glyph-check の `sys`/`noto` のどちらとも違う。確認は、拡張の font-family そのものを使うか、拡張の実画面のスクリーンショットを単位にする。`ᶟ`・`ʰ` が出るようになったので、確認する字が増えた。
