# クメール語 挨拶・日常会話アプリ 詳細設計 (v0.1 ドラフト)

前提となる2つの設計書(アプリ設計書 / カナ表記システム設計書 v0.2)、Opus による整合性レビュー、
実機検証(`cuzic/khmer-glyph-check`、iOS/Android エミュレータ)の結果を反映した詳細設計。
「決定案」のうち、§8 の表にあるものは承認済み。未決事項は §8 に集約した。

## 0. 検証で確定した事実(設計の前提)

| 事実 | 根拠 | 設計への反映 |
|---|---|---|
| 修飾文字 `ʰ ˡ ʳ ᵋ ᵓ ᵅ ᵊ ᶤ` は iOS / Android 10・14 の Chrome/Safari で表示できる | glyph-check の目視 | 表記は修飾文字ベースで確定 |
| `゚`(U+309A)は全環境で表示できる | 同上 | 鼻濁音・半濁点は現行どおり |
| `◌̯`(U+032F)は **Android で欠字**(システムフォントでも Noto 同梱でも)。iOS は可 | 同上 | 専用フォントを同梱(§3) |

| CI の自動判定(canvas 比較)は誤検知・見逃しが多い | 実験 | 合否は目視、自動判定は補助 |
| 検証は Chrome 74/113 と iOS 18.7 のシミュレータのみ | — | 実機・他メーカー端末は未検証(リスクとして残す) |

## 2. 表記ライブラリ `khmer-kana` (Phase 0)

### 2.1 型定義(H1)

```ts
// IPA は音素表記。有気音は1トークン("kʰ")。入破音は ɓ ɗ を正とし、b d は別名として受理して正規化する
type Consonant =
  | "p"|"pʰ"|"ɓ"|"t"|"tʰ"|"ɗ"|"c"|"cʰ"|"k"|"kʰ"|"ʔ"
  | "m"|"n"|"ɲ"|"ŋ"|"j"|"r"|"l"|"ʋ"|"s"|"h"
  | "g"|"f"|"ʃ"|"z";                       // 外来語のみ
type Vowel = "i"|"e"|"ɛ"|"ɨ"|"ə"|"a"|"ɑ"|"u"|"o"|"ɔ";
type Coda  = "p"|"t"|"k"|"c"|"ʔ"|"m"|"n"|"ŋ"|"ɲ"|"j"|"w"|"l"|"h";   // 語末 r は保持しない(発音しない)

interface Nucleus {
  v1: Vowel;
  long: boolean;        // ː の有無。二重母音 iə ɨə uə eə oə ɔə aə は long=true が既定
  v2?: Vowel;           // 二重母音の後半(ə, または ae ao ei ou の e o i u)
  short?: boolean;      // ブレーヴ付きの短い二重母音(ĭə ŭə ĕə ŏə)。long と排他
}
interface Syllable {
  onset: Consonant[];   // 1〜3。最後の1つが主子音、それ以前は母音なし(小書きカナ)。語頭母音は "ʔ" を明示
  nucleus: Nucleus;
  coda?: Coda;
}
type Word = Syllable[];
type Utterance = Word[];   // Phrase.syllables はこれ。外側の次元 = 半角スペース区切りの語
```

- **IPA 記法(M1)**: 語内の音節境界は `.`、語境界は半角スペース。`ʔɑː.kun` のように **1語 = 1トークン**にそろえる(現行の `ʔɑː kun` は語が2つ扱いになる)。
- **正規化(M3)**: 入力は内部で NFD に分解して解析する(ĭ = i + U+0306)。保存・出力は NFC。NFKC/NFKD は禁止。
- **強勢**: 各語の最終音節に固定。データには持たない。
- **逆変換**: `Syllable → IPA` は保証する。`カナ → IPA` は保証しない(§2.5)。

### 2.2 パイプライン

```
IPA文字列 --parse--> Utterance --render(full)--> カナ詳細 --derive--> カナライト
                        └── validate (音節構造の妥当性)
```

| モジュール | 責務 | 主な失敗の扱い |
|---|---|---|
| `parseIpa(str)` | 正規化 → 語・音節・子音・母音に分解 | 未知記号は `ParseError`(位置つき)。黙って落とさない |
| `renderFull(utt)` | §4 の対応表と並び順で詳細表記を生成 | 表にない組み合わせは `RenderError` |
| `deriveLite(full)` | 詳細から機械的にライトを導出(別辞書なし) | 置換は §2.3 の6パターンのみ |
| `toIpa(utt)` | 往復テスト用 | — |
| `graphemes(str)` | `Intl.Segmenter` があれば使い、なければ簡易実装 | Chrome 74 系は `Segmenter` なし(検証で確認) |

- 並び順: **子音+母音のカナ → `◌̯`/`゚` → 子音修飾(ʰ ˡ ʳ) → 母音修飾(ᵋ ᵓ ᵅ ᵊ ᶤ) → ー → 二重母音後半(+その母音修飾) → 末子音**。
  「二重母音後半とその修飾文字」を1単位とする(M5 の指摘への対応)。
- CLI: `khmer-kana render "ʔɑː.kun"`、`khmer-kana check phrases.yaml`(ビルドで使用)。

### 2.3 ライト表記の規則(H2・H3)

**変更(v0.2 → v0.3 案)**

1. 削除対象は `ʰ ˡ ʳ ᵋ ᵓ ᵅ ᵊ ᶤ` の **8文字**。**`◌̯` は残す。**
   理由: `◌̯` は「母音を足さない」という表記の中心的な約束で、これを消すと `cʰkae → チカエ` になり、
   日本語話者が `チ` に母音を付けて読む。Android の欠字問題はフォント同梱で解決済みなので、消す理由がなくなった。
2. 置換は従来どおり 6 パターンのみ(`カ゚キ゚ク゚ケ゚コ゚ → ガギグゲゴ`、`ン゚ → ン`)。半濁点の一律削除は禁止。
3. 「読み方の土台は変わらない」の文言を修正し、**ライトで失われる区別**を次の5つと明記する:
   有気/無気、r/l、母音の音色(ɨ ə ɛ ɔ ɑ)、語末 n/ŋ、**語頭 ŋ → ガ(音価が変わる)**。

**H3 の扱い**

- `ɗaə → ダア`: 実音 [daə] は二拍に近いので許容。
- `tɨw`: 従来は詳細 `トゥᶤゥ`、ライト `トゥゥ` で、`ゥᶤ` が読みにくかった。
  **特例として `tɨ` は詳細 `トᶤ`・ライト `トゥ`**(ライトを `ト` にすると `to` と同じになるため)。
  修飾文字を外すだけでは導出できない唯一の例外。`tɨw` のライトは `トゥゥ` のままで、`トゥー` と読まれうる**既知の弱点**。ネイティブ確認後に見直す。

### 2.4 テスト計画(H7)

Phase 0 の完了条件を「**約130件のゴールデンテスト・属性テスト・異常系テストが全て通る(詳細は [khmer-kana-spec.md](khmer-kana-spec.md) §9)**」に変更する。

| 区分 | 内容 | 件数の目安 |
|---|---|---|
| 頭子音 | 対応表の全行(25子音 × 代表段) | 25 |
| 母音・二重母音 | 単母音10 × 長短、二重母音全種、短い二重母音 | 25 |
| 子音連続 | 2連続(k t p s m l c)、3連続(str- skr-) | 10 |
| 末子音 | 全種 + 語末 r(書かない)+ c/ɲ(イ寄り) | 13 |
| 変換例 | 設計書の変換例 全件(ありがとう…はい)+ 例文「要りません」 | 16 |
| **コードポイント列** | 上記すべてで詳細/ライトの列を固定 | (併用) |
| 属性 | `parse(toIpa(x)) = x`、`deriveLite` は詳細に対して冪等、NFC 不変、NFKC を通すと失敗すること | — |
| 異常系 | 未知記号、`b/ɓ` の揺れ、ブレーヴの NFC/NFD、語頭の `ʔ` 省略 | 10 |

### 2.5 記号の「1記号1意味」原則(M4)

現状は次の例外がある。原則を「**音節構造を正とし、カナ→IPA の逆変換は保証しない**」に弱めて明記する。

- `゚`: ŋ の印(`カ゚`)と、半濁点(`ㇷ゚` の p)の2役。
- 小書き `ィ`: 二重母音後半・語末 j・語末 c/ɲ の「イ寄り」。
- 衝突する組み合わせ(`ʔi`/`ji`、`ɲi`/`ni`)は同じカナになる。未決事項に残す。

## 3. フォントと配信(検証結果の反映)

```css
/* 表記(カナ+修飾文字)に使うスタック。Kana C が先頭で、結合記号を含む基底と小書き文字を1フォントで持つ */
@font-face { font-family: "Kana C"; src: url(kana-c.woff2) format("woff2"); unicode-range: U+30C1, U+032F, U+309A, U+30AB, U+30AD, U+30AF, U+30B1, U+30B3, U+30F3, U+31F0-31FF; }
.kana { font-family: "Kana C", "Noto Sans JP", "Noto Sans", sans-serif; }
```

- `kana-c.woff2`(約5KB)は Noto Sans JP(400)と U+032F(Noto Sans フル版)から作る。文字列はチ+U+032F のまま、合字(GSUB `liga`)で**小さいチ**のグリフに置き換える。
  アイヌ語小書き `ㇰ〜ㇿ`(U+31F0-31FF)は Noto の字形を 0.8 倍に描き直し、`ㇷ゚` は小さい `ㇷ` の上に `゚` を載せた1グリフにする。
  `カキクケコン`+`゚` は形を変えずに同梱する(Android は基底と結合記号を1フォントで持たないと欠字にするため。Noto の合成グリフの ccmp ルールを引き継ぎ、合成グリフのない `ン゚` は専用グリフを作る)。
  生成は `tools/glyph-check/scripts/build-kana-font.py`(サイズは `SMALL_SCALE` `CHI_SCALE`)で再現できる。両フォントとも OFL。ライセンス表記を同梱する。
- **`◌̯` を付ける基底が増えたら、その文字もこのフォントに追加する**。現行設計で `◌̯` が付くのは c(チ)のみ。
- Noto Sans / Noto Sans JP は fontsource のサブセットを使う。修飾文字は Noto Sans に含まれ、iOS と Android で幅が一致した(同梱の利点)。
- クメール文字の表示は「参考表示」なので `Noto Sans Khmer` を別要素に適用し、カナのスタックには混ぜない(M7)。
- **オフライン**: Service Worker のプリキャッシュに、使う文字のフォント分割ファイルと `kana-c.woff2` を含める。
  Noto Sans JP は分割数が多いので、フレーズで使う文字を含むファイルだけを列挙するビルド手順にする。
- **リリース前ゲート**: glyph-check と同じ検証ページを CI で回し、スクリーンショットを目視する(自動判定は補助)。
  実機(iPhone 1台、Android 2台以上、メーカー違い)での目視を1回行う。

## 4. データモデル(H5・H6)

### 4.1 入力 `phrases.yaml`

```yaml
- id: yes
  scene: thanks-sorry
  ja: はい
  usage: 丁寧な返事。話者の性別で語が変わる
  register: polite              # polite | casual
  variants:                     # 話者(自分)の性別で変わる場合。1種類なら speaker: any の1件
    - { speaker: male,   khmer: បាទ, ipa: "ɓaːt", audio: yes-m.m4a }
    - { speaker: female, khmer: ចាស, ipa: "caːh", audio: yes-f.m4a }
  words:                        # 単語タップ用。IPA も必須(M2)
    - { khmer: បាទ, ipa: "ɓaːt", ja: はい(男性) }
  review: { ipa: false, audio: false, usage: false }
  audioSource: native           # native | tts
```

- **穴埋め**: `slots` を追加。`ipa` / `khmer` に `{name}` のようなプレースホルダーを書き、候補は最大3つ。

  ```yaml
  slots:
    - id: name
      candidates:                # 最大3件
        - { ja: トモヤ, khmer: ..., ipa: "...", audio: ... }
  ```
- **呼びかけ**: 「自分の性別」ではなく「相手の性別・年齢」で変わるため、`addressee: { gender: male|female|any, age: older|younger|any }` を持つ。
  1つの呼称 = 1フレーズ(カード)とし、`ja` に「年上の男性への呼びかけ」のように相手を書く。
- **くだけた形**: `variants[].register: casual` で持ち、カードの補足欄にだけ表示する(SRS の対象にはしない)。

### 4.2 生成物 `phrases.json` と進捗

```ts
interface Phrase {
  id: string; scene: string; ja: string; usage: string;
  variants: Variant[];                 // 表示するのは設定の性別に合う1件(なければ any)+ 補足として他方
  slots?: Slot[]; addressee?: Addressee;
  words: { khmer: string; ipa: string; ja: string }[];
  review: { ipa: boolean; audio: boolean; usage: boolean };
  audioSource: "native" | "tts";
}
interface Variant {
  speaker: "any" | "male" | "female"; register: "polite" | "casual";
  khmer: string; ipa: string;
  syllables: Utterance;                // §2.1
  kanaFull: string; kanaLite: string;  // 生成物。手で編集しない
  audio: string;
}
interface Scene { id: string; title: string; order: number; phraseIds: string[] }

// 端末側(IndexedDB)。SRS は phrase.id 単位。性別を変えても引き継ぐ
interface PhraseProgress { phraseId: string; card: FsrsCard; lastRating?: 1|2|3|4; introducedAt?: string; schema: 1 }
interface Settings {
  notation: "lite" | "full"; speakerGender: "male" | "female" | "unset";   // unset = 両方を並べて表示
  playbackRate: 1 | 0.75; newPerDay: number;                                // 3〜10、既定 6
  tripDate?: string;                                                        // 任意(§5.3)
  schema: 1;
}
```

- **カード数**: 性別ペアも 1 フレーズ = 1 カードで数える。
- **性別を変更**: 進捗はそのまま。次の表示から `variants` の主表示が入れ替わるだけ。
- **IndexedDB**: `schema` を持たせ、変更時は移行関数を書く。フレーズ id を変えたときは孤児の進捗を起動時に掃除する。
- **書き出し・読み込み**: JSON。`schema` と `phrases` のバージョンを含める。

### 4.3 レビュー状態とビルドプロファイル(H6)

| プロファイル | 含めるフレーズ | 音声 | 用途 |
|---|---|---|---|
| `prod` | `review` の3項目がすべて true | `native` のみ | 公開 |
| `preview` | すべて | `tts` も可。カードに「未確認」バッジ | 開発・自己学習の先行利用 |

- `prod` で 1 シーンの公開フレーズが 4 件未満なら、そのシーンは非公開にし、ビルドが警告する。
- 聞き取りクイズの選択肢は、同じシーンから優先し、足りなければ他シーンから補う。全体で 4 件未満ならクイズを無効化する。
- クメール語の TTS は入手性・ライセンス・オフライン同梱の可否を未調査(リスク)。`preview` 専用で、最悪なくても進められる。
- 収録話者の方言は **中部平野方言(プノンペン式でない)** を要件とする(M6)。

## 5. 学習設計

### 5.1 コンテンツと7日計画(H4)

| シーン | 数 | 追加 |
|---|---|---|
| 挨拶 | 8 | — |
| お礼・お詫び・返事 | 8 | — |
| 呼びかけ | 6 | — |
| 自己紹介 | 6 | — |
| ひとこと表現 | **12** | 現行10 + 2 |
| **合計** | **40** | |

- 既定の新規上限 **6/日**。導入順はシーン順で、7日目までに 40 件が導入される(6×6 + 4)。
- **「一巡」の定義** = 全フレーズが一度は導入された状態。習得(安定した想起)は別で、SRS が担う。
- 1日目からの目安: 1日目 挨拶6 / 2日目 挨拶2+返事4 / 3日目 返事4+呼びかけ2 / 4日目 呼びかけ4+自己紹介2 / 5日目 自己紹介4+ひとこと2 / 6日目 ひとこと6 / 7日目 ひとこと4+復習中心。

### 5.2 セッション(約10分)

```
1. 復習(期限が来たカード。上限 20 枚)
2. 新規(min(newPerDay, 未導入数))
   - 音声を2回 → カナ → 意味 → シャドーイング(録音・聞き比べ)
3. 聞き取りクイズ(新規分)
4. 評価から次回日を更新(ts-fsrs)
```

- **評価の入力**: 4段階(もう一度/難しい/言えた/簡単)。「言えた」「簡単」を押す前に、お手本の再生を必須にする。
- **FSRS 設定**: `request_retention: 0.9`、`maximum_interval: 14`(1〜2週間の学習期間に合わせる)、学習ステップは短期(同日再出題)を有効にする。
- **中断**: 1問ごとに保存。再開時は保存した「今日のキュー」から続きを出す。
- **表記の段階的移行**: 既定はライト。詳細表記への切替は、①設定で手動、②提案表示(習得済みが 10 件を超えたとき、1回だけ)。
  シーン詳細も設定の表記レベルに従わせる(M8)。詳細表記の色分け対象は **記号10種すべて**(`◌̯` `゚` を含む)。

### 5.3 旅行日の設定(任意・後回し可)

`tripDate` を設定すると、未導入数と残り日数から新規上限を自動提案する(出発の3日前に導入完了が目標)。MVP では手動設定のみでもよい。

## 6. 画面・状態(要点)

- ルーティング: `/`(ホーム)、`/scene/:id`、`/card/:phraseId`、`/practice`、`/travel`、`/settings`。
- 旅行中モード: 大きな文字、音声を相手に聞かせる再生、オフライン。**クメール文字を大きく出すかは未決事項**(§8)。
- **ストレージの永続化**: 起動時に `navigator.storage.persist()` を要求する。iOS Safari はホーム画面に追加していないと、
  7日間操作がないとストレージが消える場合があるため、①ホーム画面に追加する案内、②週1回の JSON 書き出しリマインドを入れる(M9)。
- 録音は保存も送信もしない(現行方針)。権限拒否時は「聞き比べ」を飛ばして自己評価に進めるようにする。
