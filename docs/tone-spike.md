# 声調フォント スパイク設計書 (v0.1)

`docs/tone-notation.md` の案b(声調を**音節全体**の真上に、CSS も ruby も使わず**フォントだけ**で出す)が、実機相当の環境で成立するかを確かめる使い捨ての試作。
成果物は「動くか/動かないか」と、その根拠になるスクリーンショット。製品コードには入れない。

## 1. 検証したいこと

| # | 仮説 | 駄目だった場合 |
|---|---|---|
| H1 | 声調文字の並び(˨˩ など)を GSUB で1つの折れ線グリフに置換できる | 声調文字を1個ずつ描く方式に後退 |
| H2 | 音節の先頭に置いた区切り文字を目印に、文脈つきの規則で声調グリフを音節全幅の中央へ動かせる | §2 の 2 案のうち、動いた方を採る。両方駄目なら案aに後退 |
| H3 | 区切り文字に使える文字がある(iOS Safari、Android Chrome で GSUB/GPOS の文脈に効き、余計な表示も出ない) | 別の文字を試す。私用領域(PUA)は最後の手 |
| H4 | 連続する複数音節で、声調グリフの位置調整が次の音節に漏れない(ペンが元に戻る) | 位置調整を GSUB 側に寄せる |
| H5 | 区切り文字が無い、またはフォントが効かない場合の見え方が許容できる | フォールバックの方針を決め直す |

## 2. 方式

### 2.1 音節の構造と幅クラス

音節は「区切り文字 B + グリフ列 + 声調文字」。グリフ列は次の2クラスだけを許す(スパイクの制約)。

| クラス | 中身 | 送り幅 |
|---|---|---|
| F(全角) | カタカナ、小書きカナ、長音 `ー`(U+30A1–30FA、U+30FC、U+31F0–31FF) | 1000 |
| S(上付き) | ʰ ʱ ʲ ʷ ⁿ ˣ ˠ ʶ ˀ ˤ ʳ ˡ ᵓ ᵊ ᵋ ᵅ ᶤ(既存の上付き文字) | **480 に統一**(既存は文字ごとに約 300〜500。幅クラスを1つにするため、スパイクでは中央寄せで統一) |

- 音節の全幅は `W = 1000·nF + 480·nS`。スパイクの範囲は `1 ≤ nF ≤ 5`、`0 ≤ nS ≤ 4`、グリフ数は 9 以内。
- 半濁点 U+309A、`ㇷ゚` と ħ の合字、U+0323 はスパイクの対象外(F/S に入らない)。

### 2.2 声調グリフ

- 声調文字 ˥˦˧˨˩ を1〜3個並べた列は、GSUB(`liga`)で折れ線グリフ 155 個(1個5 + 2個25 + 3個125)に置換する。1個のものは cmap のグリフをそのまま使う。
- 輪郭は現行と同じ座標(x = -800…-200、送り幅 0)。ペンが音節の右端にあるとき、末尾の1000幅の上に乗る。
- 音節全体の中央へ動かす量は `dx = -(W - 1000) / 2`。

### 2.3 位置合わせの2案(両方作って比べる)

音節の先頭は区切り文字 B で分かる。B から声調までの間は F/S の並びなので、並びをそのまま列挙する連鎖規則で W を決められる。
規則は「B + F/S の並び + 声調グリフ」の形に限る(F で始まり上の制約を満たす並びだけを自動生成、250 本)。

- **GPOS 案**: 声調グリフに単一位置調整(`dx`)を与える。グリフ数は増えない。
- **GSUB 案**: 声調グリフを、`dx` 分ずらした輪郭の別グリフ(`c_<形>_w<W>`)に置換する。グリフ数は約 4000 に増えるが、位置調整を持たない描画系でも動く見込み。

iOS の CoreText が GPOS の文脈規則をどこまで実行するかが不明なので、両方を作って画面で確かめる。フォントは別名(`Tone Spike GPOS` / `Tone Spike GSUB`)。

### 2.4 幅ヒント方式(ローカル試験で追加)

ローカルの Chrome で試した結果、区切り文字方式(§2.3)は、音節に Latin 文字の上付き文字(ʰ ᵊ など)が入ると効かなかった。
ブラウザはスクリプト(文字体系)が変わる所でシェイピングの単位(run)を分けるので、カナ(Katakana)と ʰ(Latin)の間で規則の文脈が切れる。
小書きカナだけの音節(`カㇰ`)と、Common 扱いの `ˀ`(U+02C0)を含む音節は、区切り文字方式でも効いた。

そこで、幅をデータ側に持たせる**ヒント方式**を足す。声調文字の直前に、不可視の Common 文字を次の個数だけ並べる。

| 並べる文字 | 個数 | 意味 |
|---|---|---|
| U+2062 INVISIBLE TIMES | nF − 1 | 全角カナが2個目以降にいくつあるか |
| U+2063 INVISIBLE SEPARATOR | nS | 上付き文字の数 |

例: `キァᵊ` の声調 ˥˩ → `キァᵊ` + U+2062 ×1 + U+2063 ×1 + `˥˩`(F 2、S 1)。
ヒントは声調と隣り合うので、必ず同じ run に入る。規則は `(a, b)` の 24 通りで、区切り文字も走査も要らない。
数える側(データ生成)に必要なのは「カナが何個、上付き文字が何個」だけで、フォントの送り幅は知らなくてよい。
規則は「長いヒントを先」に並べる(`HB HB` は `HA HB HB` の末尾にも一致するため)。

### 2.5 区切り文字(H3)

3種類を並べる。どれも同じグリフ B(送り幅 0、輪郭なし)に割り当てる。

| 記号 | コードポイント | 性質 |
|---|---|---|
| WJ | U+2060 WORD JOINER | 既定で無視される文字。前後で折り返さない |
| ZWSP | U+200B ZERO WIDTH SPACE | 既定で無視される文字。折り返し可 |
| PUA | U+E000 | 私用領域。フォントが無ければ豆腐が出る |

既定で無視される文字は、HarfBuzz では最後まで無視されず文脈照合に使えるはずだが、CoreText で同じかどうかは試すまで分からない。

## 4. 試験表

画面は5種類(`?view=`): `hint`(ヒント方式)、`wj` `zwsp` `pua`(区切り文字方式)、`plain`(システムフォントの素の表示、区切り・ヒントなしの GPOS/GSUB フォント)。
各画面は GPOS 案と GSUB 案の2列。

| 例 | 構造 | 狙い |
|---|---|---|
| `カ˨˩` | F | 基準。動かさない場合と一致するか |
| `カʰ˦˥` | F S | 上付き文字つき |
| `カㇰ˧˥˧` | F F | 3点の山型、小書き末子音 |
| `キァᵊ˥˩` | F F S | 二重母音 |
| `コʰᵅーン˨˦˩` | F S S F F | 長い音節、3点 |
| `ㇲㇳラʳᵊィ˨˩` | F F F S S F | 3子音連続(6グリフ) |
| 複数音節 `カ˨˩ キァᵊ˥˩ ㇲㇳラʳᵊィ˦˥` | — | 位置調整が次の音節へ漏れない(H4) |
| 平ら `カ˧`、高さ違い `カ˥` `カ˩` | F | 高さの目視 |

## 5. 完了条件

- **ローカル**: `verify-tone-spike.py` が両モードで全例を通る(uharfbuzz)。Chrome(ヘッドレス)の画面でも目視で確認する。
- **CI**: iOS、Android API 29 と 34 の各スクリーンショットが取れ、画像ギャラリー(artifact)にまとめる。
- **判定は目視**(CLAUDE.md の方針)。自動判定は補助。§1 の H1〜H5 を、各環境で「OK / NG / 不明」に整理する。

## 6. 範囲外

- 半濁点・ㇷ゚・ħ の合字・U+0323 との併用、`tone-notation.md` の他の未決事項(矢じり、基準線、タイ語の声調値)。
- `khmer-kana` への `tone` フィールドの追加、アプリへの組み込み。
- 上付き文字の幅の統一(480)を本番に採るかどうか。スパイクの都合であり、字形への影響は結果を見て判断する。

## 7. 結果の使い方

- GPOS 案と GSUB 案のどちらが全環境で動くか、区切り文字はどれが使えるかを `tone-notation.md` の §3.1.1 と §8 に反映する。
- 全環境で駄目なら、案a(声調を核の直後に置く)を本命に戻す。
