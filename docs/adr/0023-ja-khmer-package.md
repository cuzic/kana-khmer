# ADR-0023: ja-khmer の変換は packages/ja-khmer に新設し、khmer-kana・ja-hangul との共通基盤は当面切り出さない

## コンテキスト
ja-khmer(日本語の発音のカタカナ → クメール文字。ADR-0010・ADR-0017)は、`tools/ja-khmer-spike` の使い捨てスクリプト
(`spec-table.mjs`・`convert-spec.mjs`。設計書 v0.7 の表を読む)で試作してきた。設計書 [docs/ja-khmer-spec.md](../ja-khmer-spec.md)(v0.12)で
対応表・長音・促音・撥音・あい=ៃ の規則が固まり、ADR-0021 のアクセント線が「拍に対応する可視スロット(基底の書記音節・末子音・長音マーカー)」を
入力に使うことになった。アプリ(`apps/web`、ADR-0020 のコース)から呼べる、テスト付きのパッケージが要る。

既存の兄弟パッケージは、`khmer-kana`(IPA → 音節構造 → カナ。ADR-0001・ADR-0012)と `ja-hangul`(かな → ハングル。ADR-0018・ADR-0019)。
どれも「発音の列を、表と少数の規則で別の文字体系に写す」点は似ているが、入力(IPA か、かな か)・表の出所・出力の構造が違う。

## 決定
1. **`packages/ja-khmer` を新設する**。流儀は `ja-hangul` に合わせる(TypeScript、`main: src/index.ts`、vitest、`tsc -p` の typecheck、
   実行時依存なし、`?.` `??` を src で使わない)。API は `renderKhmer(pron, { longStyle })` で、クメール文字の文字列に加えて
   **句 → 書記音節 → スロット(base / coda / shoulder / long)→ 拍** の対応を返す(ADR-0021 が拍単位のスロットを使うため)。
   あい=ៃ のように1つのスロットに2拍が入る場合は、スロットが拍の添字を複数持つ。
2. **対応表は設計書 §5 から機械的に作る**(表を二重に持たない)。`scripts/gen-table.ts`(`pnpm gen`)が設計書の表を
   `src/spec-table.generated.ts` に書き出し、テストが生成物と設計書の一致を検査する(設計書を変えて `pnpm gen` を忘れるとテストが落ちる)。
   実行時に設計書を読まない(ブラウザで動かすため)。
3. **共通基盤の切り出しは当面しない**。`khmer-kana`・`ja-hangul` と重なる部分(拍/音節の列、スロットの構造、エラー型、長音マーカーの上付き文字表)は
   パッケージごとに持つ。共通化が要る具体的な場面(例: 設計書 §3.2 が言及する `kana-core` での span 種別 `long` の共有)が出たら、**別の ADR** で起こす。
4. **`tools/ja-khmer-spike` は使い捨てのまま残す**。読み戻し検証(ADR-0010 決定7(a))は `packages/ja-khmer/scripts/verify-readback.ts` に移植したが、
   `Module:km-pron`(CC BY-SA)の Lua はリポジトリに入れず、任意実行にする(`KM_PRON_LUA` で指定するか `--fetch` で取得。取れなければスキップ)。
   テストは自己完結にする。衝突率の測定(`collision.mjs`)・アクセントの単位の測定(`accent-cluster.mjs`)・kuromoji を使う `run.mjs` は、
   JMdict などの外部データが要るためスパイク側に残す。
5. **入力の扱い(設計書で要決定の点を、実装上は次のとおりにした)**: 入力はカタカナのみ(ヲ・ヂ・ヅ は表にあるので可、ァィゥェォ・ヴ は範囲外でエラー)。
   句末の `ッ` は次の子音が分からないので t 系の `ត`(スパイクと同じ。§6.2)。語頭の `ッ`・`ー`、`ー` の重複、`ン` の後の `ー` はエラー
   (スパイクは黙って捨てていた。設計書が規則を持たないため、暗黙に落とさない)。語頭・連続する `ン` は単独の `ន` の音節(スパイクと同じ)。
   これらは設計書 §6 の「要決定」が決まったら見直す。

## 検討した代替案
- **`tools/ja-khmer-spike` を育ててパッケージにする**: スパイクは JMdict・kuromoji などの外部データと使い捨てのスクリプトが混在し、
  アプリから依存するものではない。仮表(v0)の `table.mjs`・`convert.mjs` も検証に使われている。分けるほうが、使い捨ての範囲が明確。
- **`khmer-kana` に同居させる**: 向きが逆(クメール語 → カナ と、日本語 → クメール文字)で、表の出所も入力も違う。
  ADR-0010 は逆方向表記を別ディレクトリで設計するとしていた。ADR-0001 のパッケージ分割にも反する。
- **最初から共通基盤(`kana-core` 等)を切り出す**: 3パッケージの重なりは小さく、今切ると抽象が実例なしに固まる。
  ja-hangul はまだ表と規則が動いており、共通の形を決めるには早い。必要になった時点で、実際に重なる部分を根拠に別 ADR で決める。
- **実行時に設計書(Markdown)を読む**: ブラウザで動かせず、Markdown の書式変更で壊れる。ビルド時の生成物 + 一致テストにした。
- **生成物を持たず、`pnpm build` の前段で毎回生成する**: 生成物をコミットしないと、テスト・型検査の前に生成が要る。
  設計書との一致テストで足りるので、生成物はコミットする(`courses/` の生成物とは違い、設計書が更新されたときだけ変わる)。

## 結果(影響)
- アプリとアクセント線の実装が、スロットと拍の対応を直接使える。表は設計書の1か所にだけある。
- 設計書の §5 の表の書式(行が `| かな | 詳細 | …` の Markdown 表、右肩・長音の文字範囲)に生成器が依存する。書式を変えるときは `spec-parse.ts` も直す。
- 詳細とライトは現時点で全行同じ文字列(設計書 §3.4)なので、API にレベルの引数を持たない。ライトで落とす記号が出たら追加する。
- 対応表はクメール語話者の確認前(設計書 §5.1 の状態欄が正)。パッケージが存在することは表記の妥当性を保証しない。
- 読み戻し検証は、生成側と独立な実装だが回帰テストであり、音の妥当性の独立した検査ではない(設計書 §9.1)。
- 長音マーカーの字形(結合マクロン)の実機描画は未確認のままで、フォント(ADR-0003・ADR-0014)側の作業に残る。
