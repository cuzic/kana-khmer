# ADR-0021: ja-khmer の日本語ピッチアクセントは、拍単位の上線(H のみ)を DOM/CSS で描く

## コンテキスト
ADR-0010 決定6 は、日本語のピッチアクセントを文字の上の線で表す方針を置き、線を載せる対象(クメール文字の行、かなの行、下がり目記号 ꜜ)の
決着を `glyph-check` と作業量に委ねていた(未決)。声調の既存実装(ADR-0007 Chao 声調バー、ADR-0008 GSUB による音節幅への伸縮と
iOS/Android の二重符号化)を流用する案も残っていた。設計提案
[docs/research/2026-09-29-ja-accent-line-design.md](../research/2026-09-29-ja-accent-line-design.md) の調査結果は次のとおり。

- **書記音節は拍と一対一でない**。長音は右肩のマーカー、撥音・促音は末子音、あい は ៃ になる。目に見えるスロット(基底の書記音節・末子音・長音マーカー)に分ければ、
  あい=ៃ を除いてほぼ拍と対応する。書記音節単位の線が表せないものを、実測(`tools/ja-khmer-spike/src/accent-cluster.mjs`。JMdict 共通語 21,694 形)で確認した。
  - **下がり目(核)が書記音節の内側に落ちる**: 核は特殊拍(ー・ン・ッ・あい の い)に来にくいので、核の候補を「特殊拍でない拍 n の後」に限ると、
    n と n+1 が同じ書記音節に入る候補が **39.2%**(20,604 / 52,499)。書記音節の内側に落ちる候補を持つ語は、候補を持つ語の 65.4%(14,151 / 21,630)。Wiktionary の実データ(旅行フレーズの 23 語)では、語内に下がり目がある
    17 語のうち **8 語**が内側に落ちる(ニホンジン 4、スミマセン 4、ゲンキ 1、ダイジョーブ 3 など)。この下がり目は弁別的で、はっきり発音される(一般知識、文献未照合)。
    書記音節単位の線ではこれが表せず、拍単位のスロットを正当化するのはこの数である。
  - **語頭が重い音節**(2拍目が特殊拍で、1拍目と同じ書記音節に入る語)は 41.8%(9,050 / 21,633)。ただしこの割合は「語頭の上昇が書記音節の内側に落ちる語」ではない。
    東京式で1拍目と2拍目の高さは原則として違うが、**2拍目が特殊拍のときは、語頭の上昇が弱いか無い**ことが多い(辞書の型は LHHH でも実際は語頭がほぼ平らな語がある。
    一般知識で、NHK 等の原文とは未照合)。したがって根拠には使わず、語頭の簡略化(決定2の注)の適用範囲を示す数として使う。
- **クメール文字の送り幅は可変**(Noto Sans Khmer で ក 636、ហ 928、ក្រៅ 1499 など。実測)。ADR-0008 の幅ヒント(全角カナの数+上付き幅クラス)が使えない。
  生成器の出力は閉じた集合なので列挙は原理的に可能だが、規模は未測定で、Khmer シェイパでの動作も未確認。
- **DOM/CSS で描ける**。Wiktionary の Module:ja-pron 自身が `border-top`(高い拍)と `border-right`(下がり目)で描いている。
  デスクトップ Chrome で、Noto Sans Khmer+ja-khmer 用フォントの出力を書記音節・末子音・長音マーカーごとの inline-block に分け、
  `border-top` で連続した一定の高さの線になり、母音記号・◌៉◌៊・右肩記号と重ならないことを目視した。iOS・Android は未確認。
- ユーザーが方針を答えた(2026-09-29): 線の目的は自然な抑揚を真似させること(語の型番号は見せない)。L の線は引かず H だけ上線で示す(OJAD 式)。
  かなの行にも出す。活用形を含むフレーズは当面線を出さない。

## 決定
1. **線の単位は拍**とする。クメール文字の行では、生成器が拍に対応する可視スロット(基底の書記音節、末子音、長音マーカー)ごとに DOM の span を出す。
   あい=ៃ のように1つの字に2拍が入り分割できない場合は、字の半幅ずつに線を引く(未試作)。
2. **表現は上線方式(H のみ)**: H の拍の上に線を引き、L の拍には引かない。下がり目は線の右端の縦の段(`border-right`)で示す。
   頭高・中高・尾高は下がり目の段で、平板は段が無いことで区別でき、助詞が無い句でも区別が付く(助詞がある句では、尾高は助詞が L になり、平板は助詞まで線が続く)。
   語の型番号は見せない。
   **語頭の簡略化(ユーザー判断、2026-09-29)**: 辞書の型どおりなら、平板・中高の句は1拍目が L、2拍目から H である。**句頭の1拍目と2拍目が同じ書記音節に入り、かつ核が1拍目でない
   (n≠1)ときは、1拍目も H とし、線をその書記音節の頭から引く**(規則は1つ。「同じ書記音節」は生成器の畳み込み(`convert-spec.mjs`)で決まる: 2拍目が長音・撥音・促音・あい の い のとき。
   該当は語頭が重い音節の語で、JMdict 共通語の 41.8%)。頭高(n=1)は辞書どおり(1拍目 H、2拍目 L。ラーメン なら ラー が基底と長音マーカーの別スロットなので、基底のスロットにだけ線を引き、字を割る必要は無い)。
   n=2 で2拍目が句頭の書記音節に入るまれな場合は、その書記音節全体が H で、下がり目の段はその書記音節の右端に置く。
   句頭以外(句の途中の拍)には適用しない。これは**学習者向けの簡略化で、辞書の型とは少しずれる**: 2拍目が特殊拍のとき語頭の上昇は弱いか無いことが多い(一般知識、文献未照合)ため、
   辞書どおりに1拍目を下げて描くと、学習者が語頭を不自然に下げて発音しかねない(目的は自然な抑揚。Q1)。代償は、辞書・OJAD・Wiktionary と見た目が変わること。
   副次効果として、字を割る半幅の線が要るのは、1字に2拍が入る あい=ៃ の内側で高さが変わるとき(ゴメンナサ\イ・クダサ\イ のように下がり目が ៃ の内側に来る場合、句頭の ៃ に頭高が来る場合)だけになる。
   この規則は H/L 列を作る生成器で持ち、クメール文字の行とかなの行に同じ H/L 列を渡す(両行で見た目が食い違わないようにする)。
3. **実装は DOM/CSS**(生成器が span を出し、`border-top` 等で描く)。フォントは使わない。ADR-0003 の制約(結合文字は基底と同じ span)を守り、
   span の分割は書記音節・末子音・長音マーカーの境目だけとし、前置母音と子音の間では切らない。句は `white-space:nowrap`。
   ADR-0016 に従い `?.` `??` を使わない。
4. **ADR-0007(Chao 声調バーの符号化)と ADR-0008(GSUB 伸縮・二重符号化)は ja-khmer には使わない**。理由は上記コンテキストの
   核が書記音節の内側に落ちる位置(39.2%)と幅の可変性。両 ADR は声調言語(kana-multi)のためのものとして有効なまま。
5. **表示行はクメール文字の行とかなの行の両方**(ユーザー判断 Q3)。かなの行は拍が1文字なので、同じ CSS の規則で出す。ただし実装は
   クメール文字の行と別に整理する: かなの行は文字と拍が対応する(ャュョ は直前と合わせて1拍)ので span の分割規則が簡単で、
   クメール文字の行のスロット分割規則(決定1)を共有しない。両行は同じ拍ごとの H/L 列(生成器が持つ)を入力にする。
6. **データ**: アクセント句(設計書 §2 の空白区切り)ごとに核の位置 n(0=平板)を持つ。Wiktionary の `{{ja-pron|acc=N}}`(東京式)を候補の種にし、
   エージェントが取り込んで作り、後で人が確認する(ユーザー判断 Q4)。各データに確認状態(未確認/確認済み)を持たせ、**確認者は未定のため当面すべて未確認**とする(確認済みと書かない)。型が取れない句は線なし。句への合成は最小規則から: 名詞・代名詞・副詞(型 n)+**無核の1拍の助詞**(が・を・に・は・で・と・も など。多くは無核。一般知識、文献未照合)・だ は、句の型を n とする。
   **です は無アクセントではない**: です は デ\ス(で に核)を持ち、前の語に核があれば消え(雨です=ア\メデス)、平板の語の後で現れる(飴です=アメデ\ス)。
   したがって 語+です は、n>0 なら n、n=0 なら です の で(語の拍数+1 拍目)を核とする。まで・より・だけ・しか・ぐらい などの2拍以上の助詞も核を持つものがあり、人が与える
   (平板の語+まで で マ に核が来る例。一般知識、文献未照合)。旅行フレーズ 40 件のうち です を含むものが 9 件(courses/ja-km/phrases.yaml の gloss)ある。
   規則の根拠は文献照合が済んでいない。
   複合語・感動詞・慣用句の句分けは人が与える。設計書 §2・§3.3 と `packages/content` の形式は本 ADR に合わせて別途改める。
7. **ライト**では暫定で線を残す。アクセント衝突率(同じかな読みで型だけが違う語の割合。D5 と同じ測り方)を測れるまで、詳細・ライトとも同じとする。
8. **ライセンス(ユーザー判断 Q4)**: Wiktionary(CC BY-SA 4.0)由来のアクセントのデータは、**そのファイルだけを CC BY-SA として分離**し、帰属表示(各語の出典 URL と取得日、`acc_ref`)を付け、
   継承の範囲をそのファイルに限る。リポジトリ全体の LICENSE 方針(現状ルートに LICENSE 無し)は別途決める。CC BY-SA の継承が実際にどこまで及ぶかの**法的判断は未確認**。
9. **長音マーカーの位置(ユーザー判断 Q6)**: 長音マーカーは末子音の後ろ(書記音節の末尾)に置く(設計書 §3.2・§6.3・§8 #8 で決定済み)。長音+撥音・促音(カーン)の書記音節は、
   可視スロットが 基底 → 末子音 → 長音マーカー の順に並ぶ。拍の時間順は 基底 → ー → ン なので、**マーカーのスロットは ー の拍、末子音のスロットは ン・ッ の拍**に対応させ、
   スロットの並びと拍の順は逆になる。ー と ン・ッ は特殊拍で、通常は直前の拍と同じ高さ(または核の後で共に L)なので、線は途切れず連続する。**核が ー の上に来る**(ー と ン で高さが違う)
   まれな場合だけ、スロット順に描くと折れが時間順と逆になるので、その語は人が確認して例外扱いにする(規則は未定)。

**ADR-0010 との関係**: 決定5(かなの行にも出す)は、ADR-0010 決定6 の「線を載せる対象はクメール文字の行を第一候補とする」の**部分改定**である
(クメール文字の行とかなの行の両方に出す)。決定1〜4・6・7 は、ADR-0010 決定6 が未決・設計書で決めるとした点(線を載せる単位・符号化・句の核・合成規則)と、
決定3 が衝突率で決めるとした「ライトに残すか」の**具体化・暫定決着**で、決定2・3 の内容を書き換えるものではない。

## 検討した代替案
- **(B) 下がり目だけ ꜜ**: 情報が足りない(L 始まりや H の広がりは規則を知らないと読めない)。U+A71C は Noto Sans Regular にあるが Noto Sans Khmer に無く、古い Android での欠字も未確認。
- **(C) Chao 声調文字(˥˩ 等)を流用**: 書記音節ごとの輪郭で、拍の位置と対応せず、句をまたぐ連続線にならない。フォント作業が最大。声調言語向けの記号で誤解も招く。
- **フォント方式(ADR-0008 の GSUB 伸縮をクメール文字に拡張)**: 書記音節ごとの幅の列挙、Khmer シェイパでの文脈規則、二重符号化の要否がいずれも未確認で、作業量が大きい。CSS/SVG が実機で崩れた場合のみ再検討する。
- **書記音節単位の線**: 核が書記音節の内側に落ちる位置(候補の 39.2%)が表せないので却下。
- **H と L の2段の折れ線**: ユーザー判断(Q2)で H のみに決定。
- **語の型番号を見せる**: ユーザー判断(Q1)で見せない。
- **`<ruby>`+ `<rt>` の線、SVG 重ね**: 未検証のため決定には含めない。SVG 重ねは、CSS で書記音節の内側の位置(半幅)が出せない場合の逃げ道として残す。

## 結果(影響)
- ja-khmer は `kana-multi.woff2` に依存せずアクセント線を出せる(ADR-0014 の未決事項に影響しない)。生成器は拍→可視スロットの対応を保持する必要がある
  (現行 `tools/ja-khmer-spike` の変換は保持していない)。
- **未決・未確認**:
  - **確認者(Q4 の残り)**: データはエージェントが Wiktionary から取り込んで作り、確認者(日本語話者)は未定なので、当面すべて「未確認」(決定6)。
    未確認のまま表示に出すか、確認済みだけ出すかは未決(D13 の先送りの扱いに倣うなら、未確認と分かる形で出す案がある)。Wiktionary の型と NHK 等の辞典との一致も未照合。
  - **ライセンス(Q4 の残り)**: 決定8 で分離・帰属表示までは決めた。CC BY-SA の継承範囲の法的判断は未確認。リポジトリ全体のライセンス方針は別途。
  - **Q6 の残り**: 決定9 で位置は決まった。核が ー の上に来る語の扱い(未定)と、実機での並び・位置の確認(設計書 §8 #9)。
  - **実機確認**: iOS(WebKit)・Android 10/14 での CSS の線の描画、システムのクメール文字フォントの最大の高さとの重なり、span 間の隙間、コピー・読み上げ、
    あい=ៃ の半幅の線。`glyph-check` の目視が最終確認(ADR-0004)。見比べる候補は提案書 §5.3。
  - **アクセント衝突率**は未測定(ライトに残すかの根拠になる)。
  - 活用形・複合語・2拍以上の助詞でアクセントが動く語の規則は未検証(本 ADR は線を出さない範囲に限定)。
  - 語頭の簡略化(決定2の注)が実際の発音の抑揚に合うかは、話者の確認が要る(未確認。D13 と同じく先送り)。
  - 東京式の一般的な規則(1拍目と2拍目の高さの差と特殊拍での例外、です・助詞の核など)は文献照合していない。Wiktionary の型と NHK 等の辞典との一致も未照合。
- 副次: `convert-spec.mjs` の `ROW_V` a 行の「だ」の欠落(`ダー` が `undefined`)は 15b8bc6 で修正済み。
- **カバレッジの前提**: 語彙の測定(48 語)は日本人向けアプリの日本語訳(`courses/ja-km/phrases.yaml` の gloss。旧 `packages/content/data/phrases.yaml`)が元で、
  旅行者向けの本来の語彙(駅名・メニュー・数詞)ではない。実際のカバレッジはこれより低いはず(未測定)。
- **行分割・読み上げ**: span(inline-block)の分割がクメール文字の行分割・コピー・読み上げに与える影響は、行分割は句の `nowrap` で抑える設計だが、実機で未確認。
- **経緯**: 本 ADR のファイルは別セッションのコミット 0c30215(ADR-0020 の accept)に含まれて既にコミット済み(status: proposed のまま)。以降は追加の編集として直す。

崩れたら SVG 重ねに切り替える。決定3の実装手段の変更で、決定の骨格は変わらない)、(2) アクセント衝突率の測定(ライトの扱いは暫定)、(3) データの確認者と、未確認のデータを表示に出すかの判断、
