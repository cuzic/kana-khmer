# ADR-0021: ja-khmer の日本語ピッチアクセントは、拍単位の上線(H のみ)を DOM/CSS で描く

## コンテキスト
ADR-0010 決定6 は、日本語のピッチアクセントを文字の上の線で表す方針を置き、線を載せる対象(クメール文字の行、かなの行、下がり目記号 ꜜ)の
決着を `glyph-check` と作業量に委ねていた(未決)。声調の既存実装(ADR-0007 Chao 声調バー、ADR-0008 GSUB による音節幅への伸縮と
iOS/Android の二重符号化)を流用する案も残っていた。設計提案
[docs/research/2026-09-29-ja-accent-line-design.md](../research/2026-09-29-ja-accent-line-design.md) の調査結果は次のとおり。

- **書記音節は拍と一対一でない**。長音は右肩のマーカー、撥音・促音は末子音、あい は ៃ になる。JMdict 共通語(21,694 形)で、
  東京式で必ず高さが変わる1拍目と2拍目(一般知識、文献未照合)が同じ書記音節に入る語が **41.7%**、全ての拍の境目のうち書記音節の内側にあるものが 31.6%(実測)。
  書記音節単位の線ではこれが表せない。目に見えるスロット(基底の書記音節・末子音・長音マーカー)に分ければ、あい=ៃ を除いてほぼ拍と対応する。
- **クメール文字の送り幅は可変**(Noto Sans Khmer で ក 636、ហ 928、ក្រៅ 1499 など。実測)。ADR-0008 の幅ヒント(全角カナの数+上付き幅クラス)が使えない。
  生成器の出力は閉じた集合なので列挙は原理的に可能だが、規模は未測定で、Khmer シェイパでの動作も未確認。
- **DOM/CSS で描ける**。Wiktionary の Module:ja-pron 自身が `border-top`(高い拍)と `border-right`(下がり目)で描いている。
  デスクトップ Chrome で、Noto Sans Khmer+ja-khmer 用フォントの出力を書記音節・末子音・長音マーカーごとの inline-block に分け、
  `border-top` で連続した一定の高さの線になり、母音記号・◌៉◌៊・右肩記号と重ならないことを目視した。iOS・Android は未確認。
- ユーザーが方針を答えた(2026-09-29): 線の目的は自然な抑揚を真似させること(語の型番号は見せない)。L の線は引かず H だけ上線で示す(OJAD 式)。
  かなの行にも出す。活用形を含むフレーズは当面線を出さない。

## 決定
1. **線の単位は拍**とする。クメール文字の行では、生成器が拍に対応する可視スロット(基底の書記音節、末子音、長音マーカー)ごとに DOM の span を出す。
   あい=ៃ のように1つの字に2拍が入り分割できない場合は、字の半幅ずつに線を引く(未試作)。
2. **表現は上線方式(H のみ)**: H の拍の上に線を引き、L の拍には引かない。下がり目は線の右端の縦の段(`border-right`)で示す。
   平板は句末まで線が続き、尾高は句末の助詞で下がる。語の型番号は見せない。
3. **実装は DOM/CSS**(生成器が span を出し、`border-top` 等で描く)。フォントは使わない。ADR-0003 の制約(結合文字は基底と同じ span)を守り、
   span の分割は書記音節・末子音・長音マーカーの境目だけとし、前置母音と子音の間では切らない。句は `white-space:nowrap`。
   ADR-0016 に従い `?.` `??` を使わない。
4. **ADR-0007(Chao 声調バーの符号化)と ADR-0008(GSUB 伸縮・二重符号化)は ja-khmer には使わない**。理由は上記コンテキストの
   41.7% と幅の可変性。両 ADR は声調言語(kana-multi)のためのものとして有効なまま。
5. **表示行はクメール文字の行とかなの行の両方**(ユーザー判断 Q3)。かなの行は拍が1文字なので、同じ CSS の規則で出す。ただし実装は
   クメール文字の行と別に整理する: かなの行は文字と拍が対応する(ャュョ は直前と合わせて1拍)ので span の分割規則が簡単で、
   クメール文字の行のスロット分割規則(決定1)を共有しない。両行は同じ拍ごとの H/L 列(生成器が持つ)を入力にする。
6. **データ**: アクセント句(設計書 §2 の空白区切り)ごとに核の位置 n(0=平板)を持つ。Wiktionary の `{{ja-pron|acc=N}}`(東京式)を候補の種にし、
   人が確認したものだけに線を出す(確認できない句は線なし)。句への合成は最小規則から: 名詞・代名詞・副詞+助詞・だ・です は語の型をそのまま句の型とする
   (助詞・です は無アクセント)。**活用形を含むフレーズは当面線を出さない**(ユーザー判断 Q5。phrases.yaml の 40 件中 10 件が該当)。
   複合語・感動詞・慣用句の句分けは人が与える。設計書 §2・§3.3 と `packages/content` の形式は本 ADR に合わせて別途改める。
7. **ライト**では暫定で線を残す。アクセント衝突率(同じかな読みで型だけが違う語の割合。D5 と同じ測り方)を測れるまで、詳細・ライトとも同じとする。

## 検討した代替案
- **(B) 下がり目だけ ꜜ**: 情報が足りない(L 始まりや H の広がりは規則を知らないと読めない)。U+A71C は Noto Sans Regular にあるが Noto Sans Khmer に無く、古い Android での欠字も未確認。
- **(C) Chao 声調文字(˥˩ 等)を流用**: 書記音節ごとの輪郭で、拍の位置と対応せず、句をまたぐ連続線にならない。フォント作業が最大。声調言語向けの記号で誤解も招く。
- **フォント方式(ADR-0008 の GSUB 伸縮をクメール文字に拡張)**: 書記音節ごとの幅の列挙、Khmer シェイパでの文脈規則、二重符号化の要否がいずれも未確認で、作業量が大きい。CSS/SVG が実機で崩れた場合のみ再検討する。
- **書記音節単位の線**: 語頭の1〜2拍目の変化が表せない(41.7%)ので却下。
- **H と L の2段の折れ線**: ユーザー判断(Q2)で H のみに決定。
- **語の型番号を見せる**: ユーザー判断(Q1)で見せない。
- **`<ruby>`+ `<rt>` の線、SVG 重ね**: 未検証のため決定には含めない。SVG 重ねは、CSS で書記音節の内側の位置(半幅)が出せない場合の逃げ道として残す。

## 結果(影響)
- ja-khmer は `kana-multi.woff2` に依存せずアクセント線を出せる(ADR-0014 の未決事項に影響しない)。生成器は拍→可視スロットの対応を保持する必要がある
  (現行 `tools/ja-khmer-spike` の変換は保持していない)。
- **未決・未確認**:
  - **Q4**: アクセントデータの確認者(日本語話者)、Wiktionary(CC BY-SA 4.0)由来データの継承範囲(法的判断は未確認)、リポジトリ全体のライセンス方針(現状ルートに LICENSE 無し)。
    暫定の設計: アクセントのデータは別ファイル・別のライセンス表記にし、各語に出典 URL と取得日を付ける。
  - **Q6**: 長音+撥音(カーン)の並び(設計書 §8 #8)が決まるまで、拍と可視スロットの対応が確定しない(生成順は 基底→末子音→長音マーカーで、時間順と逆)。
  - **実機確認**: iOS(WebKit)・Android 10/14 での CSS の線の描画、システムのクメール文字フォントの最大の高さとの重なり、span 間の隙間、コピー・読み上げ、
    あい=ៃ の半幅の線。`glyph-check` の目視が最終確認(ADR-0004)。見比べる候補は提案書 §5.3。
  - **アクセント衝突率**は未測定(ライトに残すかの根拠になる)。
  - 活用形・複合語・助詞でアクセントが動く語の規則は未検証(本 ADR は線を出さない範囲に限定)。
  - 東京式の一般的な規則(1拍目と2拍目の高さの差など)は文献照合していない。Wiktionary の型と NHK 等の辞典との一致も未照合。
- 副次: `tools/ja-khmer-spike/src/convert-spec.mjs` の `ROW_V` a 行に「だ」が無く、`ダー` が `undefined` になる不具合がある(提案書 §7)。
