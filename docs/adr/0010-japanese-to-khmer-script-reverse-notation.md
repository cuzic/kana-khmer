# ADR-0010: クメール語話者向けに、日本語→クメール文字の逆方向表記をこの repo 内に別ディレクトリで設計する

## コンテキスト
kana-khmer は「日本人がクメール語を読む」方向(IPA → カナ)だけを扱ってきた。逆方向、つまり
クメール語話者が日本語を学ぶときの補助表記(日本語の音をクメール文字で示す)を追加したい。
**主な学習者像は、日本を旅行するクメール語話者とする**(ユーザー判断、2026-09-28)。現行アプリの
「日本人旅行者がクメール語を学ぶ」の対になる位置づけで、既存の `phrases.yaml`(シーン別の旅行フレーズ)を
再利用しやすい。就労・留学は主対象にしない(後日広げる場合は別途判断する)。

この方向は既存設計の単純な鏡像にならない。出力は発音ではなく**クメール語の正書法**(系列の選択と
慣習的綴り)なので、`khmer-kana` に無い知識が要る。音韻・正書法について、次の点を
2026-09-28 に二次資料(英語版 Wikipedia "Khmer script"・"Khmer language"、英語版 Wiktionary の
`Module:km-pron` と `{{km-IPA}}` の実行結果、Unicode 18.0.0 のデータ)で机上確認した。
**Huffman・Headley の本文とは照合していない**。ネイティブ確認・実音声の確認も未実施で、
ここでの「確認」は文献上の記述との一致にとどまる。対応表の根拠は設計書 `docs/ja-khmer-spec.md`
に記録する(初版作成済み。Wiktionary の `km-IPA` による実測で一部の記述を訂正している)。

- **母音長**: クメール文字は母音の長短を必ず書き分ける。「長短を書かない」選択肢は無く、
  日本語の短い開音節(か)を長い開音節(កា)で書けば、長音との区別が潰れる。短い開音節の書き方は
  ◌ៈ(短母音+声門閉鎖)と、終子音なしの ◌ិ ◌ុ(自動的に声門閉鎖を伴う)。**◌ះ は声門閉鎖ではなく末尾 /h/**
  なので使えない。語頭の非強勢音節(弱音節)は短母音で終子音なしが普通で、開音節の長短は語中の位置でも変わる。
- **濁音・ふ**: 外来語表記の慣習がある(g=ហ្គ、z=ហ្ស、f=ហ្វ、b/d=ប/ដ。借用語 ស៊ូស៊ី・គីម៉ូណូ・ម៉ានហ្គា で
  ら行=រ+៉、が行=ហ្គ が一致)。系列を変える ◌៉(o系→a系。付けられるのは ង ញ ម យ រ វ ប のみ)・
  ◌៊(a系→o系。ស ហ ប អ のみ)もあるが、任意の子音の系列を切り替えられるわけではない。
  「対応が無い」のではなく「慣習を採るか」の問題。慣習が無いのは つ /ts/(補助子音の表に ts は無い)。
  ហ្គ の系列は資料で食い違う(Wikipedia は a系、Wiktionary の km-IPA は ហ្ក=a系・ហ្គ=o系と読む)。
  日本語借用語の実例では ហ្គ(13行)と ហ្ក(8行)が併存し、同じ Wikipedia でも記事ごとに割れる。
  話者がどちらで読むかは未確認で、ガ行は標準の読みの確認が要る。
  ហ្វ の音価は [f]で、「ふ」/ɸ/ に近づける根拠は慣習的綴りだけ。
- **促音**: 閉音節の末子音(p t k 系)で近似できる。ただし長母音 ា の後の ក は声門閉鎖になりうる。
  coeng による重ね書きは、Wiktionary の発音入力で単子音として扱われている(間接証拠)ので使わない
  (「重子音として読まれない」と明示した記述は未確認)。
  また ◌ិ は終子音の前で [ə]/[ɨ] に変わるため、「きん・きっ」を ◌ិ+終子音で書くと
  い が別の母音になる(◌ុ は終子音の前でも a系 [o]・o系 [u] のままで、落ちるのは開音節の声門閉鎖だけ。
  Wiktionary `km-IPA` の実測による。当初の机上確認は「◌ុ も変わる」としたが誤り)。い を保つには ◌ី(長)を使うことになり、長さが変わる。
- **拗音**: coeng+យ は候補だが、系列規則(破裂音・摩擦音が共鳴音より優先)で母音が変わる
  (ព្យា=[pʰjiə]〔o系〕、a系の ក្យា=[kjaː]〔長母音〕)ので頭子音ごとに確認が要る。
- **撥音**: ម ន ង の末子音で、環境差を書ける。ただし ◌ិ の直後では母音が変わる(促音の項)。
  ◌ំ で書く手もあるが、音節全体の母音が変わるため別の設計判断になる。
- **ら行**: រ か ល か。プノンペン口語では頭子音 រ が口蓋垂音化または脱落する(文献で確認)。
  弾き音の រ は音声的に近いが、プノンペン話者には ល が確実に発音される代替になる。
- **あ・い・う・え・お**: a系だけでも o系だけでも5母音は揃わない(あ・え は a系、い・う・お は o系寄り)。
  「う」は a系だと ◌ុ=[o]・◌ឹ=[ə] で遠く、o系なら ◌ឹ=[ɨ]・◌ុ=[u]。ɯ に近いのは ◌ឹ(o系)だが、
  音声の聞き比べは未実施。「え」は ◌េ が a系でも [eː] の単母音で問題ない(o系は資料により [eː]/[ei])。
  二重母音になるのは「お」で、a系 ◌ោ は [ao] のため、o系(または ◌៊)を使う。したがって同じか行でも
  か=ក+◌ា、き=គ+◌ី、く=គ+◌ឹ/◌ុ、け=ក+◌េ のように子音字が音ごとに分かれる(お段の実際の採用は設計書の表による。
  こ=គ+◌ោ は当初の例示)。
- **アクセント**: 日本語のピッチアクセントは H/L の2段と下がり目の位置で決まる(語+助詞で効く)。
  かなはアクセントも一意な発音も表さない。

## 決定
1. **この repo 内に作る**(別 repo にしない)。**monorepo の思想に従い、ディレクトリは既存の
   `khmer-kana` 等と分ける**(ADR-0001 の延長)。ディレクトリ名・パッケージ名は仮置き
   (`kana-to-khmer` は `packages/kana-<lang>` の命名規約と方向が逆で紛らわしいため、出力がクメール文字と
   分かる名前にする)。フォント生成・`glyph-check`・`apps/web`・`packages/content` の形式を
   どう共用するか(共通パッケージ化か相互参照か)は、**共用範囲の洗い出し後に別途決める**(未決)。
   ADR-0001 が遅らせているのは表記ロジックの共通化(`kana-core`)で、フォント・検証・UI の共用は妨げない。
   洗い出しまでの既定: 既存パッケージの**公開 API のみを `workspace:*` 依存で使い、内部ファイルの参照と
   フォント生成スクリプトのコピーはしない**(試作の既成事実で共用方式が決まるのを避ける)。
2. **入力は「発音を確定した日本語」とする**。形式は、カタカナの発音表記(長音は ー、促音は ッ、
   助詞は発音どおり)+ 任意のアクセント情報。核の位置(整数、0 = 平板)は語単位で、フレーズでは表せないため、
   アクセント句の区切り+句ごとの核とする(Wiktionary は語単位なので、句への合成規則は設計書で決める)。かな綴りから発音への変換
   (は/へ/を、おう・えい)は範囲外で、データ側で人が書く。撥音の同化(ン → ម/ន/ង)は後続音から決まる
   ので、データは「ン」とだけ書き、生成器が選ぶ。無声化は、データで印を付けるか規則で出すかを設計書で決める。
   **アクセントは東京式アクセントとし、データ源は Wiktionary の日本語見出し語(アクセント型の記載)を
   参考にする**(ユーザー方針)。**英語版 Wiktionary の `{{ja-pron|acc=N}}`**(N=0 平板、1 頭高、n=第n拍の後で下がる。出典コード DJR・NHK 等付き)を使う。
   日本語版は京阪式が大半(7,276 件中、東京式は 1 件)で使えない。カバレッジは IPA 発音ページの約 75%、
   全見出しでは約 35%で、旅行フレーズの語彙での割合は未測定。語単位で、`acc` の位置・複数値・`only_show_acc` の
   扱いなど、抽出時に構造の揺れがある。ADR-0006 は Wiktionary を測定にだけ使ったが、今回は配布データに
   取り込むため、CC BY-SA の帰属表示と継承条件(share-alike)がどこまで及ぶかの判断が要る(法的判断は未確認。
   取り込む前に確認する)。
3. **表記の思想(ユーザー方針)**: クメール文字に無い音は、**IPA の発音記号を右肩に書く**。
   ピッチが変わるものは、**文字の上に線で表す**。これは既存の右肩 modifier(ADR-0005)と声調線
   (ADR-0007/0008)の思想の再利用である。
   この方針により、2階層の**仕組み**を持つ(現状の設計書 v0.7 では、ライトで落とす記号が無く、ライト=詳細である。
   差はアクセント線と、新表での衝突率の再測定で決まる): **詳細**は通常のクメール文字+右肩 IPA(+アクセント線)、
   **ライト**は詳細から右肩 IPA の span を機能負担量で選んで捨てたもの(ADR-0002 方式・ADR-0006 の選定法。
   別の変換表を持たない。差は記号の**追加**だけで、基底文字の選択は両階層で同じ)。何を右肩に回すか
   (濁音の有声性、つ /ts/、ふ /ɸ/、長音など。慣習的綴りで足りる音は基底文字で書く)は、
   対応表で書き分けられるかと、日本語の語彙で潰したときの衝突率(ADR-0006 と同じ測り方)で決める。
   右肩に置くのは、上付き文字(既存の右肩 modifier と同じ方式、ADR-0005)に限る。結合文字の IPA 記号(◌̬ ◌̥ など)は
   点線円の問題があり ADR-0003 の制約を受けるため使わない。設計書で規約にする点: 右肩記号は書記音節の
   末尾にしか置けず、頭子音・母音・末子音のどれを指すかが曖昧になること、上付き文字が Unicode に無い
   IPA 記号がありうること(ç には無い。ɾ は U+107A9 で、新しい文字なので古い環境で欠ける恐れがある)、右肩のラテン文字がクメール文字の辞書による行分割を
   乱すため nowrap が要ること。アクセント線がライトに残るかも、
   右肩 IPA と同じ衝突率の測り方で決める。
   **右肩に書く記号は、IPA ではなく日本語ローマ字(ヘボン式)の上付き文字とする**(ユーザー判断、2026-09-29。
   sh → ˢʰ、ts → ᵗˢ のように書く)。ローマ字を読める学習者に読みやすく、`ᶴ`(U+1DB4)のような珍しい文字を避けられ、
   使う文字が日本語の音に必要なものに自然に限られる。sh=ˢʰ の `ʰ` は ADR-0015 のカスタム字形と衝突するので、
   ja-khmer 用に標準の h 字形の別フォントを用意する(ユーザー判断)。長音の記号も、右肩に母音+マクロン(ō・ū 等)を書く方針に
   替わった(ユーザー判断、2026-09-29。基底の右の `ː` は取り下げ)。字形は、**右肩の上付き母音+結合マクロン(ᵃ̄ ⁱ̄ ᵘ̄ ᵉ̄ ᵒ̄)を採る**(ユーザー判断、2026-09-29。
   クメール文字側の記号(バントック等)は検討して却下)。結合文字を使うので、ADR-0003 の方式(ja-khmer 用フォントに
   5個の合成グリフを持つ)が要り、本 ADR の「結合文字を使わない」の例外になる(この判断で了承)。
   フォールバックは上付き母音の重ね書き(ᵒᵒ 等)で、`glyph-check` で実機の描画を確認して最終確認する。以下の「IPA を右肩」の記述は、
   この判断で「ローマ字を右肩」に読み替える。
   **記号を増やす基準**(ユーザー判断、2026-09-28): 右肩・長音などの記号は、**日本語で弁別的な対立**のうち、
   **衝突率が ADR-0006 の基準以上のものだけ**に付ける。判断の単位は**記号(ADR-0002 の span 種別)**で、
   同じ記号が担う複数の対立は、同時に潰したときの衝突率で測る(個別の値の和ではない)。実現差(破擦/摩擦、語ごとの [dʑ]/[ʑ] など)は、日本語で弁別的でないので
   表記しない。日本語で弁別的でも、衝突率が低く(ず・づ/ぞ、じゃ/ちゃ は 0.05〜0.10%)記号を付けるほどでないものは、
   詳細でも同綴りを許容する。IPA を使う以上、記号は際限なく増やせてしまうので、この基準で歯止めをかける。
   **揺れの大きい音(が行・つ・ふ・ん等)の既定は、日本語借用語の実例で多数派の綴りとする**(ユーザー判断、
   2026-09-28。少数派は採らない。根拠は `docs/research/` の借用語調査)。
   長音は記号で示す(ユーザー判断。借用語ではほぼ書き分けられていないため、独自の記号になる)。字形は、当初(2026-09-28)は
   `ː`(U+02D0)を基底の右に基線・通常サイズで置くとしたが、2026-09-29 の D8 で、右肩の上付き母音(結合マクロン付き、
   または重ね書き)の案に替わり、2026-09-29 の D9 で結合マクロン付きに確定した(上記)。実機の描画は `glyph-check` で最終確認する。
   ADR-0017 の衝突率の測定(仮の対応表・ネイティブ確認前)は、長短(共通語 14.4%)を記号で残す、促音は
   右肩にせず末子音の基底文字で書く、sh(ADR-0017 では `ʃ`)は右肩で書き分ける、という暫定方針を示している。本 ADR の決定3と整合する。
   長短は、通常の文字で書き分ける方法が見つかっていない(短母音の開音節は声門閉鎖を伴う)ため、
   長音の記号(上記)が第一候補になる(設計書で検討)。
   **クメール文字は、発音(+アクセント)を正として規則でビルド時に生成する**(ADR-0012 と同じ理由:
   規則を変えるたびに全データを手で直さない)。話者依存の選択(ら行の រ/ល など)は、語ごとではなく
   生成規則の設定(方言プロファイル)とする。規則で表せない個別の語(慣習的綴りの例外など)だけ、
   データ側に上書き(override)を持たせる。
4. **表記は必ず音声と併用する**。母語の文字で外国語音を書くと母語の音で読まれ、誤った発音が固定される
   (カタカナ英語の逆)。音声なしで表記だけを出さない。
5. **UI はかなとクメール文字の併記**とする。ルビか別行かは、判読性(クメール文字は縦に高い)と
   クラスタを DOM 要素で分けられない制約(ADR-0003)を踏まえ、`glyph-check` の実機確認で決める。
   旅行者向けなので、クメール文字の依存を薄めてかなで読めるようにすること自体は主目的にしない。
   ただし看板・駅名などを読む助けとして、かなの併記は残す。
6. **アクセントは、文字の上の線で表す**(ユーザー方針。決定3)。線を載せる対象はクメール文字の行を
   第一候補とするが、かなの行・下がり目記号 ꜜ との比較は `glyph-check` の実機確認と作業量で決める。
   声調文字(Chao トーンバー、U+02E5–E9)は Unicode 上は独立した文字で、どの文字列の後にも置けるため、
   声調と同じ方式でクメール文字の上に線を出すことは、符号化の面では妨げられない。妨げになるのは
   Unicode ではなく**現行の `kana-multi` 実装の前提**(声調線が乗る「音節」を全角カナ+右肩記号で定義し、
   幅ヒントもそれ前提。ADR-0008)で、これは変えられる。
   クメール文字の行に載せる場合(A)の追加作業は次のとおり。
   - クメール文字グリフのフォント同梱と、HarfBuzz の Khmer シェイピングとの干渉確認。右肩 IPA(決定3)も
     同じ行に載るため、書記音節の後ろに右肩文字を置く並びのシェイピングも確認する。
   - 可変幅クラスタ(下付き子音を含む)の幅の扱い。幅ヒントを出すには、ビルド時にシェイピングして幅を得る
     必要があり、生成器が同梱フォントに依存する。
   - 上に積まれる母音記号との縦の衝突と、線の高さの設計。
   - 既存のクメール語フォントの GSUB/GPOS と、声調の規則の統合。
   - 声調文字とクメール文字でスクリプトが分かれる境界での振る舞い(ADR-0008 の二重符号化が効くか)。
   - 区切り文字・幅ヒントが、クメール文字の行分割・コピー・読み上げに与える影響。CSS で線を描く方式も実装案になる。
   - 輪郭は書記音節ごとにしか置けず、モーラごとには置けない。
   これは作業量の見積もりであって、不採用の理由ではない。
   表現の設計としては、Chao 5段は日本語の H/L 2段に対して過剰精度になりうる点と、声調が音節単位なのに対し
   日本語アクセントはモーラ単位の高低と下がり目の位置で決まる点を、符号化の設計時に扱う
   (高い部分に線を引く、下がり目のみ示す等)。既存の符号化をそのまま流用する前提は置かない。
   声調文字を使う案は `kana-multi.woff2` を `apps/web` に採用することが前提で、それは ADR-0014 では未決。
   ꜜ・上線はこの前提に依存しない。
7. **検証は二本立て**: (a) 生成したクメール文字を独立のクメール文字→IPA 変換で読み戻す自動テスト
   (ADR-0009 に倣い、生成関数を再利用しない)。読み戻し表は生成側の対応表を参照せず、Wiktionary の
   クメール語見出し語の発音データ(ADR-0006 で使用済み)から系列×母音記号→母音を抽出して作る。対象は
   生成器が出しうる綴りに限る閉じた表で、クメール語一般の書記→発音変換は作らない。(b) クメール語話者の音読 × 日本語話者の聞き取り。
   (a) は系列の読み変わりの取り違えをネイティブ確認前に機械的に落とす。(b) の確保手段は当面無く、**当面は文献と機械読み戻し(a)だけで進め、母語話者の確認は後回しにする**
   (ユーザー判断、2026-09-28。ADR は proposed のまま)。(b) の確保は
   `docs/design.md` §8 の既存ブロッカー(クメール語話者の確保)に乗る。

対応表(基本46音・濁音・拗音をすべて。ユーザー判断)そのものは ADR に書かず、新しい設計書(`docs/ja-khmer-spec.md`、初版作成済み)を正とする。表記の確定・ネイティブ確認は設計書側の状態として管理し、
既存教材の Web 調査と、音韻・正書法の二次資料での机上確認は 2026-09-28 に済んだ(結果はコンテキストと
   代替案に反映)。残りは、Huffman・Headley との照合、現地教材の確認、ネイティブ確認で、これらの扱いを
   決めたうえで、ユーザーの明示承認をもって accepted にする(ユーザー判断。学習者像は旅行者で確定済み)。共用方式は新しい ADR で決め、
本 ADR の参照に足す(accepted の条件にはしない)。

## 検討した代替案
- **別 repo で作る**: フォント・実機検証・UI・データ形式を共用できなくなるため却下(ユーザー判断)。
- **`khmer-kana` の中にそのまま足す**: 出力が正書法で、`khmer-kana` にクメール正書法の知識が無く、
  責務が曖昧になるため、ディレクトリは分ける。
- **既存教材の慣習的な表記をそのまま採る**: Web で調べた範囲では、採れる統一慣習は見つからなかった
  (2026-09-28)。JF いろどりクメール語版(入門)は日本語をローマ字で示し、クメール文字の音写は
  目視した数ページで Ojigi の1箇所のみ。かなの全表はクメール語版 Wikipedia の ហ៊ីរ៉ាហ្កាណា/កាតាកាណា だけで、
  1かなに複数候補を併記(が=ហ្កា/ង៉ា、つ=ត្ស៊ុ/ស៊ុ、ん=ន/ង/ម/ំ)し、促音・長音の項目は無い。綴りは機関ごとに
  揺れる(ひらがな: Wikipedia ហ៊ីរ៉ាហ្កាណា、JF ហិរាហ្កាណា)。東京外国語大学はカタカナ表記を緊急用と明記している。
  したがって借用語の慣習(ហ្គ・ រ+៉ など)を出発点にし、対応表で独自に固める。
  日本語借用語・固有名詞 181 語の綴りを集めた調査(参照)では、子音字の系列の使い分け(あ・え・お段は a系、
  い・う段は o系、鼻音・流音・半母音は ◌៉)、ざ行=ហ្ស、ぱ行=ប៉、拗音=្យ、東京 តូក្យូ、着物 គីម៉ូណូ、
  寿司 ស៊ូស៊ី は比較的確立していた。が行・つ・ふ・し・ち・ん・促音・長音は揺れが大きい。長音はほぼ書き分けられない。
  王立アカデミー等の公的な日本語音写規則は見つからなかった。未確認: 紙の教材、送り出し機関、
  JICA、アプリ内表示、みんなの日本語クメール語版、YouTube。現地の教材はクメール語話者への聞き取りが要る。
- **かなを最初の1〜2週で教え、クメール文字表記は最初期だけにする**: 就労者・留学生向けなら有力だが、
  旅行者(短期利用)には学習負担が大きすぎるため、主案にしない。
- **クメール文字だけで日本語を表記して学習させる**: かなを読めるようになる動線が無く、看板・書類で使えないため却下。
- **ローマ字併記のみ**: ラテン文字の読みが追加負担になるため、単独では採らない(併記は可)。
- **音声のみで教える**: 表記を不要にする理由にはならない。音声は代替ではなく必須の併用(決定4)。

## 結果(影響)
- 多言語展開(ヒンディー語・タイ語等)の系列とは別軸の「逆方向」が増える。共通化(`kana-core`)を
  検討する際、この方向の要件も入力にする。
- 未確定・未着手: ライトで何を残すか(衝突率の実測と、クメール語として自然に読める寄りか日本語音に忠実寄りかの方針)、
  既存教材の現地での確認(Web では未確認の範囲が残る)、Wiktionary のアクセントの取り込み方(語単位→句への合成、CC BY-SA)、設計書の作成。
- 未決: アプリを1つ(UI 言語切替)にするか、分けるか。PWA のインストール単位と i18n の設計量が変わる。
- `apps/web` はクメール語 UI(i18n)が要る。右肩 IPA とアクセント線の凡例・説明も、クメール語で用意する。ライトでもクメール文字の Web フォント(Noto Sans Khmer 等、OFL)の
  同梱と、古い Android WebView での coeng の描画確認が要る(ADR-0016)。フォントの3系統(ADR-0014)に
  4つ目を足すかの判断を伴う。
- `packages/content` の `phrases.yaml` は日本語⇔クメール語の対訳を既に持つ。新規データを作る前に、
  既存データの `ja` に発音とアクセントを足す案と比較する。旅行者にも看板・駅名は漢字で、
  本設計はかなまでを範囲とする(漢字は範囲外)。
