# ADR-0008: 声調線は音節全体の幅に GSUB で伸縮させ、iOS/Android を二重符号化する

## コンテキスト
声調線を直前のカナ1文字(モーラ)の上だけに置くと、`ダア`(カナ2個)や `ストラʳᵊィ`(カナ4個+修飾2個)
のような複数カナの音節で、線がどの音節に属するか分かりにくい。一方でフォントは「音節」という概念を
持たず、文字の並びでしか判定できない。さらに iOS(WebKit)と Android(Chrome)でシェイピング単位の
分かれ方が違う: iOS はフォントの切り替えで分かれるがスクリプトでは分かれず、Android は逆にスクリプトが
変わる所(カナ⇔ラテン文字)で分かれる。そのため単一の不可視文字による符号化ではどちらか一方でしか
効かないことが `spike/tone-font` ブランチの実機相当 CI で判明した。

## 決定
音節ごとに次の符号列をデータとして出力する。

```
U+E000(区切り。iOS向け) 本体(全角カナ+修飾文字) 幅ヒント文字(U+2061-2064。Android向け) 声調文字
```

幅ヒントは、全角カナの個数と、上付き文字を3段階の幅クラス(実測送り幅を `SCLASS_CEIL` で量子化)
ごとに数えた個数から成る。GSUB(`ccmp`/`rclt`)でこの符号列を文脈にした連鎖規則により、音節の全幅に
合わせて伸縮させた声調グリフに置換する。線の長さには上限 `SPAN_MAX = 2400`(全角カナ2.4文字分)を
設け、長い音節でもレベル間の高さの差(120単位、`TONE_Y` は1レベルごとに120刻み)が水平化して
読めなくなるのを防ぐ。

## 検討した代替案
- **GPOS 単一位置調整案**(線の長さを固定し、位置だけ音節中央にずらす): フォントが軽い(16KB)利点は
  あるが、線が音節全体を覆わずどの音節に属すか分かりにくいため不採用(既定は GSUB 案。GPOS 案は
  `spike/tone-font` と本書に記述が残るのみで、`kana-multi.woff2` には実装されていない)。
- **区切り文字のみ、または幅ヒントのみの単独符号化**: 前者は Android で、後者は iOS でそれぞれ効かない
  ことを実機相当 CI で確認し、併用に決定。
- **上付き文字の幅を一律480と仮定する**: 実測(約160〜487)との誤差が最大230ユニットに達したため、
  1回目の Opus レビュー(`8419434`)で3段階幅クラス化した。ただしこの版は代表値にクラスの上限を
  そのまま使っていたため、ずれが常に同じ向きに積み重なるバイアスが残り、2回目の Opus レビュー(R1、
  `4dc45eb`/`92021b2`)で代表値をクラス内の実測平均に修正した。中心のずれが ±30 ユニット程度に
  収まっていることは、3回目の Opus レビューで実測確認した
  ([ADR-0009](0009-independent-geometry-verification.md) 参照)。
- **幅クラスを5段階にする**: 精度は上がるが、マーカー経路(区切り文字方式)の規則数がクラス数の指数で
  増え(3段階で約1.2万件、5段階では約9万件の見積もり)、フォントのビルド時間・サイズとも実用的で
  なくなる。3段階か5段階かはユーザーが判断した(`8419434` のコミットメッセージ)。

## 結果(影響)
新しい上付き修飾記号を追加する際は、その記号の幅クラス(1〜3)を `SCLASS_CEIL` の基準で割り当て、
`kana-multi-tone.json` に登録する運用になる。生成フォントのサイズは幅クラスの粒度とともに増える
(3段階で 26,495 グリフ・83,864 バイト。ビルド時間は実測約5分で、生成物としてコミットするため CI の
ビルド時間には影響しない)。アプリ側は音節 span に `white-space: nowrap` を付け、行末で声調文字だけが
次行に落ちるのを防ぐ。区切り文字 U+E000 は `kana-multi` が効かない環境では豆腐(□)として見えるが、
声調を持つ音節にしか出ないため実害は小さいと判断した。

**負の影響**: 音節内のカナ数(`nF ≤ 5`)・上付き文字の合計(`≤ 4`)・区切り文字を含むグリフ数
(`≤ 9`)に上限があり、超えると**エラーにならず黙って少しずれた位置に出る**(`khmer-kana` 側で
生成時に拒否する義務が生じる。まだ未実装)。
