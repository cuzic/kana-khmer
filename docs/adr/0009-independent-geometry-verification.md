# ADR-0009: フォント自動検証は生成関数を再利用せず幾何を独立に再計算する

## コンテキスト
`kana-multi.woff2` の声調線伸縮ロジックは、Opus のレビューを4回受けて固まった。その過程は次の順序で進んだ。

1. **検証スクリプトが無い状態で2件のバグが出荷された**: 基準ブラケット(stem)が伸縮後も固定座標のまま
   描かれる不具合(C1)と、上付き文字の送り幅を一律480と仮定した不具合(C2、実測は約160〜487)。
   どちらも自動検証が無いまま `kana-multi.woff2` に入っていた。
2. **1回目の Opus レビュー(PR#1)** が C1・C2 を含む3件の重大な不具合を指摘し、
   「検証スクリプトがリポジトリに無いこと自体が C1・C2 が素通りした直接の原因」とも指摘した。
   修正コミット `8419434` で C1 を直し、C2 を3段階の幅クラス化で緩和し、**このとき初めて
   `verify-kana-multi.py` を追加した**。ただしこの初版は、グリフ名の接尾辞(`_w1280` 等)を比較するだけの
   弱い判定だった。
3. **2回目の Opus レビュー(R1)** が、3段階幅クラスの代表値にクラスの**上限**をそのまま使っていたため
   ずれが常に同じ向きに積み重なるバイアスを発見。`4dc45eb` で代表値をクラス内の実測平均に修正すると同時に
   (「R2」)、検証スクリプトを「`build-kana-multi-font.py` 自身の `contour_glyph()`/`w_of()` を呼んで
   期待値を作り、実際のシェイプ結果と比較する」方式に書き換えた。
4. **3回目の Opus レビュー(N1)** が、mutation test(C1 のバグをわざと再現させる)で、この版の検証は
   期待値も実際の値も同じ `contour_glyph()`/`w_of()` を経由するため、生成関数自体のバグを原理的に
   検出できないことを実証した。`017f119` で、生成関数を使わずに独立して幾何を導出するチェックを追加した。
5. **4回目の Opus レビュー**が許容誤差(centring tolerance)の妥当性を mutation test で検証し、
   `6519222` で締め直した。

## 決定
検証スクリプトに、生成側の関数を使わずに独立して幾何を導出するチェックを追加する。

- `check_stem_independent`: 基準ブラケット(stem)の位置を `x0-60` から算術だけで独立に求め、実際の
  輪郭と突き合わせる。
- `check_centring_independent`: 実際の `x_advance` の合計から音節の中央を求め、線の中心との差を
  許容値と比べる。

既存の `assert_matches_expected`(生成関数を再利用する検証)は「配線(どの lookup・グリフが選ばれるか)」
の検証にすぎず、生成関数自体のバグは検出できないことを docstring に明記し、両者を役割分担させる。

## 検討した代替案
- **生成関数を再利用する「配線」チェックのままにする(R2 の版)**: lookup・グリフの選択が正しいかは
  検証できるが、`contour_glyph`/`w_of` 自身のバグは原理的に検出できない。実際に mutation test で
  検出漏れが実証されたため、独立導出のチェックを追加する方に倒した。
- **mutation test を常設のプロセスにする**: 生成関数のバグをもっと広く継続的に検出できるが、
  現時点ではスクリプトとして常設せず、Opus レビューのたびに手動で行う運用に留めている(今後の検討課題)。

## 結果(影響)
`build-kana-multi-font.py` を変更するたびに `verify-kana-multi.py` を実行することが運用ルールになった。
ただし CI には組み込まれておらず手動実行のゲートである([ADR-0004](0004-visual-review-is-authoritative.md))。
mutation test も自動化されたプロセスではなく、Opus レビューのたびに手動で行っており、次回のレビューが
無ければ同種の検出漏れ再発に気づけない可能性が残る。
