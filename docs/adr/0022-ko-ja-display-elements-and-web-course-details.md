# ADR-0022: ko-ja の表示要素(漢字・ふりがな・ローマ字・ハングル)と、apps/web のコース対応の細部

## コンテキスト
[ADR-0020](0020-course-per-language-pair.md) で、コースを言語の組み合わせ単位にした。段階1(`content` の一般化)は済んだ。
ko-ja(韓国語話者向けの日本語あいさつ)の下書き 40 件は、かなだけで書いてあった。日本の街の看板やメニューは漢字が多く、
韓国語話者が読める形の補助(ふりがな、ローマ字、ハングル)も要る。ADR-0020 の未決だった UI 文言と学習データの扱いも決める。

## 決定
1. **ko-ja のカードには 漢字かな交じり・ふりがな・ローマ字・ハングル・韓国語訳 を全部出す。まず全部入れて試す**(ユーザー判断)。
   情報量が多いので、試したあとに減らす前提。減らす判断は、実機で見てから別に行う。
   - **漢字かな交じり**: `text`(データに手で書く)。
   - **ふりがな**: `furigana`(ひらがな、正書法どおり。おう・を・は もそのまま)。データに手で書く。`text` の上に ruby で重ねる。
   - **ローマ字**: `latin`。`pron`(発音を確定したカタカナ)から `ja-hangul` の `renderRomaji` が生成する(修正ヘボン式。
     長音は ā ū ē ō、い段は ii、ん+母音・や行は n')。手で書かない。
   - **ハングル**: `readingFull`/`readingLite`。`pron` から `renderHangul` が生成する([ADR-0019](0019-ja-hangul-lite-detail-boundary.md))。
   - **韓国語訳**: `gloss`。
2. **ko-ja のフレーズは `parts`(語の分解)を必須にする。** 語ごとに `text`・`furigana`・`pron`・`gloss` を持つ。
   ローマ字とハングルの語区切り(スペース)と、ふりがなを語ごとに振ることに要る。連結すると `text`・`furigana`・`pron`
   が本文と一致することを `content` のビルドで検証する。
3. **聞き取り用の表現(相手が言うもの)を 5 件ほどに増やす。** 合計は 40 件のまま、場面ごとの件数を調整する。usage に「[듣는 표현]」と書く。
4. **UI の文言は、from の言語ごとの辞書ファイル**(`apps/web/src/i18n/<from>.ts`)にし、コースの `from` で選ぶ。i18n ライブラリは入れない。
5. **学習データ(SRS の進捗・設定)は、コースで名前空間を分ける。** localStorage・IndexedDB のキーに `kana:<course>:` を付ける。
   ja-km の既存キー(`kana-khmer:settings`)は、初回に読んで新しいキーに移す。

## 検討した代替案
- **かなだけ、または街で見る語だけ漢字を併記**: 情報量は少ないが、街の表記との対応が弱い。ユーザーは全部入れて試すことを選んだ。
- **ローマ字もデータに手書き**: 表記のゆれと入力の手間が出る。`pron` から生成すれば1つの情報源にできる。
- **`furigana` を `pron` から生成**: `pron` は発音どおり(おう→オー、は→ワ)で、ふりがなの正書法(おう・は)と違う。生成できないので手書きにする。
- **UI 文言を `course.yaml` に入れる**: 同じ from のコースが増えると重複する。
- **i18n ライブラリ**: 文言が少なく、古い Android WebView のバンドルサイズが気になる。

## 結果(影響)
- ko-ja のカードは情報量が多くなり、画面の設計(ruby、ローマ字の行、ハングルの2段)が要る。実機で見て減らす。
- `parts` の作成(語の分解、ふりがな)が 40 件分の作業になる。ネイティブ確認の対象も増える(日本語の自然さ、ふりがな)。
- `content` のスキーマに `furigana`(ひらがなだけ)、バンドルに `latin` が加わった(実装済み)。
- ja-km は影響を受けない(`furigana`・`latin` は省略可能)。
