# ADR-0030: 英語字幕の韻律表示は、語ごとの中間表現(IR)を核にし、見せる層を利用者が選べる Chrome 拡張(YouTube 限定)で出す

## コンテキスト
英語学習者(当面は日本語話者の初学者)向けに、英語字幕へ「意味のまとまり・強く読む語・弱形・推定の発音・ビート」を重ねて表示する計画がある。
出発点は、ChatGPT による英語プロソディ表記の調査と、それを一次資料に当たって検証した既存記法のカタログ
([`docs/research/2026-09-30-en-prosody-notation-catalog.md`](../research/2026-09-30-en-prosody-notation-catalog.md))。カタログの要点:

- 研究用の記法(ToBI・IViE・INTSINT・Tilt など)は凡例を覚える必要があり、数秒で消える字幕の表示層には向かない。内部に tier 構造を持ち、表示は選べる複数の層にするのが現実的。
- ToBI の自動付与は精度が限られる(人間のラベラー間でも、アクセント型の一致は約 6 割、中間句境界は約 50% と報告されている)。

`tools/en-prosody-spike`(Python のスパイク)で、手動字幕・自動字幕の語時刻・音声の無音・CMUdict から語ごとの情報を作り、表示を試した(2026-09-30)。

**ユーザーの発言(原文)**:
- 当初の前提: 「Chrome 拡張ですね。まずは Youtube をターゲットにしましょう。yt-dlp の資産を使って、音声や字幕を取得できるから。一旦、制約は無視して、サーバサイドでの実装でもいいよ。」「TED みたいなちゃんとした字幕があるコンテンツを前提とした上で、自動字幕が持つイベントタイミングも使って、音声分析もしたりして、付加情報も合わせて表示できるといい気がするかなぁ。」
- 規則だけで作った TED の見本(private のアーティファクト。音声による形はまだ無い版)を見て: 「これ、めちゃくちゃいいね。特に、弱形が意識しやすくなったのがいいです。」。ビートについては「ビートもけっこう大事だと思うけどね。ただ、なにを見せて何を見せないか選べる方がいいかもね」。
- 表示の方針: エージェントが構文木から入れ子の括り(`[The man [in the red coat]] [bought [a car]]`)を作る変換を試し、3 つの解析器の出力を見たユーザーが退けた: 「構文の括りはいいアイデアだと思ったけど、実際にやるとうまくいかないね。単純に / とか // とかを入れて、区切りを示すくらいがいいかもね。」
- PoC の範囲: 「精度はとりあえず、いいので、PoC 的に Chrome 拡張の開発を先に進めたいかなぁ。Youtube だけが対象でいいし、まずは AIを使った音声認識による発音記号の推定もやらなくていいです。」

**学習者にとって有益かどうかの検証は、まだしていない**(上の手応えは、ユーザー 1 人による、規則だけの見本への反応)。

## 決定
1. **分析結果は語ごとの IR(JSON)にする。** 形は `tools/en-prosody-spike/src/ir.py` の docstring が定義する(語ごとに `prominence` 0〜3・`beat`・`break_after`・`linked_next`・`kana`・`kana_lite` など)。
   ASS・SRT・HTML は IR だけを読む変換器にする。**Chrome 拡張は IR(JSON)を読まず、分析(`analyzeLine`)が返す `IRWord`(IR の語の部分集合。時刻・group・pause_ms・kana_rule・audio を持たない)を直接描く。**
2. **見せる層を独立に選べるようにする。** 層は `size`(強勢を文字の大きさで)・`bold`・`nucleus`(核の色と下線)・`weak`(弱形を灰色)・`breaks`(`/` `//`)・`link`(`‿`)・`beat`(`·` `●` `◎`)・
   `kana`・`ipa`(カナの右肩の IPA)・`audio`(音声で決めた形)の 10 層(拡張は音声を使わないので `audio` を除く 9 層)。プリセットは 入門・標準・詳細・リズム。
   定義は `tools/en-prosody-spike/src/layers.py`。選択は保存して次回に引き継ぐ(拡張では `chrome.storage.sync`)。
3. **入門向けに優先する情報は、まとまりの区切り・強く読む語と核・弱形とつながり。** 音の高さの線(ピッチ)と ToBI の音調は出さない。区切りは `/`(小)と `//`(大)だけで示す(ユーザー判断)。
   ビートは語単位(音節単位ではない)で、`·`(弱い)・`●`(強い語)・`◎`(核を兼ねる強い語)。
4. **最初の実装は YouTube 限定の Chrome 拡張(MV3)。** YouTube の字幕(CC)の DOM を読み、同じ文字列を分析して、プレーヤーの上に重ねて表示する。元の字幕は DOM に残して見えなくするだけ(ここから読むため)。
   **字幕の分析はブラウザ内で完結させ、字幕を外部に送らない**(規則による分析の範囲。音声を使う形は [ADR-0032](0032-en-audio-informed-variants.md) でサーバーが要り、この原則の例外になる)。
   ユーザーは「サーバサイドでの実装でもいいよ」としていたが、端末内にするのはエージェントの提案(ADR-0029 と同じく、字幕の文をサーバーに送ると、著作物の扱い上、端末内より不利なため)。
5. **分析ロジックは TypeScript パッケージ `packages/en-prosody` に持つ**(辞書は CMUdict の第 1 発音)。当面は Python 版(`tools/en-prosody-spike`)を挙動の正とし、自作の例文 60 文を 1 文ずつ Python で分析した結果
   (`packages/en-prosody/test/golden.json`)との突き合わせテストで、TS 版の一致を保つ。規則が安定し、Python 版を更新しなくなったら、TS 版を正に切り替える(その時点で golden は TS 側の回帰テストになる)。
6. **既定は規則による推定だけ。** 音声を使う形は任意の拡張([ADR-0032](0032-en-audio-informed-variants.md))とし、PoC の拡張には含めない。
7. **PoC では精度を追わない**(ユーザー判断)。

## 検討した代替案
- **一つの新しい統合記法を作る**(ChatGPT の提案): 層が多く、学習者が凡例を覚える必要がある。IR に全部を持ち、表示で選ぶ方式にした。
- **研究用記法(ToBI・IViE)を表示する**: 読めない。tier 構造の考え方だけを内部に借りた。
- **構文解析による入れ子の括り**: エージェントが試し、ユーザーが退けた(上記)。括りが深すぎて、韻律のまとまりにならなかった(例: `I [didn't think [he [was actually going [to buy it.]]]]`)。これは出力の見た目によるエージェントの見立てで、数値ではない。
  一方、TED 1 本(271 文)で spaCy(sm)・benepar・Stanza が出す構文の切れ目の強さを音声の無音と句読点と比べた数値(AUC は spaCy 0.77〜0.79、benepar 0.83〜0.84、Stanza 0.79〜0.83、句読点のみ 0.76。指標は粗い)は、
  **構文が区切りの強さの手がかりとして句読点より効く可能性**を示す。退けたのは括りの表示で、構文を区切りの補助に使うことではない。補助としての利用は未検証・未着手(スクリプトは使い捨てでリポジトリに無く、数値は再現できない)。
- **ASS を本命にする**: ASS は語単位の位置合わせ(カナ・ビートを語の真上に置く)が未実装で、実装するには語ごとの位置指定とフォントの幅の計測が要り、コストが高い。現状、カナの行と英語の行は別々に折り返される。
  DOM なら語ごとの列を作れるので、拡張は DOM で描く。ASS・SRT はオフライン用の出力として残し、ビートは語の直前の小さな `●` `◎` で出す(語に付くので位置がずれない)。
- **サーバーで変換する**: ユーザーは許していたが、字幕の文を外部に送らない方を提案した(決定 4)。音声を使う形はサーバーになる。
- **字幕をタイミング付きのデータとして取る**(yt-dlp や timedtext): **PoC では見送り**(却下ではない)。署名や認証が要るか、タイミングがどの程度得られるかは未検証。
  これを見送ると、語の時刻が得られず、音声の無音によるまとまりの区切りが使えない(ユーザーの当初の前提「自動字幕のイベントタイミング」「音声分析」から外れる。音声認識は PoC から外すというユーザー指示による)。

## 結果(影響)
- 実装状況: `packages/en-prosody`(規則分析の TS 版。突き合わせ 62 件が通る)と `apps/yt-prosody-ext`(拡張の土台。型検査は通るが、**ブラウザで動かしたことはまだない**)。コミット 46c6aae・e8d276c(スパイク)、3c27027(TS 版と拡張の土台)。
- **拡張の入力は字幕の断片で、スパイクの入力と違う。** 拡張は画面に出ている字幕の窓ごとに `analyzeLine` を呼び、末尾の語を必ず `//` にする。
  手動字幕では、字幕の区切り(意味の区切りと一致しない)ごとに `//` が出て、核は断片の最後の内容語になり、断片の末尾の機能語は強形になる。自動字幕のローリング表示では、語が増えるたびに末尾が動き、
  直前まで核だった語が普通の語に戻るなど、表示がちらつく。スパイクは字幕をまたいで通しでまとまりを作り、音声の無音も使っていた。突き合わせテストが守るのは、1 文ずつ分析する経路だけ。
  対策の候補(直前の数行をまたいで分析する、末尾の語は確定するまで強調しない、など)は未決。
- **IR の型は未整備。** 定義は Python の docstring だけ。拡張は IR(JSON)を読まず、`analyzeLine` が返す `IRWord`(時刻・group・pause_ms・kana_rule・audio を持たない部分集合)を直接描く。
  ADR-0032 でサーバーの IR を拡張が使うには、IR v0.1 の JSON Schema か TS の型が要る(未決)。
- **ビートは prominence から機械的に決まる**(核=◎、内容語=●、他=·)ので、`size`・`bold`・`nucleus` にない情報を持たない。音節単位のビート(多音節語のどこが強いか)は見送った。
  ユーザーが「大事」と言った要素なので、音節単位にするかは未決。
- 辞書(CMUdict)は約 3.3MB で、拡張が YouTube のすべてのページで読み込んで Map にする(字幕がオフでも)。メモリの見積もりと、配布物に辞書のライセンス表記を入れることは未決。辞書は生成物で `.gitignore` に入れる
  (`pnpm --filter en-prosody gen:dict`、uv が要る)。
- **言語の判定は弱い。** 拡張は、字幕の文字のうち ASCII のラテン文字が 8 割以上のときだけ元の字幕を置き換える(コミット 0fe11fd。`looksEnglish`)。日本語などラテン文字以外の字幕は置き換えない。フランス語・スペイン語・ドイツ語などラテン文字の他の言語は区別できず、元の字幕を隠して、辞書で引けない語を内容語として空欄のカナで並べる(未決)。改善の候補: 辞書で引ける語の割合をしきい値にする、字幕トラックの言語を読む。
- 発音を引けない語(数字・ハイフン語・固有名詞。TED 1 本で 26 語)は、カナが空欄になる。この数値は TED の講演(YouTube の動画 ID `iG9CE55wbtY`)の字幕によるもので、字幕も音声もリポジトリに無く、再現できない。
- 規則分析の二重実装(Python が正、TS が製品)は、当面、規則を直すたびに 2 か所を直して golden を作り直すことになる。同じ「端末内の字幕変換」でも ADR-0029(韓国語)は Python の PoC から Rust/WASM へ移す方針で、
  ここは TS へ移す。違いの理由は、**PoC が求める精度が低いため**: 規則は品詞を見ず、機能語の表だけで弱形を決める。そのため `Give me that book.` の `that`(指示詞で、強く読む)が弱形になる、
  `there`(場所と存在)・`some`(数量)を区別できない、などの誤りがある。品詞が要るようになったら、ブラウザ内の品詞付けか WASM を再検討する(未決)。
- 本記法は CMUdict(ARPABET、米国英語)を正とし、IPA はそこから写した表示用の字である(ɒ など、ARPABET にない音は書けない)。発音を IPA で持ち、カナを**ビルド時に**生成する [ADR-0012](0012-ipa-source-of-truth.md) とは入力形式も生成のタイミング(拡張は実行時に生成する)も違うので、その対象外。
- 自動字幕はローリング表示で文字列が頻繁に変わり、句読点が無い。まとまりの区切りは手動字幕より弱い。
- 拡張が動くのはデスクトップの Chrome。描画の確認の対象は [ADR-0031](0031-en-kana-with-shoulder-ipa.md) に書く。
- TED など他人の字幕は、公開リポジトリやテストに含めない。`tools/glyph-check/public/en-prosody-rows.js` には、TED の字幕から抜き出した個々の語(とそのカナ)が含まれる(語単位でリスクは低いが、字幕の文そのものではない)。
  TED の字幕は CC BY-NC-ND。見本のアーティファクトは private。
- 未決: YouTube の DOM(`.caption-window` などのクラス名。記憶に基づく前提で未確認)の変更への耐性、拡張の配布方法、YouTube の規約上の扱い(未確認)。
- 未検証: この表示が学習者の聞き取りに役立つか。要素ごとの効果(弱形の強調、つながり、ビート、右肩の IPA)を、聞き取りテストなどで測る必要がある。
