# ADR-0032: 音声の音素認識を先生役にして、語ごとの実際の形(弱形・弾き音・口蓋化)を決める。サーバー側の任意の拡張とし、PoC の拡張には含めない

## コンテキスト
[ADR-0030](0030-en-subtitle-prosody-ir-and-selectable-layers.md) の規則による推定は、CMUdict(米国英語の引用形)と「機能語はまとまりの末尾でなければ弱形」などの規則による。
実際の発話は話者で大きく違うので、TED の 1 本(約 20 分、3,080 語。話者は英国英語と思われるが未確認)で、音声から認識した音素と規則を突き合わせた(2026-09-30)。

- 音素認識: `facebook/wav2vec2-lv-60-espeak-cv-ft`(Apache-2.0、約 1.26GB。読み上げ音声 CommonVoice で学習した多言語モデル)の貪欲デコード。CPU(8 スレッド、AVX2 なし)で
  1203 秒の音声を 989 秒(実時間の 0.82 倍)。
- 語への割り当ては、自動字幕の語時刻(粗く、0.2 秒ほどずれる)の窓ではなく、認識した音素列と字幕の語ごとの期待音素の、帯つき動的計画法による整列。
  整列の一致は全体で 80%。語ごとの一致率が 0.6 未満の観測は信頼しない。
- 規則と音声の一致(`tools/en-prosody-spike/src/phonecheck.py`):
  - 弱形: 規則が弱形とした語のうち、母音が弱まったと認識されたのは 51%(419/814。欠測 67)。語によって大きく違う(`the` 96%、`a` 96%、`if` 92%、`to` 86% に対し、
    `was` 0%、`he` 0%、`had` 0%、`of` 11%、`you` 10%、`and` 20%)。規則が強形とした語(句末など)でも 26% は弱まった。
    なお `it` `if` `him` のように引用形の母音がすでに ɪ の語は、「弱まった」を区別できない(ɪ を弱い母音に数えているため、その語の数値は過大)。
  - 弾き音: 規則が弾き音と予測した 175 件のうち、認識も弾き音は 77 件(44%)、t/d は 88 件(50%)。
  - 語末の T/D(次が子音・休止): 491 件のうち 94 件(19%)が認識されない。
  - 口蓋化(`because you` など): 20 件のうち 7 件で語末が `dʒ` `tʃ` になった(欠測 3)。
- 規則は米国英語の前提で、この話者には外れる。**話者が変わると結果が変わる。**
- この音声による形を IR に反映した(`tools/en-prosody-spike/src/observe.py`、`analyze.py`)。観測のある語のうち信頼できるのは 89%、
  規則と違う形になったのは 3,106 語中 399 語(12.8%。`of` `you` `was` `have` `that` `at` `had` が大半)。
- Jev(TypeSafe AI の型つき判定モデル)でも精度を上げる検討をした。公式資料の索引には微調整の記載がなく、第三者の記事は「微調整できない。全アカウントが同じ重み」と述べている。
  入力はテキストのみで、音声は聞けない。料金は入力 100 万トークンあたり約 $0.042(第三者の記事による)。

## 決定
1. **音声による形は、規則による形とは別の層として持つ。** IR の `kana` が音声による形(観測が無い語・信頼できない語は規則)、`kana_rule` が規則だけの形。
   層 `audio` で切り替える([ADR-0030](0030-en-subtitle-prosody-ir-and-selectable-layers.md))。
2. **音素認識は、弱形・強形、弾き音・t、口蓋化(音声で融合が認識された箇所だけ)の決定にだけ使う。** 認識結果をそのまま表示はしない。
   語末の子音の脱落・同化などの規則は、規則が観測と合うと確かめてから足す(未実装)。
3. **サーバー側の任意の拡張とする。PoC の Chrome 拡張には含めない**(ユーザー判断)。音声の取得と処理はサーバーで行う前提で、拡張は結果の IR を使う形が考えられる(未設計)。
4. **Jev は、音を決める用途には使わない**(音声が聞けず、微調整もできない)。使うなら、文脈が要る判定(新情報か対比か、区切りの有無)に限り、
   「候補から選ぶ」形の質問にする。数値の比較は苦手とされるので、先にコードで区分に直して渡す。**効果は未検証**(API キーは取得可能とのこと)。

## 検討した代替案
- **認識結果をそのまま表示する**: 認識には誤りがあり(整列の一致 80%)、誤った音を「正しい音」として学習者に見せるおそれがある。
- **自動字幕の語時刻の窓で音素を語に割り当てる**: 時刻が粗く、`what` の音が `I` に入るなどの誤りが出た。
- **Jev を微調整して音の判断を蒸留する**: できない(上記)。蒸留するなら自前の小さな分類器(語・品詞・語の長さ・無音などの特徴量)で、先生の出力を正解にする形が考えられる(未着手)。
- **Whisper の API で音素・語時刻を取る**: 費用面で難しいとのユーザー判断。学習用の少数だけならよい。
- **ブラウザ側で音声を処理する**: モデルが約 1.26GB あり、YouTube の音声を拡張から取れるかも未調査。

## 結果(影響)
- 音声を使う形には、サーバーと音声の取得が要る。開発サーバーの IP から YouTube に入れなかったため、Tailscale 経由の自宅の PC で yt-dlp 用のプロキシを動かして取得した
  (環境依存の手順で、リポジトリには含めない)。音声をサーバーに保存・処理することの YouTube の規約・著作権上の扱いは未確認。公開サービスにするなら確認が要る。
- `tools/en-prosody-spike/src/phone_rec.py` が音素認識のスクリプト。依存(torch・transformers、モデル約 2.4GB)は別の仮想環境に入れる。
- 評価の正解データ(「この話者が実際に言った音」)が手元に無い。話者が変わったときの結果は未測定。音声つきの確認ページ(規則と音声のどちらが聞こえに近いかをユーザーが判定する)は未作成。
- 試した範囲は TED 1 本(1 話者)。米国英語の話者、会話、速い発話では別の結果になり得る。
