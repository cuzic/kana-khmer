# 声調表記 設計書 (v0.2)

タイ語など声調のある言語を、カナ表記の上に折れ線(Chao 声調表記の形)を重ねて表す仕組みの設計。
方針は `docs/design.md` §3(フォント)と、多言語展開の合意(声調は「カナ上に折れ線」)に従う。

**現状(2026-09-27)**: 音節全体に声調線を合わせる方式(§2.4・§3.1.1)は `spike/tone-font` ブランチで
CI 実機相当環境(iOS シミュレータ・Android エミュレータ)まで確認した(結果は `docs/tone-spike.md`)。まだ
`main` に統合していない。

`feature/kana-multi-notation` ブランチの `kana-multi.woff2` は、これとは別に、本書の符号化(§2.1・§2.3: Chao 声調文字
U+02E5–E9 を正、旧 U+0300 系をその別名とする)を先に採用して実装済み。ただし実装できているのは
**5つのレベル単体(平ら)と、旧5声調に対応する4組の2点(下降・上昇の形を含む具体的な4組。任意の2点の組み合わせではない)**
だけで、3点の並び(山型・谷型)は未実装。位置は常に**直前のカナ1文字の上**で、音節全体への位置合わせ(このブランチの
成果である §3.1.1〜3.1.3 の符号化・伸縮)は未着手。矢じりの有無(§8-1)・垂直の基準ブラケット(§8-2)は、
production側が独自に「単体は矢じりなし・2点は矢じりと基準ブラケットあり」と決めて実装済み(本書は未追認)。

## 1. 目的と非目的

**目的**
- 声調をカナの上に、**高さと動きが分かる折れ線**で出す。矢印1本では、高/上昇と低/下降の音域差が出ない。
- データ(文字列)は素の Unicode だけで持つ。フォントが当たらない環境でも意味が読める。
  ただし音節全体への位置合わせ(§3.1.1)には、私用領域の区切り文字 U+E000 が要り、その1文字だけは
  この目標の例外になる(トレードオフは §3.1.1・§5・§8-9 に記載)。
- 言語ごとの声調の数や形(タイ語5、ラオ語6、ミャンマー語4 …)を、フォントを作り直さずに表せる。

**非目的**
- 言語ごとの声調の決定(子音の類 × 声調記号 × 母音の長さ → 声調)。これは各言語パッケージの仕事で、本書は「決まった声調をどう表記・描画するか」だけを扱う。
- 声調の音声的な正確さの保証(Chao 値はネイティブ確認前は仮)。
- U+20D0–20FF の記号を声調に使うこと(§2.2 で却下)。

## 2. 符号化

### 2.1 声調文字の並び

声調は **IPA の声調文字(Modifier Letter Tone Bars)** を 1〜3 個並べたものとし、カナの直後に置く。

| 文字 | コードポイント | Chao レベル |
|---|---|---|
| ˥ | U+02E5 | 5(最高) |
| ˦ | U+02E6 | 4 |
| ˧ | U+02E7 | 3(中) |
| ˨ | U+02E8 | 2 |
| ˩ | U+02E9 | 1(最低) |

- 1個 = 平ら(レベル声調)。2個 = 始点→終点。3個 = 始点→中間点→終点(山型・谷型)。
- 声調文字は**音節の末尾**に置く(§2.4)。例: `カ˨˩`、`カʰ˦˥`、`カㇰ˨˦˥`、`ストラʳᵊィ˨˩`(音節全体で1つ)。
- 文法: `syllable := kana+ modifier* tone?`、`tone := level{1,3}`、`level := [˥˦˧˨˩]`。4個以上は不正(検証でエラー)。
- 隣り合う同レベルの重複(˧˧)は許すが、正規形は1個(˧)。データ生成側は正規形で出す。

### 2.2 U+20D0–20FF を使わない理由(調査結果)

- 矢印・ハープーン・点・囲み記号で、高さ(音域)を表せるものがない。
- 結合クラス(ccc)が 230 / 220 / 1 / 0 に散らばる。NFC で並びが入れ替わり、`カ + U+20D7 + U+0323` が `カ + U+0323 + U+20D7` になる。ccc の違う記号を並べる合成規則は GSUB で拾えなくなる。
- フォントが当たらない環境で、意味の通らない記号(⃣ ⃠ など)が出る。

声調文字なら ccc=0、カテゴリ Sk で、NFC/NFD で並びが変わらない。フォントが無くても `˨˩` として読める。
U+20D0 ブロックは、声調以外の修飾(§9 の将来枠)に取っておく。

### 2.3 既存の U+0300–030C との関係

既存の 5 声調(U+0304 中 / 0300 低 / 0302 下降 / 0301 高 / 030C 上昇)は残す。**ショートカット別名**として扱い、
`カ + U+0301` は `カ + ˦˥` と同じ折れ線を出す(グリフは共有)。新規データは声調文字で書き、U+0300 系は書かない。

### 2.4 音節の定義(声調が乗る単位)

声調は、**音節全体**の真上に描く(§8 旧未決事項6・スパイクで解決)。フォントは「音節」を知らないので、並びの形で定義する。

- **音節** = 全角カナ1個以上(U+30A0–30FF、長音 `ー` を含む)+ 修飾文字 0個以上 + 声調文字 0〜3個。次の音節の先頭カナが来たら区切る。
  `ダア`(カナ2個)、`ストラʳᵊィ`(カナ4個+修飾2個)のように、カナが複数でも1つの音節になり得る。
- **修飾文字** = 右肩の上付き文字(ʰ ʱ ʲ ʷ ⁿ ˣ ˠ ʶ ˀ ˤ 𐞥 ʳ ˡ ᵓ ᵊ ᵋ ᵅ ᶤ、ħ の合字)。半濁点 U+309A・語末の小さい子音カナ(ㇰ…ㇿ)は
  幅 1000 の全角カナ扱いとする(送り幅が同じため)。
- 声調は必ず音節の末尾(修飾文字の後)に置く。修飾文字の間や、カナの直前には置かない。
- 声調線の中心は、**音節を構成する全カナ+修飾文字の全幅の中央**にそろえる(§3.1.1)。1音節に声調は1つだけ。
- 「モーラ」(カナ1文字+修飾文字)という語は、音節を構成する最小単位として本書の以前の版で使っていた。位置合わせの対象は
  音節(複数モーラの並び)に広げたので、以降は「音節」で統一する。

## 3. 描画(フォント)

### 3.1 全体方式

`kana-multi.woff2`(カナと全記号を1フォントに収める。Android は基底と結合文字が別フォントだと欠字にするため)に、
次の3つを入れる。

1. **cmap**: ˥˦˧˨˩ の各文字に、レベル声調のグリフ(短い水平線)を割り当てる。送り幅は 0。
2. **合成グリフ**: 2個・3個の並びごとに、折れ線グリフを1つ作る(25 + 125 = 150 個)。送り幅は 0。
3. **GSUB `liga`**: 並びを合成グリフに置換する。長い並びを先に書く(3個 → 2個)。1個は cmap のままで規則なし。

グリフの輪郭はカナの上(x = -800…-200、送り幅 1000 のセルの真上)に描いておく。送り幅が 0 なので、直前の1000幅の上に重なる。
これは現行の `arrow_glyph`(x = -800…-200)と同じ作りで、座標系を変えない。

### 3.1.1 音節の幅をフォントに伝える符号(マーカー + ヒント。スパイクで確定)

フォントは声調文字の手前に何文字あるかしか知らない。音節の幅 W(全角カナの個数 nF・修飾文字の個数 nS から
`W = 1000·nF + 480·nS` で決まる)を規則の文脈だけで判定しようとすると、`spike/tone-font` の CI で次の問題が出た
(詳細は `docs/tone-spike.md` §8)。

- **iOS(WebKit)**: シェイピングの単位はフォントの切り替えで分かれ、スクリプトでは分かれない。音節の頭に置いた
  区切り文字(私用領域 U+E000)は効くが、既定で無視される文字(U+2060 WORD JOINER など)は無視されて効かない。
- **Android(Chrome)**: シェイピングの単位は**スクリプトが変わる所**で分かれる。カナ(Katakana)と上付き文字
  (Latin)の間で単位が切れ、区切り文字の文脈規則が通らない。一方、声調文字の**直前**に置いた不可視文字は
  同じ単位に入るため効く。

どちらか一方の符号では全環境をカバーできないため、**2つを併用する**。音節ごとに次の並びをデータに出す。

```
U+E000(区切り。私用領域)  本体(全角カナ+修飾文字)  U+2062 ×(nF−1)  U+2063 ×nS  声調文字(˥…˩)
```

- U+2062 INVISIBLE TIMES を「2個目以降の全角カナの数」だけ、U+2063 INVISIBLE SEPARATOR を「上付き文字の数」だけ、
  声調文字の直前に並べる。生成側は音節内のカナと上付き文字を数えるだけでよく、フォントの送り幅を知らなくてよい。
- 区切り文字とヒント文字はどちらも ccc=0 で、NFC/NFD で並びは変わらない。
- 音節に声調がない場合、この並びは出さない(区切り文字・ヒントは声調とセットでのみ意味を持つ)。
- **トレードオフ**: 区切り文字 U+E000 は私用領域のため、`kana-multi` 以外のフォントでは何のグリフも定義されておらず、
  フォールバック時は豆腐(□)として見えてしまう可能性がある(§1 の「フォントが無くても意味が読める」という目標を
  一部崩す)。実際の見え方は未検証(`docs/tone-spike.md` §8 の残課題)。声調のない文字列には影響しない。

### 3.1.2 音節全体への位置合わせと線の伸縮(GPOS / GSUB。スパイクで確定)

声調グリフは、§3.1.1 の符号を文脈にした連鎖規則で処理する。2つの実装を試し、どちらも動く環境では同じ位置に出た
(`docs/tone-spike.md` §8)。

- **GPOS 案**: 声調グリフ(輪郭は §3.2 のまま、幅 600 固定)を、音節の中央に来るよう **単一位置調整**でずらすだけ。
  折れ線グリフは増えない。フォントは軽い(実測 16KB)。線の長さは音節の幅に関係なく一定。
- **GSUB 案**: 音節の幅 W ごとに、輪郭を引き伸ばした声調グリフ(`c_<levels>_w<W>`)へ**置換**する。折れ線グリフが
  幅の種類数だけ増える(実測 4000 個、31KB)。線が音節全体を覆うので、どのカナにかかる声調かが分かりやすい。

**採用: GSUB 案(線を音節の幅に合わせて伸ばす)。ただし長さに上限を設ける。**

- 線が音節いっぱいまで伸びると、長い音節(`ストラʳᵊィ` など、幅 5000 前後)ではレベル間の高さの差(115 単位/
  レベル)に対して線がほぼ水平になり、上昇・下降が読み取れなくなる(手元の Chrome で確認)。
- そこで、線の長さに上限 `SPAN_MAX = 2400`(全角カナ 2.4 文字分)を設ける。中心は音節の中央のまま、
  長さは `min(W - 2·SPAN_MARGIN, SPAN_MAX)`(`SPAN_MARGIN = 100`)。上限が効くのは音節の幅が 2600 を超える場合のみで、
  1〜2文字程度の音節は音節の幅いっぱいまで伸びる。
- 上限を超える音節では、線は音節の中央に居るが、左右いっぱいには届かない。声調がどの音節のものかは、線の中心位置で判断する。
- `SPAN_MAX` の値(2.4 文字分)は見た目で選んだ初期値で、他の値とは比較していない。glyph-check で調整の余地がある(§8)。
- GPOS 案は、線を伸ばさずに済む用途(フォントを軽くしたい、位置だけ合えばよい)向けに残す。既定は GSUB 案とする。

### 3.1.3 実装の要点(GSUB 案)

- 修飾文字のグリフを送り幅ごとに**幅クラス**にまとめる(上付き文字は 480 に統一。小さい子音カナ・半濁点は全角カナと同じ 1000)。
- 規則は「§3.1.1 の区切り・ヒント + 声調グリフ」の連鎖(chaining contextual sub/pos)。ヒントは長い並びを先に書く
  (`U+2063 U+2063` は `U+2062 U+2063 U+2063` の末尾にも一致するため)。
- 幅の合計が同じ組み合わせは、同じ幅の lookup に集約する(lookup の数は、取り得る W の種類数。実測 24 種)。
- 合字 `ʰ + U+0335 → ħ` と `ㇷ + ゚ → ㇷ゚` は GSUB が先に走るので、幅の計算は合字後の送り幅(ħ、ㇷ゚ のグリフ)で行う。

### 3.2 折れ線の形

| 項目 | 値(初期案。glyph-check で調整) |
|---|---|
| 高さ(レベル → y) | 1 → 1000、2 → 1115、3 → 1230、4 → 1345、5 → 1460(現行 `TONE_Y`) |
| x の範囲(カナ1個の音節。GPOS 案・単体グリフ) | -800 … -200。点が2個なら両端、3個なら両端と中央(-500) |
| x の範囲(GSUB 案・音節が複数カナや修飾文字を含む場合) | 音節の中心 ±min(W − 200, 2400)/2(§3.1.2)。高さは変えず、幅だけ音節に合わせる |
| 線の太さ | 58(現行 `STROKE`) |
| 継ぎ目 | 折れ点は丸めずマイター接合。線分ごとの長方形を重ねる現行方式で足りる。折れ点の欠けが目立つ場合だけ、折れ点に円を足す |
| 終端 | 2個以上の並びは終点に小さな矢じり(現行 `arrow_glyph` 流用)。レベル声調(1個)は矢じりなし |

矢じりの有無、基準線の要否は、見た目の判断事項。`feature/kana-multi-notation` の production フォントは既に
「矢じりあり・縦の基準ブラケットあり」で出荷済み(§8-1・8-2)。本書として追認するかは、glyph-check で見比べて決める。

### 3.3 生成の自動化

- レベル列 `(a,)` `(a,b)` `(a,b,c)` から折れ線を作る関数 `contour_glyph(levels, x0, x1)`(スパイク実装 `contour_glyph`)。
- 5 + 5^2 + 5^3 = 155 通りを `itertools.product` で列挙し、グリフ名 `c_<levels>`(例 `c_241`)を付ける。
- §3.1.2 で採用した GSUB 案は、これに加えて**幅ごとの伸縮版**(`c_<levels>_w<W>`)を、取り得る W の種類数(実測 24)
  だけ複製する。155 × 24 ≈ 3700〜4000 個(スパイクの実測 4008)。
- §3.1.1 のマーカー・ヒント・声調グリフを文脈にした GSUB/GPOS 規則を、同じ列挙から生成する(手書きしない)。
- U+0300 系は、対応する並び(0304→33、0300→21、0302→51、0301→45、030C→14)への別名にする。cmap を同じグリフに向ける。

グリフ数は GSUB 案で現状から約 4000 増える(スパイク実測: woff2 で 28〜32KB)。GPOS 案なら増加は 155 個程度に収まる
(スパイク実測: woff2 で 16KB)。

## 4. データモデル

`khmer-kana` の音節型に声調を足す。

```ts
type ToneLevels = string;                 // 例 "21", "45", "241"。1〜3桁、各桁 1–5
interface Syllable { /* 既存 */ tone?: ToneLevels }
```

- 内部表現は数字列(`"241"`)。カナ文字列への変換時に ˥…˩ に写す(`5→˥ … 1→˩`)。数字列にしておくのは、言語パッケージのテーブルを人が読みやすくするため。
- 詳細表記・ライト表記の両方で声調を出す(声調を落としたライト表記は、タイ語では意味が変わる)。
- 声調を持たない言語(クメール語)は `tone` を出さない。既存の golden テストは変えない。
- `tone` は音節に付き、描画では**音節全体**(§2.4。カナが複数あっても1音節)の末尾に出る。`ダア` のようにカナが
  2つの音節でも、声調線は音節全体(`ダア`)の幅に合わせて出る(§3.1.2 の GSUB 案で解決)。
- 描画層は、音節を構成するカナの個数 nF と修飾文字の個数 nS を数え、§3.1.1 のマーカー・ヒントを文字列に組み込む。
  `khmer-kana` の `Syllable`(または `Word` 内の音節区切り)が、この個数を数える単位と一致している必要がある。
- 言語パッケージは音節ごとに `tone` を決めて渡す。タイ語の声調則(子音の類、声調記号、母音長、生音節/死音節)は `packages/kana-th`(仮)の仕事。

## 5. 文字列の扱い(環境の落とし穴)

- **正規化**: NFKC/NFKD は絶対にかけない(CLAUDE.md)。声調文字・区切り文字 U+E000・ヒント文字 U+2062/2063 は
  すべて ccc=0 なので NFC/NFD では並びは変わらないが、テストで確認する(§6)。
- **折り返し**: カナ(ID)と声調文字(AL 系)の間は、UAX #14 上、行末折り返しが可能になり得る。声調が次の行頭に離れるのを避けるため、
  音節ごとの span に `white-space: nowrap` を付ける(アプリ側の音節 span 分割と同じ場所)。
- **フォントの当たり方**: 声調文字・区切り文字・ヒント文字を含む要素には `kana-multi` を `font-family` の先頭に指定する。
  声調文字がフォールバックフォントに落ちると、送り幅 0 の前提が崩れ、カナの横に文字が出る。
- **区切り文字 U+E000 のフォールバック**: `kana-multi` が効かない環境では、私用領域の文字のため意味のあるグリフが
  無く、豆腐(□)として見える可能性がある(§3.1.1 のトレードオフ)。実際の見え方は未検証(次の一手)。
- **フォールバック表示(フォント自体が効かない場合)**: `カ˨˩` のようにカナの横に声調文字が出る。読めるので実害は小さい
  (区切り文字を除く。上と合わせて次の一手で確認する)。
- **音節以外の直前**: 声調グリフの位置は、直前が §2.4 の音節(区切り文字 + カナ + 修飾文字 + ヒント)であることを前提にする。
  ラテン文字や空白の直後、修飾文字の間、1音節に声調が2つある並びは不正とし、検証で弾く。

## 6. テストと検証

| 層 | 内容 |
|---|---|
| フォント生成 | 155 個の全並びについて uharfbuzz でシェイプし、`カ + 並び` が「カ + 合成グリフ1個」になることを表明。未合成の並びが1つでもあればビルド失敗 |
| フォント生成 | §3.1.1 の符号(区切り + ヒント)を付けた音節(`カʰ`、`カㇰ`、`カʰㇰ`、複数カナの音節、複数音節の連続など、幅の全組み合わせ)に声調を付け、シェイプ後の声調グリフの中心 x が、音節全幅の中央(±2 単位)に来ることを表明。複数音節の連続で、位置調整が次の音節に漏れないことも表明 |
| フォント生成 | 各グリフの外接矩形が想定の x 範囲・y のレベル範囲に収まること。ゼロ幅であること |
| ライブラリ | `tone` 数字列 ↔ 声調文字の往復、不正入力(4桁、0/6、空、音節以外の直前、修飾文字の間、声調の重複)の拒否、NFC/NFD で不変 |
| 目視(glyph-check) | 全並びを代表音節(ア、カ、カʰ、カㇰ、ダア、ストラʳᵊィ など)の上に並べた表を、iOS/Android で見る。**合否は目視**、自動判定は補助 |

### 6.1 スパイクの結果(CI 実施済み。`docs/tone-spike.md` §8 に詳細)

GitHub Actions の iOS シミュレータと Android エミュレータ(API 29・34)で、§3.1.1〜3.1.2 の符号化と位置合わせを確認した。

| 方式 | iOS | Android 14 | Android 10 |
|---|---|---|---|
| ヒント(U+2062/2063)のみ | ✗ | ✓ | ✓ |
| 区切り PUA(U+E000)のみ | ✓ | ✗ | 未確認 |
| **区切り PUA + ヒント(採用)** | **✓** | **✓** | **✓** |
| 声調線を音節の幅に伸ばす(上限つき GSUB 案) | ✓(手元 Chrome で確認。iOS/Android の再撮影は未了) | ✓(上限を足す前の版で確認) | 未確認 |

- HarfBuzz(uharfbuzz)では、区切り・ヒントのどちらの符号化でも 110/110 件が音節中央への位置合わせに通った。
  実機相当環境での差は、シェイピングの単位の分かれ方(§3.1.1)による。
- GPOS 案・GSUB 案は、動く環境ではどちらも同じ位置に出た。
- 未確認: 区切り文字のみの3方式(WJ・ZWSP)は WJ が iOS で無視され Android でカナだけの音節にしか効かず、
  ZWSP は iOS でカナの上に豆腐が重なったため不採用。Android 10 での区切り文字単独の挙動、伸縮つき GSUB 案の
  iOS/Android 実機相当環境での再確認、区切り文字 U+E000 のフォント非対応時の見え方は残課題(§8)。

## 7. タイ語の声調(叩き台。ネイティブ確認前)

| 声調 | Chao(バンコク標準の代表値) | 表記 |
|---|---|---|
| 中(สามัญ) | 33 | ˧ |
| 低(เอก) | 21 | ˨˩ |
| 下降(โท) | 241 | ˨˦˩ |
| 高(ตรี) | 45 | ˦˥ |

## 8. 未決事項

1. 折れ線に矢じりを付けるか(向きが分かる)、付けないか(Chao 声調文字に近い)。
   **production 実装済み(要追認)**: `feature/kana-multi-notation` の `kana-multi.woff2`(本書とは別に実装)は
   「単体は矢じりなし・2点は矢じりあり」を採用し出荷している。本書がこれを追認するなら決定でよい。覆すならフォントの作り直しが要る。
2. 基準線を出すか。
   **production 実装済み(要追認)**: 上記フォントは、薄い横線ではなく、**縦の基準ブラケット**(レベル1〜5の高さを示す
   縦棒。声調線の左に固定で描く `stem()`)を全ての声調グリフに添えている。本書がこれを追認するなら決定でよい。
3. タイ語の下降・上昇を厳密な3点形にするか、丸めるか(§7)。
   **production の実装範囲(参考。決定ではない)**: 上記フォントは、5レベル単体と、旧5声調(U+0300 系)に対応する
   **4組の2点のみ**を実装している。任意の2点の組み合わせ(25通り)や3点の並び(125通り)は実装していない。
   タイ語で3点形が要るかはこの制約と無関係に、ネイティブ確認(§7・§8-7)で決める。
4. 声調の色分け(高い声調を暖色など)を併用するか。色覚差の配慮が要る。
5. 声調文字がカナの横に出るフォールバックを許すか、フォント読み込み前は声調を隠す(`font-display` と `unicode-range` の扱い)か。
