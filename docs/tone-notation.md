# 声調表記 設計書 (v0.2)

タイ語など声調のある言語を、カナ表記の上に折れ線(Chao 声調表記の形)を重ねて表す仕組みの設計。
方針は `docs/design.md` §3(フォント)と、多言語展開の合意(声調は「カナ上に折れ線」)に従う。

**現状(2026-09-28 更新、Opus によるレビュー — `/tmp/opus-review-kana-multi-pr1.md` — を受けて修正)**:
`feature/kana-multi-notation` の `kana-multi.woff2`(`build-kana-multi-font.py`)に、本書の符号化(§2.1・§2.3)と、
`spike/tone-font` が実機まで確認した音節全体対応(§2.4・§3.1.1〜3.1.3)の**両方を統合し、uharfbuzz と
iOS/Android 実機相当環境(glyph-check CI)の両方で目視確認まで終えた**(§8-12・§10-4・§10-5 は完了)。

- 任意の2点(25通り)・3点(125通り)を含む全155通りの並びに合成グリフができ、GSUB(`ccmp`)で1つの折れ線に置換される
  (以前は5レベル単体+旧5声調に対応する4組の2点だけだった)。iOS シミュレータ・Android 14・Android 10 すべてで
  山型・谷型の3点や任意の2点が正しい形で出ることを目視確認済み。
- 声調線は、区切り文字 U+E000 + 幅ヒント(§3.1.1 の4文字、以前の2文字から拡張)+ GSUB(`rclt`)の伸縮
  (上限 `SPAN_MAX=2400`)により、直前のカナ1文字ではなく**音節全体**(カナが複数・修飾文字つきでも)の中央に来る。
  `ダア`・`カʰ` での中央寄せ、連続する2音節での位置調整の非漏出、長い音節(`ストラʳᵊィ`)での `SPAN_MAX` の頭打ちを、
  3環境すべてで目視確認済み。
- **修正(旧版のバグ)**: 音節が伸縮するとき、左の縦の基準ブラケット(stem)が伸縮後の左端ではなく元の位置に固定されたまま
  描かれ、線の途中を貫く/線の外に浮くという不具合が初版にあった。`stem(pen, x0)` に直して解消(§3.2)。
- **修正(旧版のバグ、2段階)**: 上付き文字の実際の送り幅(約160〜487、文字ごとにバラバラ)を、中央寄せの計算式は
  一律480と仮定していたため、修飾文字を含む音節で中心が最大230ユニットずれ、短い音節では線が前の音節にはみ出す
  ことがあった。まず3段階の幅クラスに量子化して最大85ユニットまで縮めたが、クラスの境界(上限)をそのまま代表値に
  使っていたため、ずれが常に同じ向き(左)に出て上付き文字の数だけ積み重なる問題が残っていた(Opus の2回目の
  レビューで実測: `キʲᵊ` -225→-85、狭い文字4個の音節 -380 相当)。代表値をクラス内の**実測平均**
  (1→211, 2→357, 3→487)に変えることで、ずれの向きが上付き文字ごとにバラけて打ち消し合うようにした(§3.1.3)。
- **修正(旧版の制約)**: 下の点(U+0323)・きしみ声(U+0330)・半濁点(U+309A、合字前)が音節の途中に挟まると、
  区切り文字経由(iOS)の規則が一致せず既定位置に後退する制約があった。`rclt` に `UseMarkFilteringSet` を足し、
  これらの結合文字を読み飛ばすようにして解消(§3.1.3)。ㇷ゚ の合字・ħ の合字は(合字が先に効く限り)元々問題なかった。
- 矢じりの有無(§8-1)・垂直の基準ブラケット(§8-2)は、production が採用した見た目(単体は矢じりなし・2点以上は
  矢じりと基準ブラケットあり)を全155通りに一律で適用した。本書として正式に採用に更新(旧「要追認」から)。

## 1. 目的と非目的

**目的**
- 声調をカナの上に、**高さと動きが分かる折れ線**で出す。矢印1本では、高/上昇と低/下降の音域差が出ない。
- データ(文字列)は素の Unicode だけで持つ。フォントが当たらない環境でも意味が読める。
  ただし音節全体への位置合わせ(§3.1.1)には、私用領域の区切り文字 U+E000 が要り、その1文字だけは
  この目標の例外になる(トレードオフは §3.1.1・§5・§8-9 に記載)。
- 言語ごとの声調の数や形(タイ語5、ラオ語6、ミャンマー語4 …)を、フォントを作り直さずに表せる。

**非目的**
- 言語ごとの声調の決定(子音の類 × 声調記号 × 母音の長さ → 声調)。これは各言語パッケージの仕事で、本書は「決まった声調をどう表記・描画するか」だけを扱う。
- 声調の音声的な正確さの保証(Chao 値はネイティブ確認前は仮)。
- U+20D0–20FF の記号を声調に使うこと(§2.2 で却下)。

## 2. 符号化

### 2.1 声調文字の並び

声調は **IPA の声調文字(Modifier Letter Tone Bars)** を 1〜3 個並べたものとし、カナの直後に置く。

| 文字 | コードポイント | Chao レベル |
|---|---|---|
| ˥ | U+02E5 | 5(最高) |
| ˦ | U+02E6 | 4 |
| ˧ | U+02E7 | 3(中) |
| ˨ | U+02E8 | 2 |
| ˩ | U+02E9 | 1(最低) |

- 1個 = 平ら(レベル声調)。2個 = 始点→終点。3個 = 始点→中間点→終点(山型・谷型)。
- 声調文字は**音節の末尾**に置く(§2.4)。例: `カ˨˩`、`カʰ˦˥`、`カㇰ˨˦˥`、`ストラʳᵊィ˨˩`(音節全体で1つ)。
- 文法: `syllable := kana+ modifier* tone?`、`tone := level{1,3}`、`level := [˥˦˧˨˩]`。4個以上は不正(検証でエラー)。
- 隣り合う同レベルの重複(˧˧)は許すが、正規形は1個(˧)。データ生成側は正規形で出す。

### 2.2 U+20D0–20FF を使わない理由(調査結果)

- 矢印・ハープーン・点・囲み記号で、高さ(音域)を表せるものがない。
- 結合クラス(ccc)が 230 / 220 / 1 / 0 に散らばる。NFC で並びが入れ替わり、`カ + U+20D7 + U+0323` が `カ + U+0323 + U+20D7` になる。ccc の違う記号を並べる合成規則は GSUB で拾えなくなる。
- フォントが当たらない環境で、意味の通らない記号(⃣ ⃠ など)が出る。

声調文字なら ccc=0、カテゴリ Sk で、NFC/NFD で並びが変わらない。フォントが無くても `˨˩` として読める。
U+20D0 ブロックは、声調以外の修飾(§9 の将来枠)に取っておく。

### 2.3 既存の U+0300–030C との関係

既存の 5 声調(U+0304 中 / 0300 低 / 0302 下降 / 0301 高 / 030C 上昇)は残す。**ショートカット別名**として扱い、
`カ + U+0301` は `カ + ˦˥` と同じ折れ線を出す(グリフは共有)。新規データは声調文字で書き、U+0300 系は書かない。

### 2.4 音節の定義(声調が乗る単位)

声調は、**音節全体**の真上に描く(§8 旧未決事項6・スパイクで解決)。フォントは「音節」を知らないので、並びの形で定義する。

- **音節** = 全角カナ1個以上(**U+30A1–30FA、長音 `ー`(U+30FC)、小さい子音カナ U+31F0–31FF**。U+30A0 ゠・U+30FB ・・
  U+30FD–30FF ヽヾヿ は含まない — フォント側の実装(`build-kana-multi-font.py` の `F` リスト)に合わせた正確な範囲)
  + 修飾文字 0個以上 + 声調文字 0〜3個。次の音節の先頭カナが来たら区切る。
  `ダア`(カナ2個)、`ストラʳᵊィ`(カナ4個+修飾2個)のように、カナが複数でも1つの音節になり得る。
- **修飾文字** = 右肩の上付き文字(ʰ ʱ ʲ ʷ ⁿ ˣ ˠ ʶ ˀ ˤ 𐞥 ʳ ˡ ᶿ ᶞ ᵑ ᵓ ᵊ ᵋ ᵅ ᶤ、ħ の合字)。語末の小さい子音カナ(ㇰ…ㇿ)は
  幅 1000 の全角カナ扱い(上の「音節」の一部)。
- **半濁点 U+309A は幅0**(ㇷ + ゚ の合字 `ㇷ゚` にしたときだけ、その合字全体が幅1000の全角カナ1個として数える)。
  修飾文字と同様、送り幅の量子化(3クラス、§3.1.3)の対象にはしない — 幅0のマークは iOS 経路(区切り文字方式)の
  `UseMarkFilteringSet` で読み飛ばされ、音節の幅の計算に一切関与しない(合字前の裸の U+309A・下の点 U+0323・
  きしみ声 U+0330 も同様に幅0・読み飛ばし対象)。
- 声調は必ず音節の末尾(修飾文字の後)に置く。修飾文字の間や、カナの直前には置かない。
- 声調線の中心は、**音節を構成する全カナ+修飾文字の全幅の中央**にそろえる(§3.1.1)。1音節に声調は1つだけ。
- 「モーラ」(カナ1文字+修飾文字)という語は、音節を構成する最小単位として本書の以前の版で使っていた。位置合わせの対象は
  音節(複数モーラの並び)に広げたので、以降は「音節」で統一する。

## 3. 描画(フォント)

### 3.1 全体方式

`kana-multi.woff2`(カナと全記号を1フォントに収める。Android は基底と結合文字が別フォントだと欠字にするため)に、
次の3つを入れる。

1. **cmap**: ˥˦˧˨˩ の各文字に、レベル声調のグリフ(短い水平線)を割り当てる。送り幅は 0。
2. **合成グリフ**: 2個・3個の並びごとに、折れ線グリフを1つ作る(25 + 125 = 150 個)。送り幅は 0。
3. **GSUB `ccmp`**(必須の合成なので、`letter-spacing`/`font-variant-ligatures` で切れる discretionary な
   `liga`/`calt` ではなくここに置く。§3.1.3・§5): 並びを合成グリフに置換する。長い並びを先に書く(3個 → 2個)。
   1個は cmap のままで規則なし。

グリフの輪郭はカナの上(x = -800…-200、送り幅 1000 のセルの真上)に描いておく。送り幅が 0 なので、直前の1000幅の上に重なる。
実装は `contour_glyph(levels, x0, x1)` 関数1つ(1〜3点の全部をこの1関数で描く。単体・2点用に分かれていた
`level_glyph`/`arrow_glyph` は統合済み)。

### 3.1.1 音節の幅をフォントに伝える符号(マーカー + ヒント。スパイクで確定)

フォントは声調文字の手前に何文字あるかしか知らない。音節の幅 W(全角カナの個数 nF・修飾文字の個数 nS から
`W = 1000·nF + 480·nS` で決まる。**旧式**。実装は上付き文字の幅クラスが3段階あるため式が異なる。§3.1.3 参照)
を規則の文脈だけで判定しようとすると、`spike/tone-font` の CI で次の問題が出た(詳細は `docs/tone-spike.md` §8)。

- **iOS(WebKit)**: シェイピングの単位はフォントの切り替えで分かれ、スクリプトでは分かれない。音節の頭に置いた
  区切り文字(私用領域 U+E000)は効くが、既定で無視される文字(U+2060 WORD JOINER など)は無視されて効かない。
- **Android(Chrome)**: シェイピングの単位は**スクリプトが変わる所**で分かれる。カナ(Katakana)と上付き文字
  (Latin)の間で単位が切れ、区切り文字の文脈規則が通らない。一方、声調文字の**直前**に置いた不可視文字は
  同じ単位に入るため効く。

どちらか一方の符号では全環境をカバーできないため、**2つを併用する**。音節ごとに次の並びをデータに出す。

```
U+E000(区切り。私用領域)  本体(全角カナ+修飾文字)  U+2062 ×(nF−1)  U+2061 ×n1  U+2063 ×n2  U+2064 ×n3  声調文字(˥…˩)
```

- U+2062 INVISIBLE TIMES を「2個目以降の全角カナの数」だけ並べる(nF、変更なし)。
- 上付き文字は実際の送り幅が文字ごとに大きく違う(約160〜487)ため、単純な「上付き文字の数」ではなく、
  **幅クラスごとの数**をヒントにする(§3.1.3 のバグ修正)。U+2061 FUNCTION APPLICATION・U+2063 INVISIBLE
  SEPARATOR・U+2064 INVISIBLE PLUS を、それぞれ幅クラス1・2・3の上付き文字の個数だけ、**この順で**並べる
  (実際の文字の出現順ではなく、クラス1→2→3の正規順。ヒントは声調とだけ結びつく合成用の信号で、見た目には
  影響しないので、生成側はクラスごとに数えて正規順に出すだけでよい — 実際の並び順を保持する必要はない)。
  U+2061/2064 は U+2062/2063 と同じ Unicode ブロック(既定で無視される・ccc=0・Cf カテゴリ)の文字で、
  スパイクが検証したのは U+2062/2063 の2つだけだったため、この2つは今回新たに glyph-check で確認した
  (§8-10)。
- 声調文字の直前に並べる。生成側は音節内のカナの数と、上付き文字を幅クラスごとに数えるだけでよく、フォントの
  実際の送り幅(゚〈U+309A〉=0、ㇷ゚=1個の全角カナ、上付き文字=クラス番号)は `kana-multi-tone.json`
  (`build-kana-multi-font.py` が出力するマニフェスト。コードポイント→クラス番号の対応表と、
  `SCLASS_WIDTH`・`MAX_NF`・`MAX_NS` の値を持つ)を読めばよく、フォント側の定数を二重管理しなくてよい。
- 区切り文字とヒント文字はどれも ccc=0 で、NFC/NFD で並びは変わらない。
- 音節に声調がない場合、この並びは出さない(区切り文字・ヒントは声調とセットでのみ意味を持つ)。
- **上限(実装済みだが本書に書かれていなかった)**: nF ≤ 5、上付き文字の合計(n1+n2+n3)≤ 4、区切り文字を含む
  音節あたりのグリフ数 ≤ 9(`MAX_NF`・`MAX_NS`・`MAX_SYLLABLE_LEN` in `build-kana-multi-font.py`)。
  **超えると、エラーにも既定位置にもならず、黙って少しずれた位置に出る**(超過分を無視して残りの並びで
  一致する規則があれば、それで解釈される)。`khmer-kana` の検証(§6)で、超過を生成時に拒否すること。
- **トレードオフ**: 区切り文字 U+E000 は私用領域のため、`kana-multi` 以外のフォントでは何のグリフも定義されておらず、
  フォールバック時は豆腐(□)として見える(§8-9 で実機確認済み。想定どおり)。声調のない文字列には影響しない。

### 3.1.2 音節全体への位置合わせと線の伸縮(GPOS / GSUB。スパイクで確定)

声調グリフは、§3.1.1 の符号を文脈にした連鎖規則で処理する。2つの実装を試し、どちらも動く環境では同じ位置に出た
(`docs/tone-spike.md` §8)。

- **GPOS 案**: 声調グリフ(輪郭は §3.2 のまま、幅 600 固定)を、音節の中央に来るよう **単一位置調整**でずらすだけ。
  折れ線グリフは増えない。フォントは軽い(スパイク実測 16KB)。線の長さは音節の幅に関係なく一定。
- **GSUB 案**: 音節の幅 W ごとに、輪郭を引き伸ばした声調グリフ(現行実装のグリフ名は `tone_<levels>_w<W>`。
  スパイク当時の名前は `c_<levels>_w<W>`)へ**置換**する。折れ線グリフが幅の種類数だけ増える
  (本番実測: 155 通り × 取り得る W の種類、woff2 で 83,864 バイト・26,495 グリフ。§3.3)。
  線が音節全体を覆うので、どのカナにかかる声調かが分かりやすい。

**採用: GSUB 案(線を音節の幅に合わせて伸ばす)。ただし長さに上限を設ける。**

- 線が音節いっぱいまで伸びると、長い音節(`ストラʳᵊィ` など、幅 5000 前後)ではレベル間の高さの差(115 単位/
  レベル)に対して線がほぼ水平になり、上昇・下降が読み取れなくなる(手元の Chrome で確認)。
- そこで、線の長さに上限 `SPAN_MAX = 2400`(全角カナ 2.4 文字分)を設ける。中心は音節の中央のまま、
  長さは `min(W - 2·SPAN_MARGIN, SPAN_MAX)`(`SPAN_MARGIN = 100`)。上限が効くのは音節の幅が 2600 を超える場合のみで、
  1〜2文字程度の音節は音節の幅いっぱいまで伸びる。
- 上限を超える音節では、線は音節の中央に居るが、左右いっぱいには届かない。声調がどの音節のものかは、線の中心位置で判断する。
- `SPAN_MAX` の値(2.4 文字分)は見た目で選んだ初期値で、他の値とは比較していない。glyph-check で調整の余地がある(§8)。
- GPOS 案は、線を伸ばさずに済む用途(フォントを軽くしたい、位置だけ合えばよい)向けに残す。既定は GSUB 案とする。

### 3.1.3 実装の要点(GSUB 案)

- **上付き文字の幅クラス(3段階)**: 実際の送り幅(Noto Sans のラテン文字幅 × 0.62、約160〜487)を、一律の値に
  丸めず、かといって文字ごとの実寸をそのまま使うのでもなく、**3段階の幅クラス**に量子化する。クラスの境界
  (`SCLASS_CEIL = {1: 280, 2: 400, 3: 500}`)は文字をどのクラスに入れるかだけを決め、W の計算に使う実際の値
  (`SCLASS_WIDTH`)は、そのクラスに入った文字の**実測平均**をビルド時に計算する(境界値そのものではない)。
  割り当てとクラスごとの平均値は `kana-multi-tone.json` に出力する(§3.1.1)。
  **旧版の不具合が2つあった**: (1) 一律480と仮定しており、実際の幅(最小160)と最大230ユニットずれていた。
  (2) 3段階化した直後の版は、境界値(クラスの上限)をそのまま W の計算に使っていたため、どの上付き文字も
  実寸より軽く見積もられることがなく、ずれが常に同じ向き(線が音節の外・前の音節側にはみ出す方向)に出て、
  上付き文字が複数あると足し合わさった(Opus の2回目のレビューで指摘。`キʲᵊ` で -85 ユニット、狭い文字4個の
  音節で -240 ユニット)。平均値を使うことで、ずれの向きが上付き文字ごとにバラけて打ち消し合うようになり、
  1個あたりの理論上の最大ずれはクラス内の実測分布による(目安 ±30 ユニット程度。厳密な値は
  `verify-kana-multi.py` の実行結果、またはビルド後の `kana-multi-tone.json` の `sclassWidth` と
  各文字の実測送り幅の差から計算できる)。
  小さい子音カナ・半濁点の合字(ㇷ゚)は全角カナと同じ幅1000(クラス扱いしない)。
- 規則は「§3.1.1 の区切り・ヒント + 声調グリフ」の連鎖(chaining contextual sub)。ヒントは長い並びを先に書く
  (`hintS2 hintS2` は `hintA hintS2 hintS2` の末尾にも一致するため)。ヒントは**正規順**(クラス1→2→3、§3.1.1)
  で出す前提なので、実際に出現しうる並びは「多重集合」であり、上付き文字が実際に現れる順の組み合わせ全部を
  列挙する必要はない(区切り文字方式=マーカー側の規則は、実際の並び順をそのまま列挙する。§3.3)。
- 幅の合計が同じ組み合わせは、同じ幅の lookup に集約する(lookup の数は、取り得る W の種類数)。
- 合字 `ʰ + U+0335 → ħ` と `ㇷ + ゚ → ㇷ゚` は `ccmp` が `rclt` より先に走るので、幅の計算は合字後の送り幅
  (ħ、ㇷ゚ のグリフ)で行う。
- **マークフィルタリング(旧版になかった修正)**: `rclt` の連鎖規則の先頭に `lookupflag UseMarkFilteringSet @CTX;`
  を置く。`@CTX` は「区切り文字・ヒント文字・声調グリフ(伸縮版含む)」の一覧。GDEF の Mark クラスに入っている
  それ以外のグリフ(半濁点 U+309A・下の点 U+0323・きしみ声 U+0330・合字前の U+0335)は、マーカー側の規則が
  文脈を走査する際に読み飛ばされる。これにより、たとえば「タ + 下の点 + ア + 声調」のように音節の途中に結合文字が
  挟まっても、マーカー経路(iOS)が既定位置に後退せず音節全体に伸びるようになった。
  **注意**: `@CTX` には声調グリフの**伸縮版**(`tone_*_w<W>`)も含める必要がある。含めないと、直前の音節で
  既に伸縮済みの声調グリフ自身が「読み飛ばされる Mark」になってしまい、次の音節の規則がその向こうの
  音節(1つ前)まで文脈を読みに行ってしまう(=音節をまたいだ位置漏れという新しい不具合になる。実装中に発見・修正)。

### 3.2 折れ線の形

| 項目 | 値(現行 `build-kana-multi-font.py`) |
|---|---|
| 高さ(レベル → y) | 1 → 1010、2 → 1130、3 → 1250、4 → 1370、5 → 1490(120刻み。現行 `TONE_Y`) |
| x の範囲(カナ1個の音節。単体グリフ) | -800 … -200。点が2個なら両端、3個なら両端と中央(-500) |
| x の範囲(音節が複数カナや修飾文字を含む場合) | 音節の中心 ±min(W − 200, 2400)/2(§3.1.2)。高さは変えず、幅だけ音節に合わせる |
| 線の太さ | 58(現行 `STROKE`) |
| 継ぎ目 | 折れ点は丸めずマイター接合。線分ごとの長方形を重ねる現行方式で足りる。折れ点の欠けが目立つ場合だけ、折れ点に円を足す |
| 終端 | 2個以上の並びは終点に小さな矢じり(`contour_glyph` が levels の長さで分岐)。レベル声調(1個)は矢じりなし |
| 基準ブラケット(stem) | 縦棒。**`x0`(その声調グリフ自身の左端)を基準に描く**(`stem(pen, x0)`)。旧版は `x0` を無視して
  固定座標に描いており、伸縮版で線の途中を貫く/線の外に浮く不具合があった(§8 未決事項の現状ノート参照) |

矢じりの有無・基準ブラケットの採否は、production が全155通りに一律で適用した見た目として本書に正式採用済み(§8-1・8-2)。

### 3.3 生成の自動化

- レベル列 `(a,)` `(a,b)` `(a,b,c)` から折れ線を作る関数 `contour_glyph(levels, x0, x1)`。
- 5 + 5^2 + 5^3 = 155 通りを `itertools.product` で列挙し、グリフ名 `tone_<levels>`(例 `tone_241`)を付ける。
- これに加えて**幅ごとの伸縮版**(`tone_<levels>_w<W>`)を、取り得る W の種類数だけ複製する(`width_combos()`)。
  上付き文字が3幅クラスに増えたぶん W の種類数も増え、155 × (取り得る W の数) の伸縮版グリフができる
  (旧版は 480 1クラスで 155×24 ≈ 3700 個、実測 25.7KB だった。3クラス化(境界のみ、代表値はクラス上限)の版は
  実測 21,070 グリフ・woff2 で 76,424 バイト。R1(§8 現状ノート・§3.1.3)で代表値を上限から実測平均に変えたところ、
  平均値が上限ほど切りのよい数でないぶん W の取り得る値の種類が増え、実測 26,495 グリフ・woff2 で 83,864 バイトに
  なった(グリフ名つきの検証用ビルドはこれよりさらに大きい。post format の違いのみ、§6 参照)。
  build 時間も alphabet が増えたぶん伸びる(実測 約5分。`kana-multi.woff2` は生成物としてコミットするので
  CI のビルド時間には影響しない))。
- §3.1.1 のマーカー・ヒント・声調グリフを文脈にした GSUB 規則を、同じ列挙から生成する(手書きしない)。
  マーカー側(`sequences()`)は「文脈=@F/@S1/@S2/@S3 の実際の並び」を列挙(nf≤5・上付き合計≤4・全長≤9で
  絞り込んでも1万件超、上付き文字を仮に5クラスにすると10万件近くに膨れる見積もりだったため、3クラスに
  留めた — §8-13 参照)。ヒント側(`hint_combos`)は「クラスごとの個数」の多重集合を列挙するだけなので、
  数百件に収まる(§3.1.3)。
- U+0300 系は、対応する並び(0304→3、0300→21、0302→51、0301→45、030C→14)への別名にする。cmap を同じグリフに向ける。

## 4. データモデル

`khmer-kana` の音節型に声調を足す。

```ts
type ToneLevels = string;                 // 例 "21", "45", "241"。1〜3桁、各桁 1–5
interface Syllable { /* 既存 */ tone?: ToneLevels }
```

- 内部表現は数字列(`"241"`)。カナ文字列への変換時に ˥…˩ に写す(`5→˥ … 1→˩`)。数字列にしておくのは、言語パッケージのテーブルを人が読みやすくするため。
- 詳細表記・ライト表記の両方で声調を出す(声調を落としたライト表記は、タイ語では意味が変わる)。
- 声調を持たない言語(クメール語)は `tone` を出さない。既存の golden テストは変えない。
- `tone` は音節に付き、描画では**音節全体**(§2.4。カナが複数あっても1音節)の末尾に出る。`ダア` のようにカナが
  2つの音節でも、声調線は音節全体(`ダア`)の幅に合わせて出る(§3.1.2 の GSUB 案で解決)。
- 描画層は、音節を構成するカナの個数 nF と、上付き文字を幅クラスごとに数えた個数(n1, n2, n3)を数え、§3.1.1 の
  マーカー・ヒントを文字列に組み込む。クラスの判定表は `kana-multi-tone.json`(§3.1.1)から読む。
  `khmer-kana` の `Syllable`(または `Word` 内の音節区切り)が、この個数を数える単位と一致している必要がある。
- 言語パッケージは音節ごとに `tone` を決めて渡す。タイ語の声調則(子音の類、声調記号、母音長、生音節/死音節)は `packages/kana-th`(仮)の仕事。

## 5. 文字列の扱い(環境の落とし穴)

- **正規化**: NFKC/NFKD は絶対にかけない(CLAUDE.md)。声調文字・区切り文字 U+E000・ヒント文字 U+2061-2064 は
  すべて ccc=0 なので NFC/NFD では並びは変わらないが、テストで確認する(§6)。
- **折り返し**: カナ(ID)と声調文字(AL 系)の間は、UAX #14 上、行末折り返しが可能になり得る。声調が次の行頭に離れるのを避けるため、
  音節ごとの span に `white-space: nowrap` を付ける(アプリ側の音節 span 分割と同じ場所)。
- **フォントの当たり方**: 声調文字・区切り文字・ヒント文字を含む要素には `kana-multi` を `font-family` の先頭に指定する。
  声調文字がフォールバックフォントに落ちると、送り幅 0 の前提が崩れ、カナの横に文字が出る。
- **区切り文字 U+E000 のフォールバック**: `kana-multi` が効かない環境では、私用領域の文字のため意味のあるグリフが
  無く、豆腐(□)として見える(§3.1.1 のトレードオフ。§8-9 で実機確認済み)。
- **フォールバック表示(フォント自体が効かない場合)**: `カ˨˩` のようにカナの横に声調文字が出る。読めるので実害は小さい
  (区切り文字を除く。上と合わせて次の一手で確認する)。
- **音節以外の直前**: 声調グリフの位置は、直前が §2.4 の音節(区切り文字 + カナ + 修飾文字 + ヒント)であることを前提にする。
  ラテン文字や空白の直後、修飾文字の間、1音節に声調が2つある並びは不正とし、検証で弾く。

## 6. テストと検証

| 層 | 内容 |
|---|---|
| フォント生成 | 155 個の全並びについて uharfbuzz でシェイプし、`カ + 並び` が「カ + 合成グリフ1個」になることを表明。未合成の並びが1つでもあればビルド失敗 |
| フォント生成 | §3.1.1 の符号(区切り + ヒント)を付けた音節(`カʰ`、`カㇰ`、`カʰㇰ`、複数カナの音節、複数音節の連続など、幅の全組み合わせ)に声調を付け、シェイプ後の声調グリフの中心 x が、音節全幅の中央(±2 単位)に来ることを表明。複数音節の連続で、位置調整が次の音節に漏れないことも表明 |
| フォント生成 | 各グリフの外接矩形が想定の x 範囲・y のレベル範囲に収まること。ゼロ幅であること |
| フォント生成 | 伸縮版の基準ブラケット(stem)の左端が、その声調グリフ自身の外接矩形の左端と一致すること(§3.2 の stem バグの再発防止) |
| フォント生成 | 下の点・きしみ声・半濁点(合字前)を音節の途中に挟んでも、マーカー経路(区切り文字のみ)で正しく伸縮版に一致すること(§3.1.3 のマークフィルタリングの検証) |
| ライブラリ | `tone` 数字列 ↔ 声調文字の往復、不正入力(4桁、0/6、空、音節以外の直前、修飾文字の間、声調の重複、nF/上付き合計の上限超過)の拒否、NFC/NFD で不変 |
| 目視(glyph-check) | 全並びを代表音節(ア、カ、カʰ、カㇰ、ダア、ストラʳᵊィ など)の上に並べた表を、iOS/Android で見る。**合否は目視**、自動判定は補助 |

これらのうち、フォント生成の5行は `tools/glyph-check/scripts/verify-kana-multi.py`(uharfbuzz ベース)で自動化
している。判定は「`contour_glyph` を同じ引数で呼び直して得た輪郭」と「実際にシェイプして得たグリフの輪郭」を
座標ごと突き合わせる方式(名前やグリフ数だけを見る弱い判定ではなく、実際の形そのものを比較する)。
`width_combos()` が列挙する全ての (nF, 幅クラス別の上付き数) の組み合わせについて、マーカー経路とヒント経路が
同じグリフを選ぶことも表明する。`spike/tone-font` の `verify-tone-spike.py`(このブランチには持ち込んでいなかった)
が実測 `x_advance` で中央を判定していたのに対し、統合時に同等の検証をリポジトリに残していなかったことが、
§3.2 の stem バグと §3.1.3 の幅クラスのバグ(どちらも Opus のレビューで見つかった)が素通りした直接の原因
だったため、`build-kana-multi-font.py` を変更するたびに実行すること。

## 9. 将来枠(今は実装しない)
