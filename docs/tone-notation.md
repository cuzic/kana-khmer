# 声調表記 設計書 (v0.1 ドラフト)

タイ語など声調のある言語を、カナ表記の上に折れ線(Chao 声調表記の形)を重ねて表す仕組みの設計。
方針は `docs/design.md` §3(フォント)と、多言語展開の合意(声調は「カナ上に折れ線」)に従う。
実装の土台は `tools/glyph-check/scripts/build-kana-multi-font.py`(現状は U+0300–030C の5種類の固定矢印のみ)。

## 1. 目的と非目的

**目的**
- 声調をカナの上に、**高さと動きが分かる折れ線**で出す。矢印1本では、高/上昇と低/下降の音域差が出ない。
- データ(文字列)は素の Unicode だけで持つ。フォントが当たらない環境でも意味が読める。
- 言語ごとの声調の数や形(タイ語5、ラオ語6、ミャンマー語4 …)を、フォントを作り直さずに表せる。

**非目的**
- 言語ごとの声調の決定(子音の類 × 声調記号 × 母音の長さ → 声調)。これは各言語パッケージの仕事で、本書は「決まった声調をどう表記・描画するか」だけを扱う。
- 声調の音声的な正確さの保証(Chao 値はネイティブ確認前は仮)。
- U+20D0–20FF の記号を声調に使うこと(§2.2 で却下)。

## 2. 符号化

### 2.1 声調文字の並び

声調は **IPA の声調文字(Modifier Letter Tone Bars)** を 1〜3 個並べたものとし、カナの直後に置く。

| 文字 | コードポイント | Chao レベル |
|---|---|---|
| ˥ | U+02E5 | 5(最高) |
| ˦ | U+02E6 | 4 |
| ˧ | U+02E7 | 3(中) |
| ˨ | U+02E8 | 2 |
| ˩ | U+02E9 | 1(最低) |

- 1個 = 平ら(レベル声調)。2個 = 始点→終点。3個 = 始点→中間点→終点(山型・谷型)。
- 声調文字は**モーラの末尾**に置く(§2.4)。例: `カ˨˩`、`カʰ˦˥`、`カㇰ˨˦˥`。
- 文法: `mora := kana modifier* tone?`、`tone := level{1,3}`、`level := [˥˦˧˨˩]`。4個以上は不正(検証でエラー)。
- 隣り合う同レベルの重複(˧˧)は許すが、正規形は1個(˧)。データ生成側は正規形で出す。

### 2.2 U+20D0–20FF を使わない理由(調査結果)

- 矢印・ハープーン・点・囲み記号で、高さ(音域)を表せるものがない。
- 結合クラス(ccc)が 230 / 220 / 1 / 0 に散らばる。NFC で並びが入れ替わり、`カ + U+20D7 + U+0323` が `カ + U+0323 + U+20D7` になる。ccc の違う記号を並べる合成規則は GSUB で拾えなくなる。
- フォントが当たらない環境で、意味の通らない記号(⃣ ⃠ など)が出る。

声調文字なら ccc=0、カテゴリ Sk で、NFC/NFD で並びが変わらない。フォントが無くても `˨˩` として読める。
U+20D0 ブロックは、声調以外の修飾(§9 の将来枠)に取っておく。

### 2.3 既存の U+0300–030C との関係

既存の 5 声調(U+0304 中 / 0300 低 / 0302 下降 / 0301 高 / 030C 上昇)は残す。**ショートカット別名**として扱い、
`カ + U+0301` は `カ + ˦˥` と同じ折れ線を出す(グリフは共有)。新規データは声調文字で書き、U+0300 系は書かない。

### 2.4 モーラの定義(声調が乗る単位)

声調は、モーラ全体の真上に描く。フォントは「モーラ」を知らないので、並びの形で定義する。

- **モーラ** = カナ1文字(U+30A0–30FF)+ 修飾文字 0個以上 + 声調文字 0〜3個。次のカナが来たら別のモーラ。
- **修飾文字** = 右肩の上付き文字(ʰ ʱ ʲ ʷ ⁿ ˣ ˠ ʶ ˀ ˤ 𐞥 ʳ ˡ ᵓ ᵊ ᵋ ᵅ ᶤ、ħ の合字)、半濁点 U+309A、語末の小さい子音カナ(ㇰ…ㇿ)。
- 声調は必ずモーラの末尾(修飾文字の後)に置く。修飾文字の間や、カナの直前には置かない。
- 声調線の中心は、**カナ+修飾文字の全幅の中央**にそろえる。1モーラに声調は1つだけ。

## 3. 描画(フォント)

### 3.1 全体方式

`kana-multi.woff2`(カナと全記号を1フォントに収める。Android は基底と結合文字が別フォントだと欠字にするため)に、
次の3つを入れる。

1. **cmap**: ˥˦˧˨˩ の各文字に、レベル声調のグリフ(短い水平線)を割り当てる。送り幅は 0。
2. **合成グリフ**: 2個・3個の並びごとに、折れ線グリフを1つ作る(25 + 125 = 150 個)。送り幅は 0。
3. **GSUB `liga`**: 並びを合成グリフに置換する。長い並びを先に書く(3個 → 2個)。1個は cmap のままで規則なし。

グリフの輪郭はカナの上(x = -800…-200、送り幅 1000 のセルの真上)に描いておく。送り幅が 0 なので、直前の1000幅の上に重なる。
これは現行の `arrow_glyph`(x = -800…-200)と同じ作りで、座標系を変えない。

### 3.1.1 モーラ全体への位置合わせ(GPOS)

修飾文字が付くと、声調グリフのペン位置がカナの右端から W(= カナ+修飾文字の送り幅の合計)へずれる。
輪郭を描き直さず、**GPOS の文脈つき単一位置調整**で声調グリフを左へ `dx = -(W - 1000) / 2` だけ動かし、モーラ全幅の中央に置く。

- 修飾文字のグリフを送り幅ごとに**幅クラス**にまとめる(50 単位刻み程度。上付き文字は約 350〜400、小さい子音カナは 1000 など)。
- 規則は「カナ + 修飾文字の幅クラス列 + 声調グリフ」の連鎖(chaining contextual pos)。後ろに付く修飾は数個までなので、クラス列の組み合わせを列挙して自動生成する。
- 幅の合計が同じ組み合わせは、同じ `dx` の lookup に集約する(lookup の数は、取り得る W の種類数)。
- 修飾文字が付かない(W = 1000)場合は `dx = 0` で、規則は不要。
- 折れ線グリフは 150 個のまま増やさない。位置だけを動かす。
- 合字 `ʰ + U+0335 → ħ` と `ㇷ + ゚ → ㇷ゚` は GSUB が先に走るので、GPOS は合字後の送り幅(ħ、ㇷ゚ のグリフ)で計算する。

### 3.2 折れ線の形

| 項目 | 値(初期案。glyph-check で調整) |
|---|---|
| 高さ(レベル → y) | 1 → 1000、2 → 1115、3 → 1230、4 → 1345、5 → 1460(現行 `TONE_Y`) |
| x の範囲 | -800 … -200。点が2個なら両端、3個なら両端と中央(-500) |
| 線の太さ | 58(現行 `STROKE`) |
| 継ぎ目 | 折れ点は丸めずマイター接合。線分ごとの長方形を重ねる現行方式で足りる。折れ点の欠けが目立つ場合だけ、折れ点に円を足す |
| 終端 | 2個以上の並びは終点に小さな矢じり(現行 `arrow_glyph` 流用)。レベル声調(1個)は矢じりなし |

矢じりの有無、基準線(薄い水平線)の要否は、見た目の判断事項なので glyph-check で見比べて決める(§8)。

### 3.3 生成の自動化

`TONES` テーブル(固定5種)を、次のように一般化する。

- レベル列 `(a,)` `(a,b)` `(a,b,c)` から折れ線を作る関数 `contour_glyph(levels)`。
- 5^2 + 5^3 通りを `itertools.product` で列挙し、グリフ名 `tone_<levels>`(例 `tone_241`)を付ける。
- GSUB の規則文字列を同じ列挙から生成する(手書きしない)。
- U+0300 系は、対応する並び(0304→33、0300→21、0302→51、0301→45、030C→14)への別名にする。cmap を同じグリフに向ける。

グリフ数は現状から約 150 増える。woff2 で数 KB の増加の見込み。

## 4. データモデル

`khmer-kana` の音節型に声調を足す。

```ts
type ToneLevels = string;                 // 例 "21", "45", "241"。1〜3桁、各桁 1–5
interface Syllable { /* 既存 */ tone?: ToneLevels }
```

- 内部表現は数字列(`"241"`)。カナ文字列への変換時に ˥…˩ に写す(`5→˥ … 1→˩`)。数字列にしておくのは、言語パッケージのテーブルを人が読みやすくするため。
- 詳細表記・ライト表記の両方で声調を出す(声調を落としたライト表記は、タイ語では意味が変わる)。
- 声調を持たない言語(クメール語)は `tone` を出さない。既存の golden テストは変えない。
- `tone` は音節に付き、描画では**音節の最後のモーラ**の末尾に出る(§2.4 の「モーラ」= カナ1文字の単位)。`ダア` のようにカナが2つの音節では、声調線は最後のカナの上に乗る。音節全体にまたがる線は §8 の未決事項。
- 言語パッケージは音節ごとに `tone` を決めて渡す。タイ語の声調則(子音の類、声調記号、母音長、生音節/死音節)は `packages/kana-th`(仮)の仕事。

## 5. 文字列の扱い(環境の落とし穴)

- **正規化**: NFKC/NFKD は絶対にかけない(CLAUDE.md)。声調文字は ccc=0 なので NFC/NFD では並びは変わらないが、テストで確認する。
- **折り返し**: カナ(ID)と声調文字(AL 系)の間は、UAX #14 上、行末折り返しが可能になり得る。声調が次の行頭に離れるのを避けるため、
  音節ごとの span に `white-space: nowrap` を付ける(アプリ側の音節 span 分割と同じ場所)。
- **フォントの当たり方**: 声調文字を含む要素には `kana-multi` を `font-family` の先頭に指定する。
  声調文字がフォールバックフォントに落ちると、送り幅 0 の前提が崩れ、カナの横に文字が出る。
- **フォールバック表示**: フォントが効かなければ `カ˨˩` のようにカナの横に声調文字が出る。読めるので実害は小さい(許容する)。
- **モーラ以外の直前**: 声調グリフの位置は、直前が §2.4 のモーラ(カナ + 修飾文字)であることを前提にする。ラテン文字や空白の直後、
  修飾文字の間、1モーラに声調が2つある並びは不正とし、検証で弾く。

## 6. テストと検証

| 層 | 内容 |
|---|---|
| フォント生成 | 150 個の全並びについて uharfbuzz でシェイプし、`カ + 並び` が「カ + 合成グリフ1個」(グリフ数 2)になることを表明。未合成の並びが1つでもあればビルド失敗 |
| フォント生成 | 修飾文字を付けたモーラ(`カʰ`、`カㇰ`、`カʰㇰ`、`ㇷ゚`、ħ の合字など、幅クラスの全組み合わせ)に声調を付け、シェイプ後の声調グリフの中心 x が、モーラ全幅の中央(±30 単位)に来ることを表明 |
| フォント生成 | 各グリフの外接矩形が x = -800…-200、y が想定のレベル範囲に収まること。ゼロ幅であること |
| ライブラリ | `tone` 数字列 ↔ 声調文字の往復、不正入力(4桁、0/6、空、モーラ以外の直前、修飾文字の間、声調の重複)の拒否、NFC/NFD で不変 |
| 目視(glyph-check) | 全 150 並びを代表モーラ(ア、カ、カʰ、カㇰ、カʰㇰ、ㇷ゚付き、濁点付き)の上に並べた表を、iOS/Android で見る。**合否は目視**、自動判定は補助 |

## 7. タイ語の声調(叩き台。ネイティブ確認前)

| 声調 | Chao(バンコク標準の代表値) | 表記 |
|---|---|---|
| 中(สามัญ) | 33 | ˧ |
| 低(เอก) | 21 | ˨˩ |
| 下降(โท) | 241 | ˨˦˩ |
| 高(ตรี) | 45 | ˦˥ |
| 上昇(จัตวา) | 315 または 24 | ˧˩˥ / ˨˦ |

- 下降・上昇の形は文献で揺れる。旅行者向けには単純な形(下降 `˥˩`、上昇 `˨˦`)に丸める案もある。要確認で、§8 の決定事項に含める。
- 3個の並びが要るのは、山型・谷型を厳密に出すときだけ。丸める方針なら 2個までで足り、150 個が 30 個に減る。

## 8. 未決事項

1. 折れ線に矢じりを付けるか(向きが分かる)、付けないか(Chao 声調文字に近い)。glyph-check で両方を見比べて決める。
2. 基準線(薄い水平線)を出すか。声調の高さの読み取りやすさと、画面の煩雑さのトレードオフ。
3. タイ語の下降・上昇を厳密な3点形にするか、丸めるか(§7)。丸めるなら 3個の並びを作らない。
4. 声調の色分け(高い声調を暖色など)を併用するか。色覚差の配慮が要る。
5. 声調文字がカナの横に出るフォールバックを許すか、フォント読み込み前は声調を隠す(`font-display` と `unicode-range` の扱い)か。
6. カナが複数の音節(`ダア` など)で、声調線を最後のカナの上に置くか、音節全体にまたがせるか。またがせるなら、モーラの定義(§2.4)を「音節」に広げ、幅クラスの連鎖を伸ばす必要がある。
7. ネイティブ話者による声調値の確認方法と時期。

## 9. 将来枠(今は実装しない)

声調以外の音韻的な修飾(短母音、入破音、タイ語の死音節など)に、U+20D0 ブロックの ccc=230 の記号
(U+20DB 三点など)を割り当てる余地を残す。声調文字の並びとは干渉しない(別のコードポイント・別の GSUB 機能)。
割り当てる際は、ccc をそろえる規則(§2.2)を守る。

## 10. 実装の順序

1. `build-kana-multi-font.py` を一般化(`contour_glyph`、150 並びの生成、GSUB の自動生成、U+0300 系の別名化、§3.1.1 の GPOS 位置調整)。
2. フォント生成時のシェイプ検証(uharfbuzz)を追加。
3. glyph-check に全並びの一覧ページを追加し、iOS/Android で目視。§8 の 1〜3 を決める。
4. `khmer-kana` に `tone` フィールドと変換・検証を追加(テスト先行)。
5. `apps/web` の音節 span に nowrap と声調表示を足す。
6. タイ語パッケージは、本書の範囲外。声調則とネイティブ確認の後に別の設計書で扱う。
