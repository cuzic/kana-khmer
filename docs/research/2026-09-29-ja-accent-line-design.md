## 0. 結論(先に)

- **推奨**: 線の単位は**拍(モーラ)**、表現は**上線方式(A)**(高い拍の上に線、下がり目で下に折れる。Wiktionary・OJAD 式)、
  実装は**フォントではなく DOM/CSS**(生成器が拍に対応する可視スロットごとに span を出し、`border-top` で線を描く)。
  ADR-0007/0008 の Chao 声調バー+GSUB 伸縮は ja-khmer には使わない。
- 決め手は実測した2点。(1) クメール文字の書記音節は拍と一対一でなく、**語頭の1拍目と2拍目の間(東京式で必ず高さが変わる境目)が
  同じ書記音節に入る語が JMdict 共通語の 41.7%(訂正: 再測定 41.8%。「必ず高さが変わる」は誤り。冒頭の訂正注記)**(§2.2)。(2) クメール文字の書記音節の幅は可変で、ADR-0008 の
  「全角カナの数+上付き幅クラス」の幅ヒントが使えない(§2.4)。
- Wiktionary のデータは、**旅行フレーズ40件の語彙 48 語すべてで東京式の型が取れた**が、9 語は見出し語の解決(漢字見出しなど)が要り、
  40 フレーズのうち 10 は活用形で辞書形の型が使えない(§3.3)。「Wiktionary を種にして人が確認する」を推奨(§4.3)。
- 決められない点は §5.2。ADR 番号は **0018・0019 が既に使われているので次の空きは 0020**(§6)。

### 1.2 旅行者に本当に必要な粒度

**提案(判断材料であって検証済みの事実ではない)**: **句単位の連続線**。理由は次のとおり。

- 旅行者が使うのは語の辞書的な対立(橋/箸のような最小対)より、フレーズを自然な抑揚で言うこと。語単位の型番号だけを
  出しても、助詞・です・ますが付いた形の高さが読み取れない(平板と尾高の区別は助詞の高さでしか見えない)。
- 句単位にすると、語単位の型は「句の核の位置 n」に統一され、表示・データとも1種類で済む(§4)。
- ただし語単位のデータ(Wiktionary)を句に変換する規則が要る(§4)。

どこまで必要かは学習目的(抑揚を真似させたいのか、語の弁別を教えたいのか)で変わり、ユーザー判断(§5.2 Q1)。
D5 の「衝突率で記号を付けるか決める」測り方をアクセントに当てるには、同じかな読みで型だけが違う語の割合が要るが、
JMdict にはアクセントが無く、Wiktionary で測るにはダンプ全体の抽出が要る。**未測定**。

## 2. 線の表現案の比較

### 2.1 前提: 拍・書記音節・可視スロット

設計書の変換(`convert-spec.mjs`)では、**書記音節は拍と一対一にならない**(コード確認)。

- 長音 ー は直前の書記音節に入り、右肩の長音マーカー(ᵒ̄ など)になる(2拍が1書記音節)。
- 撥音 ン・促音 ッ は直前の書記音節の末子音になる(直前に末子音があるとき ッ は落ちる)。
- 連母音 あい は ៃ 1つになる(2拍が1つの字。分割できない唯一の型)。
- 語頭の ン など、直前に書記音節が無い場合だけ単独の書記音節になる。

ただし**目に見えるスロットに分けると、ほぼ拍と対応する**: 基底の書記音節(頭子音+母音)、末子音(ន ក ប ត)、右肩の長音マーカー。
分割できないのは あい=ៃ だけ。例外として、長音+撥音(カーン)は生成順が「基底 → 末子音 ន → 長音マーカー」で、
時間順(ー → ン)と逆になる(設計書 §8 #8「長音マーカーを末子音の前後どちらに置くか」が未決なので、この対応は決まらない)。

### 2.2 実測: 書記音節の中で高さが変わる語の割合

方法: JMdict 共通語(jmdict-simplified 3.6.2+20260928191014)の読みを `tools/ja-khmer-spike/src/vocab.mjs` の `toPron` で発音風カタカナにし、
`convert-spec.mjs` と同じ規則で拍を書記音節にまとめた(重複を除いた 21,694 形。設計書の「範囲内 21,680 語」にほぼ一致)。
計測スクリプトは scratchpad に置いて削除した(再現は規則の記述のとおり。`convert-spec.mjs` の畳み込みを拍の添字つきで書き直せばよい。
なお `ROW_V` の a 行に だ が無い不具合があり、下記の数値は だ を a 行に足して測った。§7)。

| 指標 | 値 |
|---|---|
| 2拍以上の語のうち、1拍目と2拍目が同じ書記音節に入る語(旧測定 9,030 = 41.7%。`accent-cluster.mjs` での再測定値。差の 20 語の理由は未調査) | 9,050 / 21,633 = **41.8%** |
| 全ての拍の境目のうち、書記音節の内側にあるもの | 20,792 / 65,878 = **31.6%** |
| 長音・撥音・促音・あい のいずれかで書記音節が拍より少ない語 | 14,151 / 21,694 = 65.2% |

**(訂正)** この 41.8% は「語頭の高さの変化が書記音節の内側に落ちる語」の割合ではなく、「語頭が重い音節の語」の割合である(2拍目が特殊拍のときは語頭の上昇が弱いか無いことが多い。一般知識、文献未照合)。拍単位の根拠は、核が書記音節の内側に落ちる候補の 39.2% と、Wiktionary 実データの 8/17 語(冒頭の訂正注記、ADR-0021)。以下の旧記述は調査時点のまま:

1拍目と2拍目の高さは(一般知識として)必ず違うので、**41.7% の語は語頭の高さの変化が書記音節の内側に落ちる**。
書記音節単位で線を引くと、語頭の上昇(L→H)か下降(H→L)が表せない。

実データでの確認(Wiktionary の型 acc を持つ実在語 23 語、拍→書記音節の対応と、型から導いた H/L):
書記音節の中で H と L が混ざる語は **23 語中 10 語**(ニホンジン acc4: `L|HH|HL`、ゴメンナサイ 5、スミマセン 4、ダイジョーブ 3: `LH|HL|L`、
ゲンキ 1: `HL|L`、ユックリ 3、ベンキョー 0、クダサイ 3、オヤスミナサイ 6、ヨーコソ 1)。このうち語頭の書記音節が混ざるのが 5 語。
サンプルが小さく、選び方も偏っているので割合の推定には使えない(存在の確認のみ)。

### 2.4 フォント方式(ADR-0008 の拡張)がクメール文字で難しい理由

実測・コード確認による。

- ADR-0008 の幅ヒントは「全角カナの数」と「上付き文字の幅クラス」で音節幅を数える。クメール文字の**送り幅は書記音節ごとに大きく違う**。
  Noto Sans Khmer(UPM 1000)の HarfBuzz シェイプ結果: ក 636、ហ 928、ឈ 1251、កា 924、ហ្កា 1216、ក្រៅ 1499。
  下付き子音・母音記号(ា など)・前置母音の並べ替えで変わるので、数える単位が作れない。
- 生成器の出力は閉じた集合(対応表 103 行)なので、書記音節ごとの幅を列挙して GSUB を作ることは原理的には可能。ただし
  個数(103 行 × 長短 × 末子音 × 右肩の組み合わせ)は**未測定**で、Khmer のシェイパ(USE)が Common 文字の声調文字を
  書記音節の後ろでどう扱うか、文脈規則が母音記号などの Mark を読み飛ばせるか(ADR-0008 の `UseMarkFilteringSet` と同じ扱い)は**未確認**。
- ADR-0008 の区切り U+E000+幅ヒントの二重符号化は、Android がスクリプトの変わり目でシェイピングを分けるための対策だった。
  クメール文字→ラテン上付き(右肩)の変わり目でも同じことが起きる見込みだが、**未確認**。
- ADR-0007 の Chao 5段は H/L の2段に対して過剰(ADR-0010 決定6 の指摘どおり)。使うなら ˥˩ などの2レベルに限る設計になる。
- 声調線の高さ: `build-kana-multi-font.py` の `TONE_Y`(レベル1=1010、STROKE=58)。Noto Sans Khmer(実測)の最大の高さは、
  ឹ 930、ំ 910、ី 903、៉ ់ ិ 879、基底の子音 586。y=1010 の線の下端は約 981 で、この字体では約 50 ユニット空く。
  iOS・Android のシステムのクメール文字フォントでは**未測定**。

### 2.5 CSS だけで描く案(実測できた範囲)

デスクトップ Chrome(google-chrome headless、Noto Sans Khmer と `ja-khmer.woff2` を `glyph-check/public` から読む)で、
設計書の変換(`convert-spec.mjs`)の出力(ニホンジン・アリガトー・ゴメンナサイ・スミマセン・ダイジョーブ・ラーメン・ユックリ・オハヨー)を
書記音節・末子音・長音マーカーごとの `display:inline-block` の span に分け、H の span に `border-top`、下がり目の span に `border-right` を付けて
スクリーンショットで目視した。

```css
.u { display:inline-block; border-top:3px solid transparent; padding-top:2px; }
.u.h { border-top-color:currentColor; }
.u.d { border-right:3px solid currentColor; }   /* 下がり目 */
```

結果: 線は span の上端で連続した直線になり、前置母音(េ ែ ៃ)・上母音(ី ឹ)・◌៉・右肩の ᵒ̄ と重ならず、span 間に隙間は出なかった。
書記音節の高さに関係なく線の高さが一定なので、輪郭が途切れず読める。**この確認はデスクトップ Chrome のみ**で、iOS(WebKit)・Android 10/14 は未確認、
スクリーンショットは保存していない(scratchpad ごと削除)。`glyph-check` で再作成すること(§5.3)。

| CSS 案 | 可否 | 注意点 |
|---|---|---|
| `border-top` を inline-block の span に | 上の試作で動作 | ADR-0003 により、結合文字は基底と同じ span に入れる。長音マーカー(上付き母音+U+0304)は1つの span にまとめる。span の分割は書記音節・末子音・マーカーの境目だけにし、前置母音と子音の間では切らない。inline-block は行分割の単位になるので、句は `white-space:nowrap`(ADR-0010 決定3 の nowrap と同じ) |
| あい=ៃ(分割不能)の途中で高さが変わる | 半幅の線を `linear-gradient` の背景で描く案 | 未試作 |
| SVG を重ねる(JS で各 span の `getBoundingClientRect` を測り、折れ線を描く) | 可。任意の位置(書記音節の内側)に折れ線を描ける | JS が要る。フォント読み込み後・リサイズ後の再計測が要る。古い Android では `?.` `??` を使わない(ADR-0016) |
| `<ruby>`+ `<rt>` に線 | **未試作・未確認** | rt の幅が親の幅になるか、行の高さが増えるか、読み上げ・コピーに rt が混ざるか。旨味が小さいので比較対象に留める |
| 下がり目の縦線 | `border-right` で可 | 折れ線の斜めの下降にはならず、直角の段になる(Module:ja-pron と同じ) |

コピー・検索・読み上げ: DOM の span を分けても文字列は連結すれば元のクメール文字と同じなので、コピー・読み上げの影響は小さいと見込む(**未確認**)。
線そのものはコピーされない。

## 3. Wiktionary のデータ取り込みの現実性

### 3.1 `{{ja-pron}}` のアクセント指定の構造(Module:ja-pron のソースと実データで確認)

| 項目 | 内容 |
|---|---|
| 値 | 整数 n(第n拍の後で下がる。0=平板)、`h`(=0)、`a`(=1)、`o`(=語末拍=尾高)、`p`(助詞。値なし扱い)。範囲外の n はエラー |
| 複数値 | `acc` `acc2` …(別の型)。それぞれに `accN_loc`(地域)・`accN_ref`(出典コード)・`accN_note`(注記)が付く |
| 地域 | `acc_loc` が無ければ東京として扱われる(ソース実測: `al_is_tokyo_default`)。地域つきの値は別方言。例: ありがとう は `acc=2`(DJR)と `acc=3|acc_loc=Aichi` が別の行にある |
| `only_show_acc` | 発音(IPA)の行を出さず、アクセントだけを出す行。ありがとう は `{{ja-pron}}` の行と `only_show_acc=true|acc=2` の行に分かれていて、型は後者にしかない |
| 語の分割 | `acc=前部 + 後部 n+m` の形で、複合語を複数の部分に分ける(「+」で分割。Module は複合アクセント `complex` として扱う)。例(実データ): ありがとう ございます は `acc2=ありがとう + ございます 2+4`(注記 careful speech)、どう致しまして は `acc=どう+いたしまして 1+4` |
| 読みの違い | 見出し語に読みが複数ある場合は別のテンプレートに分かれる。例: 日本 は にほん(acc=2)、にっぽん(acc=3)、じっぽん(acc=3) |
| その他 | `dev=`(無声化する拍)、`respelling`(かな綴りの上書き)、`>>`(シフト後の型) |

抽出は、ダンプまたは API の生のウィキテキストから `{{ja-pron` の入れ子を含む波括弧を数えて分解し、`Japanese` 見出しの節に限る必要がある
(第1段落の正規表現だと `acc_loc={{w|Tokyo dialect|Tokyo}}` の入れ子で途切れる。本調査の抽出では実際に起きた)。

### 3.2 カバレッジ

- カテゴリ件数(実測、2026-09-29、API `prop=categoryinfo`): 日本語の見出し語(lemmas) 127,295、IPA 発音あり 59,712、うちアクセントあり 44,898・欠落 15,853。
  **44,898 / 59,712 = 75.2%、44,898 / 127,295 = 35.3%**(ADR-0010 の「約75%・約35%」を再確認)。
- 旅行フレーズでの割合: §3.3。

### 3.3 旅行フレーズ語彙での実測

対象: `packages/content/data/phrases.yaml` の日本語 `ja` 40 件(旅行フレーズの proxy)。**注意**: この `ja` は日本人向けアプリの日本語訳であり、
ja-khmer 用のフレーズ集は未確定(ADR-0010 結果「既存データの `ja` に足す案と比較」)。この語彙は基本語が中心で、駅名・メニュー・数詞などを含まないので、
実際の割合はこれより低いはず(**未測定**)。

方法: 40 件を手で語(見出し語)に分け(助詞・です・か・接辞の活用語尾は除く)48 語を得た。英語版 Wiktionary の API(`action=query&prop=revisions`、
3 回 × 最大 20〜50 見出し語、間に 2 秒空けた)から生のウィキテキストを取り、`Japanese` 節の `ja-pron` を分解して、東京式(`acc_loc` なし)の型の有無を調べた。

| 結果 | 語数 |
|---|---|
| 48 語のうち、東京式の型(`acc`)が取れた | **48 / 48**(見出し語を人が解決したあと) |
| うち、かな見出しのページではそのまま取れず、別の見出しへの解決が要った | 9(こんにちは→今日は(`こんにちわ` acc=5)、はじめまして→初めまして(4)、おやすみなさい→お休みなさい(`acc=6, acc2=0`)、どういたしまして→どう致しまして(`1+4`)、ください→下さい(3)、お兄さん・お姉さん(兄さん・姉さん のページは無い)、おじさん→叔父さん、おばさん→伯母さん(意味が違う可能性あり)) |
| 構造の揺れ(複数値・地域・only_show_acc・「+」分割)を処理する必要があった | 9 語以上(さようなら acc=4/5、来る、する、ちょっと、お休みなさい、ありがとう、ありがとうございます、いくら、どう致しまして)。読みが複数(日本 にほん/にっぽん、日本人)は別に 2 語 |

つまり、**基本語の範囲では型は取れるが、見出しの表記が漢字かかなか、読みがどれか、を人が決める必要がある**。フレーズ側に見出し語の表記(漢字かな混じり)を持たせるか、
別に対応表を持つ必要がある(`phrases.yaml` の `ja` は表記がまちまち: `元気`・`大丈夫` は漢字、`ありがとう` はかな)。

もう1つの制約: **辞書形の型しか無い**。フレーズ 40 件のうち 10 件(24 来ました、26 勉強しています、28 来ました、29 わかりません、30 わかりました、31 言ってください、
32 話してください、34 高すぎます、38 助けてください、39 待ってください)は活用した形を含み、Wiktionary の見出し語の型(来る 1、わかる 2、言う 0、話す 2、高い 2、助ける 3、待つ 1)から
活用形の型は導けない(活用による核の移動規則は本調査で検証していない)。ます・です・ください の型も同様。

### 3.4 CC BY-SA の扱い(規約の事実。法的助言ではない)

- サイトの権利表示(実測、API `siprop=rightsinfo`): Creative Commons Attribution-Share Alike 4.0。
- (既存文書。本調査で再取得せず) Wikimedia Terms of Use §7: 帰属は、(1)記事へのハイパーリンクまたは URL、(2)適合する安定した公開コピーへのリンク、(3)著者一覧の
  いずれか。改変・追加した内容は CC BY-SA 4.0 以降で提供。寄稿者はデータベース権を放棄し、寄稿された「事実」は帰属なしで再利用してよいとされる。
  事実(この語の型は 0)と、編集された文章・表現の区別が取り込み方の判断に関わるが、**その適用は法的判断で、本調査では判断しない**。
- 実務の論点として: 各データに見出し語の URL と取得日(ダンプの日付・改訂の識別子)を付ける、アクセントのデータファイルは他のコードと**別のファイル・別のライセンス表記**にして
  継承の範囲を絞る、が挙げられる(設計上の提案)。`acc_ref` の辞書(DJR・NHK など)の著作権は Wiktionary のライセンスとは別で、その本文は取り込まない。
- リポジトリのルートに LICENSE ファイルは無い(実測)。全体のライセンス方針がまず要る。

## 4. 助詞・語の連続(アクセント句)での実現

### 4.1 拍ごとの高さの決め方

句の核の位置を n(0..N、N は句の拍数)とすると、Module:ja-pron の描画と同じ規則で次のとおり(ソース実測):

- n=0(平板): 1拍目 L、2拍目以降 H(句末まで。後続の助詞も H)
- n=1(頭高): 1拍目 H、以降 L
- n≥2: 1拍目 L、2〜n拍目 H、n+1拍目以降 L

### 4.2 最小の規則(設計書が採る案)

- **R0(入力)**: アクセント句は空白で区切る(設計書 §2 の既存の書式 `utterance = phrase { " " phrase }` を使う)。句ごとに核の位置 n を持たせる(整数、0=平板)。
  データ側で人が書く(ADR-0010 決定2)。
- **R1(句内の高さ)**: §4.1 のとおり。線は句ごとに引き、句の境目で切る(句をまたいだ連続線にしない)。
- **R2(名詞・代名詞・副詞+助詞・だ・です)**: 句の型は、語の型と同じ n を使う。助詞・です は無アクセントで、n=0 なら H のまま続き、n≥1 なら核より後は L。
  平板と尾高は語だけでは同じで、助詞・です の高さで区別される(R1 が自動的にそうなる)。
  Wiktionary の型から句の型を機械的に作れるのはこの R2 の範囲だけ。
- **R3(範囲外。人が句ごとに与える)**: 動詞・形容詞の活用形、ます・です・ください・て形の付き方、複合語(Wiktionary の「+」分割は語ごとに
  別の句として扱う手がかりになる。どう致しまして=`1+4` は2句)、感動詞・慣用句。Wiktionary が複数の型(`acc2`)を持つ語は、人が選ぶ。

助詞でアクセントが動く例外など、上の R2 に当てはまらない例が旅行フレーズにあるかは**未検証**(R3 の人手確認が前提)。

### 4.3 データ作成の流れ(提案)

1. フレーズを句に分け、各句の主要語の見出し語・読み(漢字表記)を人が決める。
2. 抽出スクリプトが Wiktionary から型の候補(東京式)を出す。R2 の範囲なら句の n の初期値にする。
3. 人が確認し、確認済みフラグを付ける。活用形・R3 の語は人が書く。確認できない句は線を出さない(推測で線を出さない)。
4. 表示: 確認済みのデータだけに線を出す。未確認は線なしで、UI 上は「アクセント未確認」を出さない(ノイズになるため)。

## 5. 推奨案・決められない点・確認方法

### 5.1 推奨案(1つ)

**拍単位の上線(A)を、DOM/CSS で描く。** ADR-0007/0008 の声調バー・GSUB 伸縮は ja-khmer に適用しない。

- 表現: H の拍の上に線を引き、L の拍には引かない(H のみ)。下がり目は線の右端の縦の段(`border-right`。Wiktionary 式)。平板は線が句末まで続き、
  尾高は句末(または最後の助詞の直前)で下がる。
- 単位: クメール文字の行では可視スロット(書記音節・末子音・長音マーカー)。あい=ៃ は半幅の線。
- 同じ規則をかなの行(併記、ADR-0010 決定5)にも出せる(拍が1文字なので簡単)。かな行は補助で、必須ではない。
- ライトへの残し方(ADR-0010 決定3)は、アクセント衝突率を測れるまで**詳細・ライトとも残す**とする(暫定。ADR に暫定と書く)。
- 却下の理由の要約: (B) は情報が足りず、読み方の説明が要る。(C) は書記音節単位で、語頭が重い音節の語 41.8% の書記音節内の変化と句をまたぐ連続線が表せず、フォント作業が最大。
  (D) は有効だが、クメール語話者の主行にならない(併記の補助として (A) と併用できる)。

### 5.2 決められない点(ユーザーへの問い)

- Q1. **線の目的**: 自然な抑揚を真似させたい(句単位・H のみでよい)か、語のアクセントの弁別を教えたい(語単位の型番号も見せる)か。
- Q2. **L も線で示すか**: H のみ(OJAD 式)か、H を上の線・L を下の線でつないだ2段の折れ線か。後者は「H/L の2段」という方針に忠実だが、縦の高さが増える(§5.3 で比べる)。
- Q3. **かな行にも線を出すか**、クメール文字行だけか。出す場合、どちらが主か。
- Q4. **データの出所と責任**: Wiktionary を種にして人が確認する(推奨)でよいか。確認できる人(日本語話者)が誰か。CC BY-SA の継承をアクセントデータのファイルに限る方針でよいか。
  リポジトリ全体のライセンス方針(現状 LICENSE 無し)。
- Q5. **フレーズ集の範囲**: 活用形(来ました・高すぎます)を含むフレーズが 40 件中 10 件ある。活用形の型を人が全て書くか、R2 の範囲(名詞+助詞)だけ線を出すか。
- Q6. **長音+撥音の並び**(設計書 §8 #8)が決まるまで、可視スロットとの対応が決まらない。設計書側の決定が先。

### 5.3 glyph-check で見比べる候補と確認方法

同じ語を1ページに並べる(`tools/glyph-check/public/ja-khmer.html` と同じ形式。合否は目視、自動判定は補助 ─ ADR-0004)。

| 候補 | 内容 |
|---|---|
| V1 | CSS inline-block+`border-top`(H のみ)+`border-right`(下がり目)。クメール文字行 |
| V2 | 2段の折れ線(H を上の線、L を下の線、境目で縦につなぐ)。CSS の `background` グラデーション、または SVG 重ね |
| V3 | SVG 重ね(JS が span の位置を測る)。書記音節の内側の位置を出せるか確認 |
| V4 | (B) ꜜ のみ(U+A71C。ja-khmer 用フォントに同梱した場合と、無い場合のフォールバック) |
| V5 | (D) かな行に V1 と同じ線 |
| V6 | (C) 文字列に ˥˩ を後置(フォールバックの見え方を見るための対照) |
| V7(任意) | フォント方式(§2.4)。V1〜V3 が実機で崩れたときだけ試作する |

テスト語: 書記音節の内側で高さが変わる語(ニホンジン 4、ダイジョーブ 3(ROW_V の修正後は ダイ が ៃ 1つになり、あい=ៃ の半幅の線の試験になる)、ゲンキ 1、ユックリ 3、ベンキョー 0、
ヨーコソ 1)、平板/尾高の区別(句+助詞)、句の境目(2句のフレーズ)、長い句。
環境: 既存の CI と同じ iOS シミュレータ、Android 14、Android 10(API 29)、それぞれ「sys(同梱フォント無し)」と「同梱フォント」の2行。
確認項目: (1) 線が連続で高さが一定、(2) 母音記号・◌៉◌៊・右肩・長音マーカーと重ならない(最も高い記号の直上に線が来るか)、(3) span 間に隙間や行分割が無い、
(4) 長音+撥音の並びでの位置、(5) ダークモード、(6) コピーしたときの文字列、(7) `?.`・`??` を使っていないこと(ADR-0016)。
自動判定の補助: 各 span の `getBoundingClientRect().top` が同じ句内で一致すること、tofu 検出。

## 6. 新しい ADR に書くべき決定の骨子

番号は **ADR-0020**(0018・0019 は既存で使用済み。依頼文の「0018 相当」は次の空き番号の意味と解した)。

- **コンテキスト**: ADR-0010 決定6 が未決とした「線を載せる対象(クメール文字行/かな行/ꜜ)」の決着。§2.2 の実測(書記音節と拍のずれ)、§2.4(幅可変)。
- **決定1(表現)**: 上線方式。H の拍の上に線、下がり目で下がる。L と H の2段か H のみかは Q2 の判断で確定。
- **決定2(単位)**: 拍。クメール文字行では可視スロット(書記音節・末子音・長音マーカー)。あい=ៃ は半幅の線。
- **決定3(実装)**: 生成器が DOM の span を出し、CSS で描く。ADR-0003 の制約(結合文字は基底と同じ span)を守る。
  ADR-0007(Chao 声調文字の符号化)と ADR-0008(GSUB 伸縮・二重符号化)は**声調言語(kana-multi)のためのものとして維持し、ja-khmer には適用しない**。
  ADR-0010 決定6 の「声調と同じ方式で符号化上は妨げられない」は変わらないが、実装の前提(音節の定義が全角カナ+右肩)が合わない、と記録する。
  ADR-0008 を supersede するのではなく、適用範囲を明記(ADR-0010 決定6 に「本 ADR で決着」の言及を残し、frontmatter の `note` にも書く)。
- **決定4(データ)**: 句ごとの核の位置 n(0=平板)を入力(設計書 §2)に持つ。Wiktionary は候補の種で、人が確認したものだけを表示。合成規則は R0〜R3(§4.2)。
- **決定5(ライセンス)**: アクセントのデータは別ファイル・別のライセンス表記(CC BY-SA 4.0)、出典 URL と取得日を付ける。法的判断が別途要ることを書く。
- **決定6(ライトへの残し方)**: 暫定でライトにも残す。アクセント衝突率の測定後に見直す。
- **却下した案**: (B) ꜜ のみ、(C) Chao 声調文字、フォント方式(GSUB 伸縮の拡張)、`<ruby>`(未確認のため保留)。
- **未確認・残る作業**: iOS・Android 10/14 の実機確認、システムのクメール文字フォントの高さ、あい=ៃ の半幅の線、長音+撥音の並び(設計書 §8 #8)、活用形の型の規則、ダンプ全体からの抽出。
- **影響**: `packages/content` の `phrases.yaml` に句(空白区切り)と核の位置 n を足す。設計書 §3.3 を本 ADR に合わせて書き換える。

- ダンプ全体(1.6GB)からの抽出。ダンプ由来の他のデータセット(kaikki.org 等)の内容。
